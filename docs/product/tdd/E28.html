E28: Onboard plans: no dead ends

Technical design document brief · All scope belongs to the hackathon

Owner stream: B for the plans (E28-02, E28-03), with stream A for the schema, release validation and PlanRun engine (E28-01, E28-04), stream C for the assistant tools (E28-06) and stream D for the Assessment screen and plan card (E28-05). Dependency stage: S2. Depends on: E10 E26 E27.

Product contract

Requirements: R47 R50 R56 R57. Shared entities: OnboardPlan, PlanView, PlanRun. Read PRD (requirements R47, R50, R56, R57), pitch (the six acts), use cases (UC21 and UC22), contracts (section 22, onboard plans, and section 28, the invariants EI1 to EI12; endpoints in api/openapi.yaml), interaction design (section 3.8, the plan aboard, and section 8, the Assessment) and validation (scenarios V81 to V84 and V94; demo assertions D32, D36, D39 and D40) before designing.

The rule in one line: for every kit map row in every environment there is a plan the crew can run with what is aboard, starting with the best check this ship can do where the confirming test is missing; the log for the ground is always the last row and nothing waits for it. The ground is a reader of the log, never a step anything waits on. Every step, threshold and phrase comes from a versioned configuration document; clinical text is the team's reading of public sources, labeled “Unreviewed draft: needs clinician review” until a clinician checks it, and medicine steps say “as in the onboard procedure” with no dose.

Decisions the TDD must settle

Freeze the plan schema and its stage order (check it another way, do now, watch, if it gets worse, the medical officer, return where the environment allows it, the log for the ground last and never blocking); the four modes (resolve here, talk a crewmate through it, stabilize and watch, prepare to return); the release validation that every kit map row has, in every environment, a plan with at least one step any crewmate can run with that kit; split the plan rows among writers and second checkers; keep medicine steps as "as in the onboard procedure" with no dose anywhere. Decide how a plan written for its family is labeled and counted, how a step whose instrument, supply or skill is missing shows its substitute, how the controller checks an assistant's step choice against the active plan, and how a plan run records escalation into Someone needs help. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

Required work and acceptance

E28-01: Define the plan schema, stage order and release validation

Acceptance: onboard-plans.json validates against its schema; stages run in the fixed order with the log for the ground last and never blocking; release validation fails, naming the row and environment, when a plan lacks a step any crewmate can run with that environment's kit or lacks a watch or check step; in SIM the count shows the gap (EI3, EI4, V82).

E28-02: Write the plans for the seven demo conditions and the 20 responder flows

Acceptance: Each plan is written for its condition from its sources: every step has who, needs, source IDs and review state; medicine steps read "as in the onboard procedure" with no dose; every text carries the unreviewed label; a second person checks each plan (V83, D40).

E28-03: Give every other kit map row its form's ground needs and a plan from its family

Acceptance: Every other row carries its NASA form's ground needs, treatment scope and removal-to-definitive-care values copied with page numbers, and a plan from its family labeled as such; This kit reports [k] written for the condition and [119 minus k] from its family; no value comes from anywhere but the form; a second person checks each row (V82).

E28-04: Implement the PlanRun engine and its actions

Acceptance: A plan run starts on an episode or a help session; its actions are step done, not available, use substitute, escalate and close; its states are active, watching, escalated and closed, and none waits for the ground; an if-it-gets-worse step opens the named Someone needs help flow (EI5, V81, D40).

E28-05: Build the rewritten Assessment screen and the plan card

Acceptance: The Assessment shows Can't test here: check it another way and The plan aboard, rendered only from the API's plan view; no Prepare a summary for medical review action exists; the plan card's ground line reads the link state; the heart keeps its dashed ring and no text excludes the condition (D36, D39).

E28-06: Give the assistant the plan tools get_plan, choose_plan_step and explain_step

Acceptance: The three tools are in the tool catalog; the controller rejects and logs a step ID that is not in the active plan or cannot run with this kit, and any dose; step text always renders from configuration; with the model stopped every plan runs unchanged (EI6, V84).

TDD completion checklist

Specify API payloads and errors; state transitions and invariants; persistence/index choices; authorization and consent checks; unit/time/provenance handling; concurrency, idempotency and cancellation; resource limits and degradation; observability without private-content leakage; fixture IDs and acceptance evidence; dependencies and integration examples. Include a sequence diagram for the principal success path and a failure path. Name unresolved clinical or equipment assumptions explicitly.

Handoff to implementation

Produce the technical design document, concrete contract examples, implementation task breakdown and meaningful tests. Use the frozen shared contracts; propose changes through an explicit decision record. Mark evidence as planned until tests actually run. No feature is removed solely because the team has four developers.
