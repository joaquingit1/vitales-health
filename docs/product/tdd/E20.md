# E20: Accessibility, resilience and packaging

**Technical design document brief · All scope belongs to the hackathon**

Owner stream: D. Dependency stage: S4. Depends on: E03 E06 E08 E13 E14 E16.

## Product contract

Requirements: R24 R25 R26. Shared entities: ReleaseManifest, RecoveryReport. Read [PRD](../PRD.md), [contracts](../CONTRACTS.md), [LLM architecture](../LLM-ARCHITECTURE.md) and [validation](../VALIDATION.md) before designing.

## Decisions the TDD must settle

Decide packaging, local-network access, model scheduling and supported devices. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

## Required work and acceptance

### E20-01: Verify accessible responsive flows

Acceptance: Keyboard, focus, contrast, text labels and errors tested.

### E20-02: Verify offline, overload and recovery behavior

Acceptance: Inference/camera/forecast contention cannot block Someone needs help or corrupt records.

### E20-03: Package local deployment and operator runbook

Acceptance: Dependencies, models, corpus and hardware modes pinned; clean install reproducible.

### E20-04: Verify body map accessibility

Acceptance: Every region reachable by keyboard through the region menu; locks announced as text; marks distinguishable with color removed; reduced motion stills the figure; every text position on gradient cards measured at 4.5:1, or 3:1 for big numbers. See [UX design](../UX-DESIGN.md), sections 1.10 and 1.11.

## TDD completion checklist

Specify API payloads and errors; state transitions and invariants; persistence/index choices; authorization and consent checks; unit/time/provenance handling; concurrency, idempotency and cancellation; resource limits and degradation; observability without private-content leakage; fixture IDs and acceptance evidence; dependencies and integration examples. Include a sequence diagram for the principal success path and a failure path. Name unresolved clinical or equipment assumptions explicitly.

## Handoff to implementation

Produce the technical design document, concrete contract examples, implementation task breakdown and meaningful tests. Use the frozen shared contracts; propose changes through an explicit decision record. Mark evidence as planned until tests actually run. No feature is removed solely because the team has four developers.
