E03: Crew experience and daily check

Technical design document brief · All scope belongs to the hackathon

Owner stream: D. Dependency stage: S1. Depends on: E01 E02.

Product contract

Requirements: R03 R05 R24. Shared entities: DailyCheck, Answer, Observation, BodyRegion. Read PRD, UX design (section 1, visual direction, is binding for every screen), contracts (section 7, body regions), LLM architecture and validation before designing. The reference build is design/interaction-prototype.html; the figure comes from design/body-render.js and design/body-mesh.js.

Decisions the TDD must settle

Choose UI framework and accessible control patterns; integrate the body renderer and the visual-direction tokens. Decide how the stage, the card grid and the reading column share state (which region is peeked or locked, and by which control), how the renderer is paused while Someone needs help is open, and how the no-WebGL fallback is tested. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

Required work and acceptance

E03-01: Build home, daily flow and profile settings

Acceptance: Routine check can complete with skipped optional fields.

E03-02: Build measurement and indicator cards

Acceptance: Every value shows time, origin, quality and an understandable next step.

E03-03: Add optional reaction test

Acceptance: Raw timing records retained; interrupted test invalidated and excluded from comparison; taking or skipping the test never changes the streak, patches or crew goal.

E03-04: Implement the stage, body map and cards per the UX-DESIGN visual direction

Acceptance: Tokens, type scale, two-zone layout and the six Today cards match UX-DESIGN section 1 and the reference prototype; flows reuse the same stage and card grid with no tab bar; cards, vitals, symptoms, requests and assessment lines light their named region (hover peeks, click locks, Escape returns); filled, hollow and dashed marks follow object state; every value says Live, Replay or Sim; without WebGL all information remains in text.

TDD completion checklist

Specify API payloads and errors; state transitions and invariants; persistence/index choices; authorization and consent checks; unit/time/provenance handling; concurrency, idempotency and cancellation; resource limits and degradation; observability without private-content leakage; fixture IDs and acceptance evidence; dependencies and integration examples. Include a sequence diagram for the principal success path and a failure path. Name unresolved clinical or equipment assumptions explicitly.

Handoff to implementation

Produce the technical design document, concrete contract examples, implementation task breakdown and meaningful tests. Use the frozen shared contracts; propose changes through an explicit decision record. Mark evidence as planned until tests actually run. No feature is removed solely because the team has four developers.
