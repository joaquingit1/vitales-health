# E33: Stay or return

**Technical design document brief · All scope belongs to the hackathon**

Owner stream: B for the return stages (E33-01), with stream A for the ReturnReadiness view (E33-02) and stream D for the Return and Who decides cards (E33-03). Dependency stage: S4. Depends on: E28.

## Product contract

Requirements: R60. Shared entities: ReturnReadiness. Read [PRD](../PRD.md) (requirements R60), [pitch](../PITCH.md) (the six acts), [use cases](../USE-CASES.md) (UC26), [contracts](../CONTRACTS.md) (section 22, onboard plans, and section 27, stay or return; endpoints in `api/openapi.yaml`), [interaction design](../UX-DESIGN.md) (section 3.8, the plan aboard, Return and Who decides) and [validation](../VALIDATION.md) (scenario V94) before designing.

The rule in one line: on the Moon base a plan can end in preparing to return, with criteria and what to prepare; on Mars and in transit the plan says that return is not an option and stays aboard. The ground is a reader of the log, never a step anything waits on. Every step, threshold and phrase comes from a versioned configuration document; clinical text is the team's reading of public sources, labeled “Unreviewed draft: needs clinician review” until a clinician checks it, and medicine steps say “as in the onboard procedure” with no dose.

## Decisions the TDD must settle

Freeze the return stage (Moon base only), its criteria held as [to be set by flight rules], NASA's modeled chance from each form's Table 4 shown as context, the trip from NASA's figure, and the rule that the app lists and the commander and the medical officer decide. Decide how criteria stay as placeholders until flight rules exist, how the form's modeled values are copied with their page, and how the screen avoids any wording that reads as a decision. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

## Required work and acceptance

### E33-01: Write the return stages for lunar plans

Acceptance: Lunar plans may carry a return stage with criteria [to be set by flight rules], NASA's modeled chance from the form's Table 4 and the trip; Mars and transit plans have none and say Return is not an option from here (EI11, V94).

### E33-02: Serve the ReturnReadiness view

Acceptance: ReturnReadiness lists each criterion as met, not met or unknown and the prepare steps; the app never sets a decision; outside the Moon base it answers not applicable with the environment's words (V94).

### E33-03: Build the Return and Who decides cards and the Mars and transit wording

Acceptance: The plan detail shows Return and Who decides on the Moon base; on Mars and in transit the Return card reads Return is not an option from here. The plan stays aboard; the screen is kept out of the demo.
