E27: Kit map: what this ship can test

Technical design document brief · All scope belongs to the hackathon

Owner stream: B for the 119 rows (E27-01), with stream A for the engine and API (E27-02), stream C for the request gate (E27-03) and stream D for the screens and the venue study (E27-04, E27-05). Dependency stage: S2. Depends on: E01 E05 E10 E23.

Product contract

Requirements: R07 R43 R44 R45 R46. Shared entities: KitMap, KitMapView, KitCheck. Read PRD (sections 1, 4.12 and 11), pitch (what a judge sees, items 1 to 4, and act 1), use cases (UC19 and UC20), contracts (section 21 “Kit map” and section 11 “Configuration documents and the no-hardcoded-data rule”; endpoints in api/openapi.yaml), interaction design (sections 3.6 and 3.7) and validation (scenarios V76 to V80; demo assertions D28 to D31; the venue study in section 6) before designing. The source material is NASA's Clinical Findings Forms, listed in NASA-SOURCES.md section 5, and the 119 conditions of condition-assessments-119.csv.

The rule in one line: for each of the 119 conditions, the server computes from the kit map whether this ship's kit can measure it, can only hear what the person reports, or lacks the test that would confirm it, and every screen, request and handoff reads that one computed view. The rows are the team's reading of NASA's forms, written at the event, labeled unreviewed until a clinician checks them. The forms model a physician aboard, so the map uses them for what would confirm a condition, never for steps a non-doctor follows.

Decisions the TDD must settle

Freeze the kit map schema, the precedence rule that computes each condition's state, the kit per environment and the planning list; split the 119 rows among writers and second checkers; keep every state computed, never stored or typed. Decide how a condition with several confirming tests resolves when only some instruments are aboard, how an instrument that is connected, manual or import only counts toward Measured here, how body regions aggregate several conditions into one mark, how the what-if is bounded so it never writes, and how the request gate reports a missing instrument to the assistant without leaking other people's data. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

Required work and acceptance

E27-01: Write the 119 kit map rows from NASA's Clinical Findings Forms

Acceptance: Every row of the 119 conditions has its form link, body regions from the fixed list, the confirming tests with the instruments each needs, the findings a person can report, a writer and a second checker; review state unreviewed until a clinician checks it; the document validates against its schema; no row without a form link.

E27-02: Implement the kit map engine, the environment kits and the what-if

Acceptance: The server computes Measured here, Only what you report or Needs a test not aboard by the frozen precedence rule from the kit map and the current environment's kit; no state is stored; switching the environment recomputes; a planning what-if returns new counts and the conditions that change and persists nothing (V76, V77, V79).

E27-03: Gate every assistant measurement request on the kit map

Acceptance: Each request carries a kit check naming the instrument that can meet it or the missing instruments and form links; a request the kit cannot perform is rejected before it reaches a person and kept as an unresolved gap that reaches the handoff as Not available here (V78, D30).

E27-04: Build the This kit card, the kit view and the planning toggles

Acceptance: Today's This kit card and the kit view render only the API's computed view; the figure's dots, hollow rings and dashed rings match the states; a planning toggle fills exactly the rings the what-if returns and is labeled Planning view; the counts on the card, the kit view and the result panel are the same (D28, D29, D31).

E27-05: Run the venue study and publish How we know

Acceptance: The camera study protocol and consent wording are frozen before the first volunteer; adults only; people, windows, mean error, bias, refusal rate and one camera against two agreeing are reported with raw results; the assistant's turn time and rules alone against rules plus the assistant are published with failures counted; the How we know panel shows only numbers traced to the result panel and Not measured yet otherwise (V80).

TDD completion checklist

Specify API payloads and errors; state transitions and invariants; persistence/index choices; authorization and consent checks; unit/time/provenance handling; concurrency, idempotency and cancellation; resource limits and degradation; observability without private-content leakage; fixture IDs and acceptance evidence; dependencies and integration examples. Include a sequence diagram for the principal success path and a failure path. Name unresolved clinical or equipment assumptions explicitly.

Handoff to implementation

Produce the technical design document, concrete contract examples, implementation task breakdown and meaningful tests. Use the frozen shared contracts; propose changes through an explicit decision record. Mark evidence as planned until tests actually run. No feature is removed solely because the team has four developers.
