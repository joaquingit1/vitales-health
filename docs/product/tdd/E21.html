E21: Integration, evidence and demonstration

Technical design document brief · All scope belongs to the hackathon

Owner stream: D. Dependency stage: S5. Depends on: E07 E09 E15 E17 E18 E19 E20 E22 E23 E24 E25 E26.

Product contract

Requirements: R22 R26 R27 R30. Shared entities: CapabilityManifest, EvaluationReport, DemoRun. Read PRD, contracts, LLM architecture and validation before designing.

Decisions the TDD must settle

Freeze truthful demo claims and actual source modes. Run the frozen demo fixture demo-mara-fd19 (validation, section 3, assertions D01 to D44 across the six acts, with the ground link down from act 3) at every integration checkpoint in stub mode, and in live mode before any recording. Record alternatives, the selected design, evidence, failure modes and migration/rollback impact. This is a design brief, not an assertion that the technical design is complete.

Required work and acceptance

E21-01: Run end-to-end scenarios across all modules

Acceptance: Live, replay, simulation and unavailable paths clearly shown.

E21-02: Publish results, failures and limitations

Acceptance: Denominators and withheld/unrun cases included; no publisher score presented as ours.

E21-03: Prepare shared documentation and presentation package

Acceptance: Nine original modules plus expanded architecture trace to evidence and backlog.

TDD completion checklist

Specify API payloads and errors; state transitions and invariants; persistence/index choices; authorization and consent checks; unit/time/provenance handling; concurrency, idempotency and cancellation; resource limits and degradation; observability without private-content leakage; fixture IDs and acceptance evidence; dependencies and integration examples. Include a sequence diagram for the principal success path and a failure path. Name unresolved clinical or equipment assumptions explicitly.

Handoff to implementation

Produce the technical design document, concrete contract examples, implementation task breakdown and meaningful tests. Use the frozen shared contracts; propose changes through an explicit decision record. Mark evidence as planned until tests actually run. No feature is removed solely because the team has four developers.
