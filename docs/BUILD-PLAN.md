# Medicine potency engine: build plan

The contract is docs/ENGINE-SPEC.md plus the implemented foundation modules (`pharmacy/types.py`,
`pharmacy/constants.py`, `pharmacy/errors.py`, `pharmacy/config.py`, `pharmacy/contracts.py`), the generated schemas
and the configuration. Round 2 proceeds only after the coordinator approves the foundation spec and report.
The engine modules implement this contract on their owned files. Four builders own disjoint scopes; nobody edits
a file owned by someone else, except for the calibration value updates explicitly listed below.

## 1. Roles

| Role | Scope |
|---|---|
| Foundation (coordinator) | The contract: types, schemas, configuration, fixtures, vectors, spec, this plan. Frozen during the build; changes only through 5. |
| CX-B, numerical core | Exposure, microclimate, kinetics, uncertainty, update, decision, pipeline, store, offline fit. |
| CX-C, chemistry layer | Structures, pathways, LFER, BDE (xTB), radiolysis, parameter resolution; the xTB cache. |
| CX-CAL, calibration | Offline `pharmacy/calibration.py`, `tests/unit/calibration/**`, and values of total-rate priors and zone rate multipliers. |
| CX-D, independent verification | Environment simulator, mpmath oracle written from the spec alone, vector, validation, scenario and end-to-end tests, the validation report. |

Tests run with `--import-mode=importlib` and the repository root on `pythonpath` (pyproject), so test directories need
no `__init__.py` and test file names may repeat across directories. Shared helpers are importable by their path from
the root (for example `from tests.oracle.kinetics import ...`) and stay inside the owner's directory; a directory gets
its own `conftest.py` only if it needs fixtures.

## 3. Interfaces between builders

* CX-C to CX-B: `chemistry.parameters.build_stability_model(bundle, product_id, ingredient_id, package_ids)` returns a
  `StabilityModel` (spec 9). CX-B can also build `StabilityModel` values in tests and pass them through the
  `model` argument of `pipeline.estimate_potency`.
* CX-C to CX-B: `chemistry.radiolysis` functions are called by `kinetics.evaluate_draws` and the radiation report.
* CX-B and CX-C to CX-D: CX-D tests call only public functions named in the spec (15.2) and the pipeline entry points
  (`assess_inventory`, `replay`, `estimate_potency`, `forecast_lot`). CX-D never imports private helpers.
* CX-D to everyone: the oracle is the referee for deterministic quantities (1e-9 relative, spec 1.7 and 15.2). A
  disagreement is resolved by reading the spec: whichever side departs from it fixes its code; if the spec is ambiguous,
  the coordinator amends it (5) and both sides follow.

The round-2 numerical core files are the B1 scope; chemistry files are the B2 scope; verification files are the
B3 scope, including `tests/virtual/**`. CX-CAL reruns calibration from the supplied local vector file and checks
that committed prior and multiplier values equal its output exactly. Foundation defines the storage-condition
and calibration-provenance shapes without recalculating values.

## 4. Integration order

| Step | CX-B | CX-C | CX-D | Gate to advance |
|---|---|---|---|---|
| 1 | Scalars: `rate_constant`, `integrated_rate`, the closed forms and inverses, `humidity_integral`, `integrate_ode_reference`; microclimate; `mean_kinetic_temperature`; `derive_seed`, `batch_generator`, `jcgm_batch_size`, `numerical_tolerance`, quantiles; update primitives; decision helpers (Q1E, Q3B, ordering, `crossing_times`); store; fit | `structure`, `pathways`, `lfer`, `radiolysis`; BDE and the cache | Oracle for every 15.2 function; vector tests (15.1); `envsim` and its self-tests | Unit, oracle and vector tests green for the step-1 functions |
| 2 | Exposure (3); `draw_parameters`, `run_adaptive`; `evaluate_draws`, `nominal_thetas`, `placards_for` on hand-built models | `parameters` and `build_stability_model` for all ten formulary products, with the expected-pathway table | Oracle for `evaluate_draws` and `nominal_thetas` on fixed DrawBlocks; property tests reviewed | `evaluate_draws` agrees with the oracle; every formulary product builds |
| 3 | Pipeline wired to `build_stability_model`; forecasts, decisions, ordering, replay | Fixes from integration | Scenario tests (15.4) and end to end (15.6) on the demo fixture | Demo expectations hold; replay identical; outputs validate against schemas |
| 4 | Fixes | Fixes | Validation (15.5), coverage studies (15.7), docs/VALIDATION-REPORT.md | Validation rules evaluated and reported; coverage studies pass |
| 5 | Cold review of the whole package by a reviewer who did not build it; every finding fixed or answered | | | All gates of 6 green |

Builders start from the coordinator-approved foundation. CX-CAL and CX-C coordinate reference conversion so
calibrated `ln_k_ref_per_s` values are converted once, offline, and not again during estimation. CX-B fits use
chamber logs and sample packages; CX-D supplies those inputs and evaluates predictive measurement intervals.
A step is integrated only when its gate is green. Compression design and its error analysis are CX-B's
responsibility in spec 12.5. The coverage-regex requirement in `pyproject.toml` is already satisfied; that file is outside the foundation
engineer's round-2 editable files.

## 5. Contract changes

A builder who needs a contract change (a type, a schema, a config value, a spec rule) stops and asks the
coordinator. The coordinator edits the foundation files, regenerates schemas
(`.venv/bin/python -m pharmacy.contracts --write`), updates the spec, reruns the foundation gates and tells all four
builders what changed. Configuration values never change to make a validation test pass; only new sourced evidence
changes them, with a version bump and the source recorded.

## 6. Quality gates

Run from the repository root with the project venv (Python 3.14).

```
.venv/bin/python scripts/validate_contracts.py
.venv/bin/python -m mypy --strict pharmacy
.venv/bin/python -m ruff check pharmacy tests scripts
.venv/bin/python -m ruff format --check pharmacy tests scripts
.venv/bin/python -m pytest -q -m "not slow and not xtb and not validation" --cov=pharmacy --cov-branch --cov-report=term-missing
.venv/bin/python -m pytest -q -m xtb
.venv/bin/python -m pytest -q -m slow
.venv/bin/python -m pytest -q -m validation
```

| Gate | Rule |
|---|---|
| Contracts | `validate_contracts.py` prints `0 problem(s)` (schema drift, configs, fixtures, vectors, no en or em dashes). |
| Types | `mypy --strict pharmacy` clean. Tests are type-checked too: `.venv/bin/python -m mypy --strict tests`. |
| Lint | `ruff check` and `ruff format --check` clean. |
| Fast tests | All pass; branch coverage of `pharmacy/` at least 95% (`pharmacy/chemistry/bde.py` excluded, see pyproject). |
| xTB | All `xtb` tests pass; `bde.py` coverage reported separately (`--cov=pharmacy.chemistry.bde`). |
| Slow | End to end, coverage studies and virtual stability studies pass (spec 15.6, 15.7, 15.8). |
| Validation | Every dataset evaluated; rules of spec 15.5 met or the failure recorded in docs/VALIDATION-REPORT.md with sign-off. |

Markers are strict (`--strict-markers`): only `slow`, `xtb` and `validation` exist. A `DeprecationWarning` raised from
`pharmacy` is an error.

## 7. Rules for every builder

* Follow the spec literally; when it is silent or ambiguous, ask (5) instead of choosing.
* No numbers in code that a reviewer would want to change: they belong in `config/pharmacy` with a source (spec 1.3).
* Deterministic code only: no wall clock, no global random state, sorted iteration (spec 1.5).
* Raise the documented `PharmacyError` subclass; never return NaN, infinity or a silent default (spec 1.6).
* Published numbers in vectors are never edited; a mismatch is a finding.
* No network access in tests. No en or em dashes in any file.
* Do not commit; the coordinator integrates.
* Done means: the step's gate is green, the commands and their output are reported, and every skipped or
  `known_mismatch` test states its reason.
