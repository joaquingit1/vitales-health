## R-E02-1: Consent operations and projection contract

- Target: coordinator, product owner; CONTRACTS 2/5/19, OpenAPI and generated consent models.
- Exact proposal: define ConsentGrant with ID/revision, authenticated subject, actor, recipient kind/ID, mission and
  origin partition, exact object reference, purpose/action, explicit field IDs, policy version, valid_from,
  nullable valid_until and ends_with_ref, state and nullable closed_at. Fields/actions are nonempty bounded arrays;
  empty or unknown selection grants nothing. Add owner-only GET/POST /v1/consents and
  POST /v1/consents/{grant_id}/revoke. Creation takes recipient/object/purpose/actions/fields/validity, never an
  authoritative subject supplied by the caller; revoke takes Idempotency-Key and If-Match. Subject derives from
  SessionContext. Return only the caller's permitted grant projection, never another person's object contents.
  Use existing error codes and C5 paging; define effective schemas and payload maxima before generating code.
  Keep general consent separate from E22's accepted D10 crew-goal API.
- Reason: C2 specifies grants but the base package provides no general grant/revoke operation or field-projection
  schema. R02 and E02-03 need explicit owner action and durable revocation.
- Interim: authenticated owner CLI uses the same local grant/revoke application logic and S5.7/S5.8 transaction,
  identity, revision, validity and field checks. No invented HTTP route or consent event ships. Consumer-specific
  consenting commands require a settled port and explicit owner action; otherwise sharing stays off. Retain R02,
  E02-03, V64 and auditable export history; UI acceptance remains pending.

  authenticated presence operation that advances the idle anchor only on explicit user interaction. Its body carries

  Preserve unattended/offline-screen protection, R02, E02-03 and fixed emergency access. No private screen without
