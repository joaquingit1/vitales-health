# E02 requests

Addressed to the coordinator unless an entry names a provider for propagation. Decisions in
`docs/requests/COORDINATOR-DECISIONS.md` Part A and `docs/SYSTEM.md` already bind implementation.
A pending proposal below is not an accepted shared interface or an effective-contract overlay input.
Disabled integration is reported as incomplete acceptance, never as a pass.

## R-E02-1: Consent operations and projection contract

- Target: coordinator, product owner; CONTRACTS 2/5/19, OpenAPI and generated consent models.
- Exact proposal: define ConsentGrant with ID/revision, authenticated subject, actor, recipient kind/ID, mission and
  origin partition, exact object reference, purpose/action, explicit field IDs, policy version, valid_from,
  nullable valid_until and ends_with_ref, state and nullable closed_at. Fields/actions are nonempty bounded arrays;
  empty or unknown selection grants nothing. Add owner-only GET/POST /v1/consents and
  POST /v1/consents/{grant_id}/revoke. Creation takes recipient/object/purpose/actions/fields/validity, never an
  authoritative subject supplied by the caller; revoke takes Idempotency-Key and If-Match. Subject derives from
  SessionContext. Return only the caller's permitted grant projection, never another person's object contents.
  Use existing error codes and C5 paging; define effective schemas and payload maxima before generating code.
  Keep general consent separate from E22's accepted D10 crew-goal API.
- Reason: C2 specifies grants but the base package provides no general grant/revoke operation or field-projection
  schema. R02 and E02-03 need explicit owner action and durable revocation.
- Interim: authenticated owner CLI uses the same local grant/revoke application logic and S5.7/S5.8 transaction,
  identity, revision, validity and field checks. No invented HTTP route or consent event ships. Consumer-specific
  consenting commands require a settled port and explicit owner action; otherwise sharing stays off. Retain R02,
  E02-03, V64 and auditable export history; UI acceptance remains pending.

## R-E02-2: Lockout response

- Target: coordinator, product error/schema owner.
- Exact proposal: add SIGN_IN_LOCKED, HTTP 429, retryable true, with a bounded retry_after instant in current_state
  for createSession; generate the status table and configured error words. Do not expose whether a person exists.
- Reason: the existing createSession responses cannot express a typed rate-limit result.
- Interim: generic IDENTITY_MISMATCH under the current operation contract for credential/lockout refusal;
  capacity/storage failure remains INTERNAL_ERROR. Independent person/client/global limits, timing equalization,
  secret-safe errors and help responsiveness remain mandatory. No undeclared code or free-form private error detail.

## R-E02-3: Renewable human-presence session policy

- Target: coordinator, E01 HTTP boundary, E02 and E03; Session schema and session operations.
- Exact proposal: expose a validated session security policy with idle duration and absolute maximum, plus an
  authenticated presence operation that advances the idle anchor only on explicit user interaction. Its body carries
  a monotonic client activity sequence, not client authority over time; the hub timestamps acceptance and bounds
  renewal by absolute lifetime. Bind it to current session/device generation, and define idempotency and replay
  rejection in the effective contract. Add no editor actor kind: S5.7 already settles editor attribution.
- Reason: Session has only created_at and expires_at; background polling cannot be human presence, and a client must
  lock without waiting for a 401.
- Interim: issue short nonstation sessions capped by security.idle_lock_minutes. Derive the local budget from the
  configured created_at/expires_at interval, start the conservative monotonic timer at request dispatch, clip to the
  absolute expiry and never extend it from background traffic. Local human activity cannot extend beyond that cap;
  active users reauthenticate. Hide/suspend/offline locks immediately; E03 epoch/draft cleanup remains mandatory.
  Preserve unattended/offline-screen protection, R02, E02-03 and fixed emergency access. No private screen without
  a known policy deadline; no hardcoded idle duration.

## R-E02-4: Private deletion operation

## R-E02-5: Durable invalidation and local-secret mutation declarations

- Target: coordinator, SYSTEM 4.2/5.7/5.12, E01 events/platform and E02.
- Exact proposal: publish an exact SessionRevocation/SessionValidator protocol that accepts the caller's
  ReadSnapshot or UnitOfWork, checks session/principal/device generation and returns a typed live/ended decision.
  Every SSE delivery and heartbeat uses it from current durable state; private batches carry the checked generation
  and are discarded on mismatch. Notifications close streams promptly but never authorize them. Vault decryption
  uses the same current session check in addition to its S7.4 revocation generation. Specify the linearization of a
  concurrent revoke and delivery and test separate CLI/hub processes with no intervening HTTP request.
  Register identity_auth_bucket and identity_access_generation as E02 local tables. Define an explicit local-only
  mutation declaration in the S5.7 registry so credential/session/token/bucket writes pass commit accounting without
  storing secrets in replication payloads. Include exact finite descriptor ceilings for the shared bounds inherited
  in E02 section 11; registry completeness is a startup gate, not an E02 default.
- Reason: SYSTEM names SessionRevocation but lacks its exact cross-process API; every mutation requires a replication
  declaration, while authentication secrets must not replicate. Callback-only liveness leaks on CLI revocation.
- Interim: authenticate all HTTP operations directly against durable state. Disable private streaming and any shared
  secret-mutation integration that cannot enforce local-only declarations until this mechanism is settled. Public
  emergency cache and manual-record policy remain. Keep E02-03 immediate subsequent-read denial, secret isolation,
  audit atomicity and stream revocation tests; unbuilt stream integration remains incomplete, not passed.

## R-E02-6: E03 shared private protocol and client lifecycle propagation

- Target: E03, coordinator and E01 platform; E03 sections 2/4.3/7.2, ui-copy owner.

  PrivateJournalCoordinator, exactly including fingerprint, current owner authorization, seal, replay receipts,

- Interim: build protocol fakes against SYSTEM, not the older key interfaces. Journal integration remains off until
  the real two-store and vault tests pass; owner CLI/local lock integration cannot claim journal acceptance. Preserve
  R20, D4 crash/deduplication, private HMACs, no browser persistence, owner responses and E02-03 offline locking.

## R-E02-16: Owner recovery and restored authentication freshness

- Target: coordinator, E01 recovery, E02 vault and deployment owner.
- Exact proposal: specify how a restored hub proves the latest credential/access generation against current local
  recovery material before authenticating old credentials. Specify owner-controlled recovery authorization for
  private unwrap independently of operator account reset, and bind it to the current S7.4 vault generation; no
  credential-derived wrapping secret, snapshot escrow or stale recovery medium may reconstruct deleted keys.
  Any current vault recovery device participates in the existing revocation receipt barrier. Define the exact
  recovery-state/authorization interface centrally, rather than another two-store protocol inside E02.
- Reason: S7.4 settles deletion and backup safety but not forgotten-credential owner authentication or credential
  freshness after a pre-reset backup. Operator reset alone cannot prove owner consent to private-data access.
- Interim: no automatic destructive reset or private recovery from old credentials. An owner who proves the old
  credential may change it atomically in the hub. Operator reset of an existing account stays disabled until the shared protocol can durably lock prior private
  unwrap atomically with reset. An operator may provision a new account ID for nonprivate operations, with no claim
  to prior private records; owner recovery remains unavailable. Old-generation restore authentication
  is disabled pending reconciliation; local provisioning and fixed help remain available. Preserve R20, no deleted
  key resurrection, no cross-owner access, accepted ciphertext retention and honest pending/unavailable states.
