# Requests from E23: Environment profile and habitat sensors

One entry each: target, exact proposal, reason, interim. The interim never switches off a safety check, a validation
or an acceptance criterion; where no safe interim exists, the feature stays off and says so. Design:
`docs/tdd/E23.md`.

## R-E23-1 Freshness basis of REPLAY channels (coordinator ruling)

**Decided:** option A, by the owner on 14 November; recorded as decision D8 in COORDINATOR-DECISIONS.md and built
in E23 design 3.4.

- **Target:** the coordinator, because it applies decision D3; then `api/schemas/requests.schema.json`
  (`AdapterReadingBatch`), `api/schemas/sensor-reading.schema.json` and CONTRACTS.md section 13 "Freshness" if option B
  is chosen.
- **Proposal:** rule on one of two options.
  - **A.** A REPLAY channel's freshness reference is the hub receive time of the latest accepted reading that advanced
    the channel's window end E. A reading that does not advance E (a replay restarted from the top, a late or repeated
    row) never refreshes it.
  - **B.** Add `played_at` (instant, required) to the `replay` object of a batch reading and of `SensorReading`: the
    instant on the adapter's synchronized clock at which it played the sample. Freshness of a REPLAY channel is
    computed from `played_at`, under the same future tolerance and `clock_state` rules as LIVE observation times.
- **Reason:** decision D3 computes freshness from the observation time on the hub's corrected clock. A REPLAY
  reading's `observed_at` is its original date (2014 for the RR-1 file), so it cannot be compared with the hub clock,
  and D3 did not address this case. Option A uses an arrival time, which D3's wording forbids for LIVE data, so it
  needs an explicit ruling. Option B needs a contract change but keeps D3's letter.
- **Interim:** none; decided as option A (decision D8) and built in E23 design 3.4. LIVE and SIM follow D3
  unchanged.

## R-E23-2 Plausibility criteria in the sensor catalog

- **Target:** `api/schemas/config-sensor-catalog.schema.json`, CONTRACTS.md section 11 "The sensor catalog", loader
  check 12.
- **Proposal:** an optional `plausibility` object per sensor type: `min`, `max` (canonical unit), `saturation_values`
  (list), `stuck` (`count` of identical consecutive readings and the `span_seconds` they must cover, in observation
  time), `max_rate_per_second`, each with `basis` and `source_ids`. A reading that fails is stored with
  `quality_status` `rejected` and the failed check named; a stuck channel cannot show `within_limit`.
- **Reason:** AGENTS.md section 2 requires range, saturation, stuck value and rate of change checks on every input.
  Their criteria are domain content, so they cannot live in code or in hub settings, and no document holds them.
  Borrowing another number (for example `stale_after_seconds`) gives a check with no basis that misfires on quantized
  data such as the RR-1 file.
- **Interim:** the checks that need no criterion run on every reading (finite value, unit, timestamps, sequence,
  origin, quality status). The four bounded checks stay off, and the channel registry refuses every LIVE channel
  until its sensor type has criteria, so no real sensor reaches the crew without them; REPLAY and SIM values carry
  their source word.

## R-E23-3 Channel registry

- **Target:** CONTRACTS.md section 11 "The documents"; SYSTEM.md 5.11.
- **Proposal:** decide where sensor channels are declared: a nineteenth configuration document `sensor-channels.json`
  pinned by the release, or a deployment file next to the adapter tokens. E23 proposes the configuration document,
  because a channel's interval and stale time carry domain meaning.
- **Reason:** `SensorChannel` is served by the API but no command or document creates one.
- **Interim:** `<data_dir>/sensor-channels.json`, validated at start against the static part of
  `sensor-channel.schema.json`, with a `basis` on every interval or stale override; an invalid file is rejected and
  the last good one stays loaded; the demo registry loads only with the demo profile in a SIM or REPLAY mission,
  after `mission init`, from E23's interim copy under `eval/scenarios/e23/demo/` until E21 holds it (R-E23-15).

## R-E23-4 Mission identity and the first profile

- **Target:** SYSTEM.md 4.2 (tables of `mission`), DEPLOYMENT.md 6.2 and 7.1; E26 and every consumer of
  `MissionStatePort`.
- **Proposal:** a single-row `mission_identity` record (`mission_id`, `mission_mode`, `planned_length_days`) and the
  first EnvironmentProfile (reason `mission_start`) written together by `crew-health mission init`, audited; changing
  the mode needs a new mission. Before init the hub runs, `MissionStatePort` returns `None` for mission, mode and
  environment, and every consumer handles `None` without blocking Someone needs help.
- **Reason:** `MissionContext` serves these fields and every module reads the mode, but nothing in the package or
  SYSTEM.md says where they are set or how the first active profile is created.
- **Interim:** as proposed (E23 design 3.3). Consumers that type these values as non-null keep working once init has
  run, which the demo profile does from the fixture.

## R-E23-5 One set of E23 port names and shapes

- **Target:** SYSTEM.md 4.2 and 4.4; designs E01, E03, E04, E11, E12, E13, E15, E22, E24, E25, E26, E27, E28, E30,
  E31, E33.
- **Proposal:** record the ports and signatures of E23 design section 4.2 and retire the local names for the same
  seams: `EnvironmentPort`, `ActiveEnvironmentReader`, `MissionPort`, `MissionReader`, `EnvironmentFactsPort`,
  `EnvironmentProfileReader`, `OverlayReader`, `EnvironmentReader`, `SensorSummaryPort`. Shape differences to settle:
  `MissionStatePort.current` takes an optional snapshot (E25 and E28 call it with none, E24 passes a unit of work) and
  returns `MissionFacts | None`; `mission_mode` and `active_environment_id` return `None` before mission init (E33
  already expects `None`); `OverlayPort.active` takes a collection of person IDs (E11 passes one ID); E01 reads
  `planned_length_days` from `MissionStatePort.current()` rather than from `MissionRef`; `DayLabelPort.inline_label_at`
  is provided by E23 (E15, E28, E31); `ProvenanceStreamsPort.habitat_streams` is provided by E23 (E27); E25 does not
  consume `SensorEvaluated`.
- **Reason:** many designs declared E23's seams under different names and shapes before an E23 design existed.
- **Interim:** E23 provides the 4.2 ports; each consumer maps its local name in its own gateway, as their designs
  already plan with fakes.

## R-E23-6 Ground link in views

- **Target:** `api/schemas/habitat-view.schema.json`, `api/schemas/mission-context.schema.json` and
  `api/schemas/context.schema.json` (`getContext`, decision D10); E29 design (not
  written yet); SYSTEM.md 4.2.
- **Proposal:** (a) make `ground_link` nullable in HabitatView, MissionContext and ContextView, null meaning "ground link state
  unavailable", which the client renders from ui-copy; (b) E29 provides `GroundLinkQuery.view(snapshot: ReadSnapshot)
  -> GroundLink`, the contract object.
- **Reason:** both responses require a `GroundLink`, so a failing E29 fails the whole Habitat view, the screen where
  stale and beyond-limit sensors are shown. CONTRACTS.md section 19 says nothing on a screen depends on the ground
  link.
- **Interim:** with E29 absent or failing, the two operations answer `INTERNAL_ERROR` (retryable) naming
  `ground_link` as unavailable; no link object is invented. The Habitat client falls back to `listSensorStatus` and
  the warnings list, so every sensor card and warning stays on screen.

## R-E23-7 Person of an overlay created by an operator

- **Target:** `api/schemas/requests.schema.json` (`OverlayCreate`).
- **Proposal:** an optional `person_id`, honored only for `operator` and `crew_medical_officer` sessions.
- **Reason:** CONTRACTS.md section 12 says an operator can start an overlay, but the body names no person and an
  operator session has none.
- **Interim:** an operator records a mission event with `person_ids` (the configured types start and end overlays).
  A `createOverlay` from a session with no person is `INVALID_VALUE`.

## R-E23-10 Words for "what changed" (E03)

- **Target:** `config/ui-copy.json` and its schema (owner E03).
- **Proposal:** `designed_states.environment_activated` with `{place}` ("You are now on {place}"), and heading words
  for the lists of what an activation switched on and off: hazards, sensors, routine tasks, ground delay.
- **Reason:** V66 and UC12 require the app to say what changed after a switch; no configured words exist for it, and
  the client may not hold them.
- **Interim:** the panel stays off and says nothing; the Habitat screen itself shows the new hazards, sensors and
  ground delay; V66 is reported as partly met.

## R-E23-11 UCUM codes in the sensor catalog

- **Target:** `api/schemas/config-sensor-catalog.schema.json`.
- **Proposal:** a required `ucum` field next to `unit` and next to each `accepted_units[].unit`, for example `mmHg`
  with `mm[Hg]`, `dBA` with `dB{A}`, `index` with `{index}`.
- **Reason:** AGENTS.md rule 8 and SYSTEM.md 5.4 carry UCUM units in every quantity; the catalog's units are display
  spellings and two of them (`dBA`, `index`) have no UCUM code.
- **Interim:** one spelling to UCUM table in `sensors/domain/units.py`, key to key like the fixed vocabulary; a
  catalog unit missing from it rejects the release.

## R-E23-13 stale_since and series channel

- **Target:** CONTRACTS.md sections 11 and 13; `api/openapi.yaml` (`getSensorSeries`).
- **Proposal:** (a) say whether `SensorStatus.stale_since` is the last observation time or the time the channel
  became stale. E23-02 asks for "No data since" with the last time, while the example sets it to the last
  observation plus `stale_after_seconds` (status-noise-quiet.json). (b) Add an optional `channel_id` query parameter
  to `getSensorSeries`.
- **Reason:** the package disagrees with itself on (a); a sensor type can have several channels and the series names
  only one.
- **Interim:** (a) C11 and the example: `stale_since = reference + stale_after_seconds`. (b) The series serves the
  card channel; other channels' values appear in the card `trace`.

## R-E23-14 Per-channel status and a conflict state

- **Target:** `api/schemas/sensor-status.schema.json` or `habitat-view.schema.json`; `config/ui-copy.json` (E03).
- **Proposal:** a `channels[]` list on SensorStatus (channel ID, source label, location label, display value,
  evaluation status) and `designed_states.channels_disagree`.
- **Reason:** AGENTS.md section 2: when sources disagree, show the conflict. The card can show one channel.
- **Interim:** the card shows the worst channel and its `trace` lists every other channel's source, location and
  value, joined by separators only.

## R-E23-15 Demo feed file and fixture copies (E21)

- **Target:** E21 design (`fixtures/demo-mara-fd19/**`), SYSTEM.md 4.3 fixture ownership.
- **Proposal:** (a) `fixtures/demo-mara-fd19/sensors/feeds.json` follows `adapters/habitat/schemas/feeds.schema.json`
  (E23), and E23's `crew-health adapters replay` and `adapters sim` replace the interim `CsvReplayFeeder` (E21

- **Interim:** E23 ships the demo registry, the feed file and the NASA file copies under its own
  `eval/scenarios/e23/demo/`, loaded only by the demo profile (E23 design 5.3); the demo acceptance tests and walking
  skeleton W1.5 use them. When E21's fixture carries the same files, the demo profile points at E21's and E23's copies
  are removed.

## R-E23-16 Health component for sensor faults

- **Target:** SYSTEM.md R-SYS-9 (health response schema; TodayView and HabitatView); `config/ui-copy.json` (E03).
- **Proposal:** add health component `sensors` with state `degraded`, `since` and the codes `EVALUATION_UNAVAILABLE`,
  `SCHEDULER_LAG`, `INSTANT_CONFLICT`, `SEQUENCE_CONFLICT` and `WINDOW_SCAN_BOUND`; include `sensors` in the views' `evaluation_notice`;
  add ui-copy words for each code.
- **Reason:** E23 reports these five faults through health (E23 design 3.4), but R-SYS-9 names only the `rules` and
  `pathways` components and no words exist for these codes.
- **Interim:** the faults are served by `/v1/health`, which the operator panel and the station read (the R-SYS-9
  interim); no crew screen shows a sentence for them. The crew side stays safe by behavior: a pending evaluation keeps
  the last status and blocks every clear, the sweep runs during scheduler lag, a conflict is evaluated on its worse
  variant, an unevaluated limit shows `insufficient_data`.

## R-E23-17 Model release on the assistant status port (E13)

- **Target:** E13 design 4.2 (`AssistantStatusPort`).
- **Proposal:** add `model_release_id(self) -> str | None`, the release the assistant runs, `None` only when none is
  installed.
- **Reason:** `getContext` (decision D10, E23 design 6.1) serves `model_release_id`; the port E03 declared and E13
  provides exposes only `state()`.
- **Interim:** `getContext` serves `model_release_id` `null` and E23 design 6.1 documents it as a gap, not as a claim
  that no model release exists; `assistant_state` is served from `state()`.
