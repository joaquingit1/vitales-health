# Requests from E18 (HealthBench and clinical evaluation)

Each entry: target, exact proposal, reason and interim. Every interim names the checks it keeps; none drops a safety
check, a validation or an acceptance criterion. The design (`docs/tdd/E18.md` section 14) only references these.

## R-E18-1 Settings for evaluation members

- **Target:** coordinator; `docs/SYSTEM.md` section 5.11.
- **Proposal:** add to 5.11: "Processes outside the hub that never hold crew records (the evaluation members
  `eval/bench` and `eval/harness`) keep their operational bounds in `<member>/config/<member>-settings.json`, one
  `{value, unit, basis, to_be_set_by}` object per key as in `hub-settings.json`, validated at start by a schema the
  member owns and read through the `HubSettings` protocol implemented over that file. Keys are prefixed with the member
  name (`bench.`, `harness.`)."
- **Reason:** COORDINATOR-DECISIONS D7 makes queue sizes, timeouts and retries hub settings, but E18 never runs inside
  a hub and has no `<data_dir>/hub-settings.json`. E21 put the same kind of bounds in `profiles.json`; one shared rule
  avoids two shapes.
- **Interim:** `eval/bench/config/bench-settings.json` with exactly that shape, read through a `HubSettings` shaped
  reader in E18's adapters. Keeps every bound, limit and test of E18 section 11; nothing runs unbounded; an invalid
  settings file refuses the run (exit 4).

## R-E18-2 Evaluation documents outside the configuration release

- **Target:** coordinator; `docs/SYSTEM.md` 5.6 and CONTRACTS.md section 11 ("The documents").
- **Proposal:** add to SYSTEM.md 5.6: "Documents that configure evaluation tooling and never reach a crew hub
  (`eval/bench/config/*.json`, `eval/harness/config/*.json`) are not configuration release documents. Each has a JSON
  Schema owned by its member, provenance per value group with `basis`, `source_ids` and `to_be_set_by` from
  `common.schema.json`, a loader that refuses an invalid document without substituting a last good version, and its
  SHA-256 recorded in every run manifest that used it."
- **Reason:** AGENTS.md rule 1 puts content in versioned documents with provenance, and CONTRACTS section 11 lists only
  the 18 hub documents. E18's partition policy, HealthBench plan, suites and claims policy are content (thresholds,
  gates, forbidden phrases) but belong to no hub module and must not ride in a crew release.
- **Interim:** as proposed (E18 section 8). Keeps schema validation, provenance, the refusal of invalid documents, the
  manifest hashes and the configuration edit test T-E18-17.

## R-E18-3 Kernel imports and ID prefixes for evaluation members

- **Target:** coordinator; `docs/SYSTEM.md` 6.2 and 5.1.
- **Proposal:** add to 6.2: "Evaluation members may import `crew_health.kernel` (pure: `Clock`, `IdFactory`,
  `Quantity`, `UnitRegistry`, `require_id`) and `crew_health.contracts_gen`, and nothing else from the hub package."

  artifact, and module independence.

## R-E18-4 Owner of eval/harness and the eval/freeze member

- **Target:** coordinator; `docs/SYSTEM.md` 4.3, 6.1 and 6.2; R-SYS-10 member list. Answers E21 request 16.
- **Proposal:** 4.3 rows read "`eval/bench/`, `eval/freeze/` | E18 | HealthBench harness and the freeze library" and
  "`eval/harness/` | E21 | Scenario harness"; 6.1 reads "`eval/bench/  eval/freeze/` E18, `eval/harness/  eval/runner/`
  E21, `eval/scenarios/<epic>/` each epic"; 6.2 and R-SYS-10 add the member `eval/freeze` (distribution
  `crew-health-freeze`, package `crew_health_freeze`) holding `freeze_tree`, `verify_tree` and `FrozenManifest`.
- **Reason:** SYSTEM.md 4.3 lists `eval/harness/` under E18 while E21's design owns `eval/harness/**`. E21 imports the

- **Interim:** E18 claims only `eval/bench/**`, `eval/vault/**` and `eval/scenarios/E18/**`; the freeze library stays in
  `crew_health_bench.freeze` (E21's interim); `crew_health_bench` imports `crew_health_harness` only in its hub system
  adapter, as an optional extra, so the cycle never forms at import time. Keeps the freeze check of the demo fixture and

## R-E18-5 condition_ids on Assessment hypotheses and missing evidence

- **Target:** package; `api/schemas/assessment.schema.json`, CONTRACTS section 2.
- **Proposal:** add optional `condition_ids` (array of strings matching `^ICL[1-9][0-9]{0,2}$`, `uniqueItems: true`) to
  the items of `hypotheses` and `missing_evidence`, validated by the controller against
  `condition-assessments-119.json`.
- **Reason:** E18-03 acceptance asks for serious omissions reported independently, which needs a deterministic match;
  `request_measurement` already carries `condition_ids` (model-action schema). E13 supports this request.
- **Interim:** `AlternativesInclude` is `not_graded` and `serious_omission` reads "not graded deterministically"; the
  clinical review sample grades omissions where a reviewer exists. Every other category, the gate and the acceptance
  criteria of E18-01 and E18-02 are unchanged; E18-03's omission criterion is reported as not met rather than
  approximated.

## R-E18-8 timeout as Quantity on BenchmarkAnswerPort.answer and HubClient.call

- **Target:** E13 (provider of `BenchmarkAnswerPort`, declared by E18) and E21 (`HubClient`).
- **Proposal:** E13: `answer(messages: Sequence[ChatMessage], *, evidence_release_id: str, tool_profile: str, timeout:
  Quantity) -> BenchmarkAnswer`, with `BenchmarkAnswer{text, tool_calls[], provenance_ids[], limitations[],
  finish_reason}`. E21: `HubClient.call(..., timeout: Quantity) -> ApiResponse` in place of `timeout_s: float`.
- **Reason:** SYSTEM.md 5.4 and AGENTS.md rule 8: no bare float crosses a module boundary.
- **Interim:** E18's adapters convert the `Quantity` to seconds at the call to each provider's current signature; no
  timeout or bound is dropped. Until E13 provides the port at all, the system-assisted HealthBench track is `not_run`
  with that reason, and the product suites use the public API.
