# Contract change requests from B3 (verification)

Each entry gives the exact proposed change, the reason and the interim behavior the B3 tests implement now (the code
cites the request number). B3 edits no foundation file; every change below is for the owner of that file to decide.
A request marked answered needs no change.

---

## R1. Location of the virtual-study fixture

**Proposed change (pharmacy/contracts.py `repository_problems`, the fixture loop):** validate only scenario
fixtures as scenarios, for example `for path in sorted(...glob("*.json")): if path.name == "virtual-studies.json":
problems += schema_violations(load_json(path), <tests/virtual/virtual-studies.schema.json>); continue`, or name
scenario fixtures by a pattern (`demo-*.json`, `scenario-*.json`) and glob that.

**Reason:** spec 15.8 puts the study designs in `fixtures/pharmacy/virtual-studies.json`, but the contract validator
loads every `fixtures/pharmacy/*.json` with `pharmacy/scenario.schema.json`. The designs are not a scenario, so the
file at the spec's path makes `scripts/validate_contracts.py` fail.

**Interim:** the fixture lives at `tests/virtual/virtual-studies.json` (validated by
`tests/virtual/virtual-studies.schema.json` in `tests/virtual/test_virtual_fixture.py`). Moving it is one line in
`tests/virtual/studies.py` (`FIXTURE_PATH`).

## R2. Spec 15.4: the OU variance criterion of the simulator self-test

**Proposed change (spec 15.4, simulator self-tests):** replace "empirical OU variance within 20% of sigma^2" with
"empirical OU variance within the 99.9% band of its sampling distribution, sigma^2 (1 +- 3.29 sqrt(2 tau / T_span))
for a series of span T_span", or lengthen the self-test series until the 20% band is at least 3 standard errors
wide (T_span >= 2 tau (3.29 / 0.2)^2, about 540 tau).

**Reason:** over the 30-day self-test mission the sample variance of an OU process with tau of several hours has a
relative standard error near 0.13 to 0.18, so the 20% band is 1.1 to 1.5 standard errors and a correct generator
fails it often. Three of the eight zone and quantity series fail with the self-test seed (transit_kit temperature,
station_kit RH, mars_base_pharmacy RH) while their means, autocorrelation and exact-discretization checks pass.

**Interim:** those three cases are strict xfails carrying finding B3-F1 (`tests/scenarios/test_envsim.py`); nothing
is tuned.

## R3. Spec 9.7: median of a fixed zone multiplier

**Proposed change (spec 9.7):** replace "ln m = mu" with "ln m = mu for a lognormal multiplier and ln(value) for a
fixed one".

**Reason:** `types.Prior` with family fixed stores the multiplier itself in `mu` (value = mu), so "ln m = mu" read
literally makes a fixed multiplier of 1 a multiplier of e.

**Interim:** the oracle takes ln(mu) for fixed priors (`tests/oracle/draws.py`, `median_ln_multiplier`).

## R4. Spec 5.8: the API molar mass for degradant percent

**Proposed change (types.StabilityModel):** add `api_molar_mass_g_per_mol: float` (from the formulary ingredient).

**Reason:** the degradant amount in percent of label API mass needs the ratio of the degradant's molar mass to the
API's (spec 5.8), but the model carries only the degradant's. The oracle receives the API molar mass as an argument
and so cannot be called from the model alone.

**Interim:** `tests/oracle/draws.py` takes `api_molar_mass_g_per_mol` as a keyword argument.

## R5. Spec 9.9: how p enters the JCGM 101 batch size

**Proposed change (spec 9.9):** state "M = max(ceil(100 / (1 - p)), 10^4) with p taken as the decimal number written
in configuration".

**Reason:** in binary floating point 100 / (1 - 0.9995) is 200000.00000000017, so ceil gives 200001 while the
decimal reading gives 200000. The spec does not say which.

**Interim:** the oracle reads p as its shortest decimal representation (`tests/oracle/exact.py`,
`jcgm_batch_size`).

## R6. Spec 11.6: rounding against ICH Q3B thresholds written with a trailing zero

**Proposed change (spec 11.6):** state the number of decimals of each threshold explicitly in configuration (for
example `decimals: 2` for 0.10%) instead of deriving them from the number.

**Reason:** Q3B rounds an observed result to the decimals of the threshold as written. A JSON number 0.10 is 0.1,
so the decimals are lost; 0.10% and 1.0% thresholds cannot be applied as written. The engine and the oracle agree
on every rounding point the tests check today; the request is about thresholds as Q3B writes them.

**Interim:** the oracle uses the decimals of the shortest representation (`decimals_as_written`).

## R7. Spec 11.5: `ordering_key` needs the lower quantile

**Proposed change (spec 11.5 signature):** add `lower_quantile: float` to `decision.ordering_key`, or document that
the function reads `decision.lower_quantile` from settings passed in another argument.

**Reason:** the out-of-specification ordering uses the estimate's quantile at `decision.lower_quantile`, which the
documented signature does not receive.

**Interim:** the oracle takes it as an explicit argument.

## R8. Spec 13.1.3: illuminance and UV sensors

**Reason:** the profiles give noise and bias only for temperature, RH and dose sensors.

## R9. Spec 13.1.3: clipping after quantization

**Proposed change (spec 13.1.3):** append "Readings are clipped to the physical domain again after quantization."

**Reason:** quantizing a clipped RH of 100 to a 0.1 resolution gives 100.00000000000001 in floating point, which the
inputs schema rejects.

**Interim:** implemented as proposed in `pharmacy/envsim.py`.

## R10. Spec 13.1.2: truth grid and sampling end points

**Proposed change (spec 13.1.2):** state "The truth grid is t0 + k dt for k = 0..N, N = ceil((end - start) / dt);
sampling instants are t0 + j dt_sample for every j with t_j <= end; outages cover [start, start + duration)."

**Reason:** the spec does not say whether the grid reaches mission end when the span is not a whole number of
steps, nor whether outage intervals are open or closed.

**Interim:** implemented as proposed (snap tolerance 1e-9 steps).

## R11. Spec 15.8: interpolation inside the truth integral

## R15. Spec 15.8: the prediction interval and the conditions handed to study fits

**Proposed change (spec 15.8):** define "the selected model's 95% prediction interval" as the 2.5% and 97.5%
quantiles of potency at (T, RH, t) over a multivariate normal on the fit's mean and covariance (N = 4000 draws). For
the fit conditions, either (a) state that each observation receives the chamber log's mean temperature and RH from
the start of the condition to its pull (what a laboratory records), or (b) keep the setpoints and state that VS-1
coverage is judged with the chamber fluctuation as an unmodelled error, which then needs its own allowance in the
pass rule.

**Reason:** neither the interval nor the conditions are defined. With setpoints, the isoconversion chamber's
fluctuation dominates the fit error: at 80 C a 0.5 K deviation changes k by about 8% for Ea near 160 kJ/mol, the
study lasts about one OU time constant so the deviation does not average out, while the assay noise contributes about
1.5%. A diagnostic run (16 replicates, aspirin, isoconversion) gave 95% interval coverage of 11/16 (ln k*), 8/16 (Ea)
and 11/16 (B) with the design's fluctuation, and 16/16, 16/16 and 15/16 with the fluctuation set to zero. The ICH
design, months long, averages it out.

**Interim:** the fits receive the setpoints (option b without an allowance), so VS-1 on the isoconversion design is
expected to fail; the fixture's fluctuation is not changed.

## R24. Spec 15.8 VS-3 and VS-4: the validated-range premise

**Proposed change (spec 15.8):** in VS-3 replace "after the 45 C excursion (outside the validated range, 8.2) the
fraction is at least 0.86 and the estimate carries `outside_validated_range`" with "after the 45 C excursion the
fraction is at least 0.86; every estimate whose history leaves the measured model's validated range carries
`outside_validated_range`". In VS-4 replace "pooled coverage within [0.86, 0.94] for estimates inside the validated
range" with a set that is not empty under this design (for example all estimates, or estimates without the flag
reported and those with it held to the after-excursion rule). Also state VS-4's templates: one `tcs_failure_hot` at
day 180 and one SPE at day 250 (`mars_surface_sep_2017` on Mars, `aug1972_behind_20_g_cm2` elsewhere).

**Reason:** the measured model's validated range is the study range (spec 14.5, `model_document`): 298.15 to
353.15 K from the ICH long-term condition to the 80 C isoconversion condition. 45 C (318.15 K) is inside it, while
every profile's setpoint (295.15 or 296.15 K) is below it. So the excursion does not leave the range, and every
estimate of every profile is outside the range for the opposite reason; VS-4's pooled set is empty and its rule
cannot pass. The templates are global in environment-profiles.json, not per profile.

**Interim:** the tests implement the rules literally and report the flag counts before and after the excursion;
VS-4 uses the templates above.

## R25. Spec 7.4: tests must not write the committed BDE cache

**Proposed change (spec 7.4 and `pipeline.assess_inventory`):** let the cache directory be set for a run (an
environment variable such as `PHARMACY_XTB_CACHE_DIR`, or a member of the bundle), and write cache entries through
a temporary file and `os.replace` so a concurrent reader never sees a partial entry.

**Reason:** "A miss computes and writes the entry" into `data/pharmacy/xtb-cache`. Validation and VS products are
built in tests and are not in the committed cache, so any test that estimates them writes into B2's directory.
`build_stability_model` and `estimate_potency(model=...)` let a test redirect the cache; `assess_inventory` does
not. During one run, a reader using the previous `BdeResult` layout met an entry written in the new layout and
raised `XtbError`.

**Interim:** every B3 test that builds a model passes `cache_dir` to a per-process copy of the committed cache
(`tests/scenarios/bundles.py`, `stability_model`); validation and VS estimates pass that model to
`estimate_potency`. The demo scenario and end-to-end tests call `assess_inventory` on formulary lots only; B3 runs
them under a macOS sandbox profile that denies writes to `data/pharmacy/xtb-cache`, so a missing entry fails the
test instead of being written.

## R29. Spec 15.8 VS-2: selection between kinds at low conversion

**Proposed change (spec 14.4 or 15.8):** either restrict VS-2's 24-month prediction rule to studies whose
conversion range covers the predicted conversion, or state that misselection at isoconversion (conversion up to the
specification edge, about 10%) is expected and judge the prediction with the AICc-weighted average of the kinds
instead of the selected kind alone.

**Reason:** at conversions up to 10% F0, F1 and R3 (and D1 and D3) are nearly indistinguishable, and the 14.4 tie
rule (|dAICc| < 2 goes to fewer parameters, then kind order) selects F0 for F1 and R3 truths and D1 for D3 truths.
The 24-month prediction at 25 C then extrapolates to about 15% loss with the wrong curvature. A diagnostic with six
replicates per kind gave the confusion F1: F0 5, F1 1; A2: A2 6; R3: F0 6; D3: D1 6, and 5 of 17 misselections inside
the interval even with a fluctuation-free chamber (the rule needs at least 0.79 at m = 17).

**Interim:** the rule is implemented literally and fails; reported in docs/VALIDATION-REPORT.md.

## R31. Spec 15.5: covering a noisy measurement with an interval for the true potency

**Proposed change (spec 15.5, V1 and V6 pass rule):** define a row as covered when the measured value lies inside
the 90% interval of the predicted measurement, that is the engine's potency draws each plus an assay error
N(0, s_row^2) with s_row the row's reported sd, before the quantiles are taken. Keep the binomial rule on the count.

**Reason:** the engine's interval is for the true potency; the published value carries its own assay error (sd 0.2 to
3.0 points in V1 and V6). Comparing a noisy value with a true-potency interval lowers the expected coverage below 0.90
whenever the assay sd is comparable to the interval's half width, so the 0.90 binomial rule can fail a calibrated engine.
In the current V6 run all four misses lie above the upper bound by 0.03 to 1.04 of their own assay sd, while the V1
misses lie 5 to 25 sd away, so the definition matters for V6 and not for V1.

**Interim:** the rule is applied literally (measured value inside the engine's interval); V6 fails and is reported in
docs/VALIDATION-REPORT.md with the distances above.
