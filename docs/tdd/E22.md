# E22: Participation streak, patches and crew goal

Technical design for epic E22. Inputs: the brief (`tdd/E22.md` in the planning package), PRD.md (4.6, R31 to R33),
USE-CASES.md (UC01, UC13, UC24), CONTRACTS.md (sections 8, 9, 12, 18, 19, 20 "Modules", "Sessions and roles" and the
test vectors, 24), `api/openapi.yaml`, UX-DESIGN.md section 11, VALIDATION.md (V41 to V48, V67, V90; D03, D09, D14, D27,
D44), `backlog.json` (E22-01 to E22-03), `docs/BUILD-CHARTER.md`, `AGENTS.md`, `docs/tdd/E03.md` (shell, slots, the
daily check that calls this module) and the deployment research in
`crew-health-build-2026-11-14/research/`. `docs/SYSTEM.md` and `docs/DEPLOYMENT.md` do not exist
yet; dependent points are marked "per SYSTEM.md" or "per DEPLOYMENT.md" and listed in section 14.

Participation rewards showing up, never the numbers. Everything is derived from one immutable event, the
CheckCompletion, plus the mission clock, the roster and `participation-rules.json`. This module cannot read a value.

### 1.3 Decisions

| ID | Decision | Alternatives | Selected and why | Failure mode and rollback |
|---|---|---|---|---|
| DE22-1 | Views computed on read or materialized | Materialized views updated on write; a nightly batch | Computed on read by one pure function over completions, voids, day assignments, roster days, rules and `today`. Rule 9 says views are never the source of truth; computing on read makes rebuild, SIM reset and late arrival trivially correct. Sized for a 1,200 day Mars transit with a crew of four (research `surface-mobility-comms.md` 1.2) plus margin: 1,200 days x 6 people x 3 events = 21,600 rows, linear scans under budget (section 11). A bounded memo is added only if T-E22-100 misses its budget | If a budget is missed, add an LRU memo keyed by the max row ids, clock history version, roster version, rules version and `today`; no schema change |
| DE22-2 | Isolation of the derivation | Code review only | Three layers: the pure function's inputs are typed facts with no value field (CompletionBasis forbids extras); import-linter forbids `participation` from importing any other domain module and forbids every model, handoff, ground and catch-up module from importing `participation`; the read connection has a SQLite `set_authorizer` that denies any table outside `participation_*` | A forbidden read raises `ParticipationIsolationError` and the test suite fails |
| DE22-3 | Late sync and identity corrections | Edit the completion | Late arrival keeps `occurred_at` (rule 8): the day row recomputes on read. Identity correction appends a `participation_void` referencing the completion and records a new completion for the corrected person; nothing is edited (CONTRACTS 8 state rules) | Voids are append only; a wrong void is answered with a new completion, never a delete |
| DE22-4 | Mission day of an event | Store the day once | Store the day assignment under the clock version in force (audit), and recompute on rebuild or on a clock correction; every moved day is an AuditEvent (rule 2, V46) | A rebuild under the same clock history is a no op (T-E22-033) |
| DE22-5 | SIM reset between demo runs | Delete SIM rows | No participation state to reset. Completion tables are append only (triggers block DELETE). E21 resets by restoring the demo hub database from the frozen `demo-mara-fd19` snapshot; views follow because they are computed (Q-E22-2) | If E21 cannot restore, the demo shows the honest count from the events present |
| DE22-6 | Origin of a view | One mixed view | One view per (mission, origin). A person's view uses the person's record origin (E02 `RecordRouting.record_origin`); a station session uses `mission_mode`; `REPLAY` creates no events (CONTRACTS 8) and its crew goal is honestly empty | n/a |
| DE22-7 | A participation fault and the Today screen | Fail Today | Request X-E22-6 makes TodayView `streak` and `crew_goal` nullable so a participation fault never hides warnings; interim: the recorder and derivation raise only on infrastructure faults (disk, database), which fail every module equally | n/a |

## 3. Domain model

Pure code in `hub/src/crew_health/participation/domain/`. No I/O, no clock reads.

### 3.1 Types

```python
Basis = Literal["daily_check", "concern_reported", "episode_updated"]
ViewOrigin = Literal["LIVE", "SIM"]

@dataclass(frozen=True, slots=True, kw_only=True)
class CompletionBasis:                        # the only input a producer can pass; references only
    basis: Basis
    basis_ref: str                            # DailyCheck or Episode id
    patient_id: str
    mission_id: str
    origin_mode: Literal["LIVE", "REPLAY", "SIM"]
    occurred_at: datetime                     # aware, converted to UTC at construction
    original_offset: str                      # "+HH:MM" as received
    actor_person_id: str | None               # who performed the act; None for an engine (urgent event)
    cause_kind: Literal["answer", "urgent_event"] | None   # episode_updated only
    cause_ref: str | None                     # answer or urgent event id; episode_updated only
    required_answers_complete: bool | None    # daily_check only: the producer's check, a boolean, never answers
```

Construction validates: `basis` specific fields present or `None` as stated; `occurred_at` aware; ids match the
`common.schema.json` id pattern. There is no field for a value, presence, quality, outcome, symptom count or journal fact,
and the dataclass has no `**extra`; T-E22-004 asserts the field set equals this list.

```python
@dataclass(frozen=True, slots=True)
class CompletionFact:                         # what the derivation sees
    completion_id: str
    patient_id: str
    mission_day: int                          # current assignment
    seq: int

@dataclass(frozen=True, slots=True)
class Rules:                                  # parsed participation-rules.json
    patch_thresholds: tuple[int, ...]         # sorted ascending
    designs: Mapping[int, PatchDesign]        # threshold -> (patch_design_id, label)
    crew_goal_window_days: int
    derivation_version: str

@dataclass(frozen=True, slots=True)
class StreakCore:
    today_status: Literal["checked", "due"]
    current_streak_days: int
    longest_streak_days: int
    completed_days_total: int
    days: tuple[tuple[int, Literal["checked", "missed", "due"]], ...]

@dataclass(frozen=True, slots=True)
class CrewGoalCore:
    window_first: int
    window_last: int
    completed_total: int
    due_total: int
    reached: bool
```

### 3.2 Derivation (CONTRACTS 8 rules 1 to 9)

```python
def checked_days(facts: Sequence[CompletionFact], person_id: str) -> frozenset[int]: ...
def derive_streak(checked: frozenset[int], first_day: int, today: int) -> StreakCore: ...
def derive_patches(facts_in_order: Sequence[CompletionFact], rules: Rules) -> tuple[PatchCore, ...]: ...
def derive_crew_goal(pairs: frozenset[tuple[str, int]], roster: Mapping[int, frozenset[str]],
                     today: int, rules: Rules) -> CrewGoalCore: ...
def award_id(patient_id: str, mission_id: str, origin: ViewOrigin, threshold: int) -> str: ...
```

| Rule | Implementation |
|---|---|
| 1 Inputs | Accepted completions of one mission and origin, minus those referenced by a void; day assignments; roster; rules; `today`. No other parameter exists |
| 2 Mission day | `MissionClock.day_at(occurred_at)` at record time under the version in force; recomputed in rebuild and on `MissionClockCorrected`; each change writes `participation.day_moved` |
| 3 Checked day | `checked = {f.mission_day for f in facts if f.patient_id == person}`; several events count once |
| 4 Current streak | Walk back from `today` if `today in checked`, else from `today - 1`; count consecutive days in `checked`; 0 when neither `today` nor `today - 1` is checked. Loop bounded by `today - first_day + 1` |
| 5 Longest | One forward pass over `range(first_day, today + 1)`; bounded |
| 6 Missed | Days in `[first_day, today - 1]` not in `checked`; `today` is `due` or `checked`, never `missed` |
| 7 Patches | Order distinct checked days by the completion that first checked each day (ascending `seq`, then day); the k-th distinct day (k in `patch_thresholds`) is reached by that day's first completion: `reached_by_completion_id`, `reached_on_mission_day`. `completed_days_total = len(checked ∩ [first_day, today])` |
| 8 Late arrival | A synced event keeps `occurred_at`; its day is computed from it, so a past `missed` day becomes `checked`; it never counts for the day it synced |
| 9 Determinism | Same inputs give byte identical canonical JSON apart from `as_of`; `result_sha256` in rebuild is the SHA-256 of the sorted canonical serialization of every view with `as_of` removed |

`first_day` is `ParticipationRoster.first_mission_day(person_id)` (the person's first day on this mission's roster);
for a person not on the roster (a guest LIVE profile, UX 11) it is the mission day of the person's first accepted
completion, so a guest starts at 1 with no missed days before they began (Q-E22-4).

`derive_crew_goal`: window `[today - window_days + 1, today]`, clipped below at the mission's day 1; `due_total =
sum(len(roster[d]) for d in window)`; `completed_total = |{(p, d) in pairs : d in window and p in roster[d]}|`, so a
person off the roster (a guest) never moves the crew goal and `completed_total <= due_total` always holds; `reached =
completed_total >= due_total` exactly as CONTRACTS 8 defines it (see X-E22-7 for `due_total = 0`).

Award ids are `pat_` followed by the first 24 hex characters of SHA-256 over `patient_id|mission_id|origin|threshold`
(deterministic, within the id pattern for any id length). The examples (`pat_mara_7`) are illustrative.

### 3.3 Recording rules

| Case | Outcome |
|---|---|
| `origin_mode` REPLAY | Nothing written; `CompletionOutcome(status=None, created=False)` (CONTRACTS 8) |
| `origin_mode` differs from `RecordRouting.record_origin(patient_id)` | Written `rejected`, `ORIGIN_MISMATCH` |
| `actor_person_id != patient_id`, except `episode_updated` with `cause_kind == "urgent_event"` | Written `rejected`, `IDENTITY_MISMATCH` |
| `basis == "daily_check"` and `required_answers_complete is not True` | Written `rejected`, `REQUIRED_ANSWER_MISSING` (defensive; E03 refuses such a submit first) |
| Same idempotency key seen | Returns the stored completion; nothing written; no event |
| Otherwise | Written `accepted`; day assigned; events published |

Idempotency key: `cc:{basis}:{basis_ref}:{patient_id}` for `daily_check` and `concern_reported` (one per basis), and
`cc:episode_updated:{basis_ref}:{patient_id}:{cause_ref}` (one per update). Rejected completions are persisted and never
raised, so a producer's transaction never fails because participation refused it.

### 3.4 State machines

| Object | States | Transitions |
|---|---|---|
| CheckCompletion | `accepted`, `rejected` (terminal at creation); voided is a separate fact | `accepted` + void event → excluded from derivation. Nothing else |
| Day status (derived) | `due`, `checked`, `missed` | `due → checked` on an event that day; `due → missed` at the boundary with none; `missed → checked` by late arrival or a clock correction rebuild |
| PatchAward (derived) | `earned` | removed only when a void drops `completed_days_total` below its threshold; removal is audited |
| CrewGoalView | `reached` flag | moves with the window at the boundary; never presented as a loss |

## 4. Application layer

`hub/src/crew_health/participation/application/`.

### 4.1 Use cases

| Use case | Input | Output | Errors | Idempotency |
|---|---|---|---|---|
| `RecordCompletion` (port, in the producer's unit of work) | `uow`, `CompletionBasis` | `CompletionOutcome(created, completion_id, status, status_reason)` | `ParticipationStorageError` only (infrastructure) | key in 3.3, unique index |
| `ReassignCompletions` | `uow`, `basis_ref`, from, to, `correction_ref` | voids written, new outcomes | `NotFound` when no accepted completion has the basis | key `void:{completion_id}:{correction_ref}` |
| `ImportSyncedCompletion` (per DEPLOYMENT.md) | `uow`, CheckCompletion | outcome | as `record` | `completion_id` and `idempotency_key` unique |
| `GetMyStreak` | session | StreakView | `UNAUTHORIZED_SCOPE` (no person, e.g. station), `MALFORMED_REQUEST` | read |
| `GetMyPatches` | session, cursor, limit | page of PatchAward | `UNAUTHORIZED_SCOPE` | read |
| `GetCrewGoal` | session, raw query params | CrewGoalView | `AGGREGATE_ONLY` (any query parameter), `UNAUTHORIZED_SCOPE` | read |
| `RebuildParticipation` | operator session, `{origin_mode}`, key | RebuildResult | `UNAUTHORIZED_SCOPE`, `DUPLICATE_COMMAND` | E01 store |
| `OnDayBoundary` | scheduler, `d` | events | none | key `participation:day:{d}` |
| `OnClockCorrected` | `uow`, event | moved days audited, events | none | by clock version |

Steps of `RecordCompletion`: validate the basis; decide per 3.3; insert into `participation_completion`; compute
`mission_day` with `MissionClock.day_at(occurred_at)` and insert the day assignment; compute the person's StreakView
and the CrewGoalView for that origin on the same connection; `Outbox.append("participation.streak_changed", "person",
patient_id, streak_view)` and `Outbox.append("participation.crew_goal_changed", "crew", None, crew_goal_view)`; return.
A `rejected` outcome writes the row and publishes nothing.

Steps of `RebuildParticipation(origin)`: load completions and voids of the origin; recompute every day assignment under
the current clock history; for each change update `participation_day_assignment` and append `participation.day_moved`;
recompute every person's view and the crew goal; compare awards before and after and append
`participation.award_removed` for any removed; return counts (`events_read`, `events_voided`, `views_rebuilt` = number
of StreakViews recomputed, `changed_day_assignments`, `result_sha256`, `finished_at`). It never returns a per person
view. Publishes `streak_changed` for each person whose view changed and one `crew_goal_changed`.

### 4.3 Events

Published to the outbox (CONTRACTS 18): `participation.streak_changed` (StreakView, scope person, only for its own
person: E01 delivers person scope events only to that person's sessions) and `participation.crew_goal_changed`
(CrewGoalView, scope crew; the client ignores a view whose `origin_mode` differs from the one it displays). Both are
emitted on accepted `record`, on `reassign`, on rebuild changes, on clock corrections and at each day boundary
(`today` flips to `due`; yesterday may become `missed`; the window moves).

Consumed: `MissionClockCorrected` (E01, in transaction), `config.release_activated` (no stored state; new
`derivation_version` and thresholds apply on the next read and the next rebuild audits award changes).

| `participation_completion` | `seq INTEGER PRIMARY KEY`, `completion_id TEXT NOT NULL UNIQUE`, `patient_id TEXT NOT NULL`, `mission_id TEXT NOT NULL`, `origin_mode TEXT NOT NULL CHECK (origin_mode IN ('LIVE','SIM'))`, `basis TEXT NOT NULL CHECK (basis IN ('daily_check','concern_reported','episode_updated'))`, `basis_ref TEXT NOT NULL`, `occurred_at TEXT NOT NULL`, `original_offset TEXT NOT NULL`, `mission_clock_version TEXT NOT NULL`, `mission_day INTEGER NOT NULL`, `completion_rule_version TEXT NOT NULL`, `status TEXT NOT NULL CHECK (status IN ('accepted','rejected'))`, `status_reason TEXT CHECK (status_reason IN ('ORIGIN_MISMATCH','IDENTITY_MISMATCH','REQUIRED_ANSWER_MISSING'))`, `idempotency_key TEXT NOT NULL UNIQUE`, `created_at TEXT NOT NULL`, `source_hub TEXT` | `CHECK ((status = 'accepted') = (status_reason IS NULL))`; triggers `BEFORE UPDATE` and `BEFORE DELETE` raise `ABORT`; index `(mission_id, origin_mode, status)`, `(patient_id, mission_id, origin_mode)`, `(basis_ref)` |
| `participation_void` | `seq INTEGER PRIMARY KEY`, `completion_id TEXT NOT NULL REFERENCES participation_completion(completion_id)`, `correction_ref TEXT NOT NULL`, `voided_at TEXT NOT NULL` | `UNIQUE (completion_id)`; append only triggers |
| `participation_day_assignment` | `completion_id TEXT PRIMARY KEY REFERENCES participation_completion(completion_id)`, `mission_day INTEGER NOT NULL`, `clock_version TEXT NOT NULL`, `assigned_at TEXT NOT NULL` | derived; updated only by rebuild and clock correction; index `(mission_day)` |

`participation_completion.mission_day` and `mission_clock_version` are the values at record time (the audit copy the
schema requires); reads use `participation_day_assignment`. `source_hub` is `NULL` for local records and the origin hub
id for `import_synced` (per DEPLOYMENT.md). No column can hold a value, answer, quality or text.

Read fence: `participation/adapters/fenced_reader.py` opens its read connection through E01 and installs
`sqlite3.Connection.set_authorizer`, returning `SQLITE_DENY` for `SQLITE_READ` on any table not starting with
`participation_` (and not a `sqlite_` internal). Writes run on the producer's unit of work connection; T-E22-041
records every statement the recorder issues and asserts each names only `participation_*` tables.

No external calls, no network, no model. Bounds: queries filter by mission, origin and day ranges; the rebuild processes
rows in batches of `settings.participation.rebuild_batch` per statement (runtime setting per SYSTEM.md).

## 9. Deployment and fallbacks

Participation is not a safety function. It depends on no optional part: it never calls the model, devices, cameras,
habitat feeds or the ground link, so all of them can be absent with no change (T-E22-070). The reverse matters more:
participation must never block or decorate a safety path (sections 7 and 10).

| Tier (provisional, per DEPLOYMENT.md) | Behavior |
|---|---|
| T1 One laptop and its webcam | Everything in this TDD. Station mode on the shared laptop shows only the crew goal; each person sees their own streak after signing in (E03 DE03-11) |
| T2 Habitat network with tablets and a station screen | Each tablet session sees its own person's streak; the station screen sees only the crew goal of `mission_mode`; person scope events go only to that person's sessions |
| T3 Several hubs (pressurized rover, transit replica) | Each hub derives from the completions it holds. Completions recorded on another hub arrive through `import_synced` keeping `occurred_at`, so a day can move from missed to checked (rule 8); the crew goal on a disconnected rover counts only what it holds and is labeled stale by E03 when its data is old. Sync transport, hub ids and conflict rules per DEPLOYMENT.md (Q-E22-3) |
| Ground | Nothing. The ground console, ground log and handoffs never contain participation (INV-E22-12) |

| Missing part | Effect on participation | Test |
|---|---|---|
| Language model | none | T-E22-070 |
| Devices, camera, band | none (a check completes without them, E03) | T-E22-070 |
| Ground link | none | T-E22-070 |
| Scheduler timer missed (process down at the boundary) | views still correct on read; the boundary push happens at restart | T-E22-071 |
