# E22: Participation streak, patches and crew goal

Technical design for epic E22. Inputs: the brief (`tdd/E22.md` in the planning package), PRD.md 4.6 (R31 to R33),
USE-CASES.md (UC01, UC13, UC24), CONTRACTS.md (sections 5, 8, 9, 18, 19, 20, 24), `api/openapi.yaml`, UX-DESIGN.md
section 11, VALIDATION.md (V41 to V48, V67, V90; D03, D09, D14, D27, D44), `backlog.json` (E22-01 to E22-03),
`docs/BUILD-CHARTER.md`, `AGENTS.md` and the neighbouring designs E03 (shell, station mode, submit), E15 (concern
producer), E21 (demo reset) and E31 (practice patches). `docs/SYSTEM.md` and `docs/DEPLOYMENT.md` do not exist yet;
dependent points say "per SYSTEM.md" or "per DEPLOYMENT.md" and are listed in section 14. CONTRACTS 8 is implemented as
written; this document records only what it leaves open.

Participation rewards showing up, never the numbers, and it is not a safety function. The design has one shape:
producers drop a reference-only **intent** into their own transaction and never wait for participation or fail because
of it; a **projector** turns intents into immutable CheckCompletions in its own transactions; StreakView and PatchAward
are derived on read from completions, voids, activated day assignments, the roster, `participation-rules.json` and an
append-only award ledger; the **crew goal** is published once per mission day under the owner's consent and
disclosure rule. This module cannot read a value.

## 3. Domain model

Pure code in `hub/src/crew_health/participation/domain/`. No I/O, no clock reads.

### 3.1 Types

```python
Basis = Literal["daily_check", "concern_reported", "episode_updated"]
ViewOrigin = Literal["LIVE", "SIM"]

@dataclass(frozen=True, slots=True, kw_only=True)
class CompletionBasis:                        # the only input a producer can pass; references only
    basis: Basis
    basis_ref: str                            # DailyCheck or Episode id (common id pattern)
    patient_id: str
    mission_id: str
    origin_mode: Literal["LIVE", "REPLAY", "SIM"]
    occurred_at: datetime                     # hub time at which the producer accepted the basis, aware, UTC
    original_offset: str | None               # "+HH:MM" as received; None when unknown (common offset)
    actor_person_id: str | None               # who acted; None only for an urgent signal
    cause_kind: Literal["answer", "urgent_event"] | None   # episode_updated only
    cause_ref: str | None                     # answer id or urgent signal reference; episode_updated only
    required_answers_complete: bool | None    # daily_check only: a boolean, never the answers

@dataclass(frozen=True, slots=True)
class CompletionFact:                         # what the derivation sees
    completion_id: str
    patient_id: str
    mission_day: int                          # activated assignment
    occurred_at: datetime
```

Construction validates the basis specific fields, an aware `occurred_at` and the id pattern. There is no field for a
value, presence, quality, outcome, symptom count or journal fact and no `**extra` (T-E22-004). `original_offset` is
never synthesized from `occurred_at` (T-E22-039).

Logical identity (DE22-3): `["daily_check" | "concern_reported", basis_ref, patient_id]`,
`["episode_updated", basis_ref, patient_id, cause_kind, cause_ref]`, a replacement `["replacement", lineage_id,
generation]`, a correction `["correction", lineage_id, correction_ref]`, a reconcile `["reconcile", cause, cause_ref]`.
Separator characters inside ids therefore cannot collide (T-E22-018). The payload hash is SHA-256 over the RFC 8785
form of every basis field.

### 3.2 Derivation decisions

| Point | Rule |
|---|---|
| `today` | `MissionClock.day_at(now).day` |
| `first_day` | `ParticipationRoster.first_mission_day(person)`; a person off the roster (guest LIVE profile, UX 11): the day of their first accepted completion; none yet: `today` (first read shows today due, zeros) |
| Eligible days | `E = [first_day, today]`. The same filter feeds the streak, `completed_days_total`, `days[]` and patches. A completion outside `E` (a future roster start, or a backward clock correction that puts it after today) is ignored until `E` contains it. `first_day > today` gives `days = []`, `today = "due"`, zeros |
| Mission days zero or negative | Ordinary days (common `mission_day` permits preflight); nothing clips them |
| Planned length unknown or exceeded | No effect on derivation; the UI pages the day row (7) |
| Size | `len(E)` at most `MAX_VIEW_DAYS = 4096` (asserted bound; the longest mission sized in the research is 1,200 days). Beyond it the view is unavailable with audit `participation.view_bound_exceeded`, never truncated |
| Patch reached | Threshold k is reached on the k-th eligible checked day in ascending day order; `reached_by_completion_id` is that day's completion with the least `(occurred_at, completion_id)` |
| `event_cursor` | First 32 hex of SHA-256 over the sorted `(completion_id, voided)` pairs of this person and origin plus the clock history version: person scoped and identical across databases |
| Determinism | Views serialize as canonical JSON without `as_of`; `result_sha256` hashes, sorted: every StreakView, every active award, the current crew goal publication without `published_at`. Practice awards (E31) are not included |

Award ids: `pat_` and the first 24 hex of SHA-256 over the JSON array `[patient_id, mission_id, origin, threshold]`.

### 3.3 Crew goal: consent, publication and the disclosure guard

Consent (owner interim decision, X-E22-13):

1. Counting toward the crew goal is per member and per origin, off until the member turns it on from their own session.
   Nobody else can turn it on or off, read it, or learn it from any view, event, roster or log; the audit event carries
   ids only and is never crew visible.
2. A grant counts from the next mission day (no partial day); a withdrawal removes the member from the next
   publication entirely. Neither changes the member's private streak or patches.
3. Before the toggle, the member sees `crew_consent_body` (ui-copy), which states what counting reveals (residuals
   below). SIM personas consent through the same command in the fixture; no seeding path bypasses it.

Publication at the start of mission day `t` (scheduler, plus reconcile after a rebuild, a clock correction or a release
activation), one per origin:

- Window `[t - W, t - 1]`, `W = crew_goal_window_days`: completed days only (X-E22-12 c). Member `i` counts on day `d`
  when on the roster that day and `d` is after the grant day; `m_i` = such days; `M = sum(m_i)`; `completed` = counted
  `(i, d)` pairs with an eligible completion.
- Bands: with configured `k` (X-E22-12 b), band `j` of a k band partition is `[floor(j(M+1)/k), floor((j+1)(M+1)/k) - 1]`.
- **Guard (code, never configuration).** A partition is admissible when, for every viewer `v` (each counting member with
  its `m_v`, and an outsider with `m_v = 0`), every band `[a, b]` and every own count `c` in `[0, m_v]` that is
  consistent with the band, the set of others' totals `[max(0, a - c), min(M - m_v, b - c)]` holds at least two values.
  The publication uses the largest admissible `k' <= k` with `k' >= 2`; if none exists, `disclosure =
  "too_few_counting"` with no band. The choice depends only on who counts and on how many days, never on `completed`,
  so withholding a band reveals nothing about anyone's checks.
- Published: `disclosure`, `band_index`, `band_count`, the window days. Never: `M`, `completed`, the number of counting
  members, who counts, or a per day value. `crew_goal_changed` goes out only when the publication differs from the
  previous one; nothing is published when a check is recorded.

Worked case: four counting members, `W = 7`, `k = 4`: the band `[0, 6]` would let a member with 6 own checks conclude
the other three had none, so `k' = 3` (`[0, 8]`, `[9, 18]`, `[19, 28]`); the demo's 24 is band 3 of 3. Three counting:
`k' = 2`. Two counting: `too_few_counting`.

Residuals, stated in `crew_consent_body` and in Q-E22-6: consecutive publications differ by one day of the crew's
checks; whether a goal is shown depends on how many members count; "reached" is never singled out, because a total
equal to `M` would tell every viewer that every counting member checked every day. The guarantee is exactly the guard,
not anonymity.

Interim until X-E22-12 and X-E22-13: there is no consent command, so no member counts, `M = 0`, and the served
CrewGoalView is `completed_total 0`, `due_total 0` (true for zero counting members); `reached` is computed as CONTRACTS
8 writes it and never shown (X-E22-7).

### 3.4 Projection rules (per intent, in the projector's transaction)

| Case | Outcome |
|---|---|
| `origin_mode` REPLAY | Nothing written but the projection bookkeeping (CONTRACTS 8) |
| Origin differs from `RecordRouting.record_origin(patient_id)` | Completion `rejected`, `ORIGIN_MISMATCH` |
| `actor_person_id != patient_id`, except `episode_updated` with `cause_kind == "urgent_event"` | `rejected`, `IDENTITY_MISMATCH` |
| `daily_check` and `required_answers_complete is not True` | `rejected`, `REQUIRED_ANSWER_MISSING` |
| Otherwise | `accepted`; day assigned under the clock version in force at `occurred_at`; `completion_rule_version` = the version of `participation-rules` in the active release; ledger updated (DE22-8); `streak_changed` to the person when the view changed |

Producer obligations (E03, E15; tested through their real commands, T-E22-120): call `record` only inside the
transaction that accepted the basis (a rolled back or refused command leaves no intent); `occurred_at` is that
command's hub time; the actor is the session person, or `None` for an urgent signal; E15 calls `episode_updated` only
for an open episode of the patient. E22 cannot re-verify these from other modules' tables (DE22-2); the in-process,
same transaction call is the trust boundary.

### 3.5 Identity corrections

`reassign(uow, completion_id, to_patient_id, correction_ref, expected_generation)` enqueues a correction intent.
Every completion carries `lineage_id` (the first completion of its basis) and `generation` (0 for the original). The
projector applies a correction only when the lineage's active generation equals `expected_generation`: it voids the
active completion, then projects a replacement for `to_patient_id` with `generation + 1`, `replaces_completion_id`,
and the voided row's `occurred_at`, `original_offset`, `basis`, `basis_ref` and cause fields. A stale generation is a
`correction_conflict` (audited; outcome readable through `CorrectionQueries`); the same `correction_ref` again is a
duplicate returning the first outcome. A to B to A gives three rows with distinct keys (generations 0, 1, 2). A
replacement rejected by 3.4 (for example `ORIGIN_MISMATCH`) leaves the void in force. Authorization belongs to the
calling workflow; E22 enforces only the chain.

| Day status (derived) | `due`, `checked`, `missed` | as CONTRACTS 8 |

| Crew goal publication | `shown`, `too_few_counting` | recomputed at each publication |

`hub/src/crew_health/participation/application/`.

### 4.1 Use cases

| Use case | Input | Output | Errors | Idempotency |

`ProjectIntent`, one intent per transaction: open the projector's unit of work; read the intent; apply 3.4 or 3.5
with every read on that transaction's connection (`tx` parameter, 4.2); insert completion, day assignment and ledger
rows; append audits; recompute the person's view and append `streak_changed` only when it changed; write the
projection row; commit. An exception rolls back, increments `attempts` in a separate bookkeeping write and retries with
backoff; after 5 attempts the intent is `parked` with its error code and `participation.intent_parked`. Ordering of
intents never changes a result (DE22-7), so the projector continues with the next one.

Reads (`StreakQueries`, `PatchQueries`) use a separate fenced read connection that sees committed state only. A read for
a person with a pending intent older than the settle deadline or any parked intent raises `ParticipationUnavailable`
instead of returning a view that omits it.

`Reconcile(origin)`: (1) pin, in one read transaction: max completion and void ids, clock history version, roster
version, active release id, `now`; compute every day assignment under the current clock history, the award ledger diff
(earned for newly reached thresholds; removed only for void caused drops) and the crew goal publication; (2) activate
in one `BEGIN IMMEDIATE` transaction: re-read the pins; if any changed, go back to (1) (3 attempts, then
`RebuildContended`); otherwise write the assignment diffs with one `participation.day_moved` each, the ledger diffs
with their audits, the publication, the outbox events and the rebuild record with `result_sha256`; commit. A crash or
`SQLITE_FULL` before commit leaves everything as before; rerunning is safe. `RebuildParticipation` is `Reconcile` with
cause `operator` plus re-projection of parked intents, and returns counts only (`views_rebuilt` = StreakViews,
X-E22-8).

### 4.3 Events

Published: `participation.streak_changed` (StreakView, scope person, only to that person's sessions, CONTRACTS 18) on a
changed view after a projection, a reconcile or the day boundary; `participation.crew_goal_changed` (CrewGoalView,
scope crew) only when a publication differs from the previous one. Recording a check never emits a crew event.
Consumed: `MissionClockCorrected` and `config.release_activated`, each only enqueueing a reconcile intent. A release
rejected by the loader never activates, so the last good `participation-rules` stays in force.

### 5.2 Intake

`record` runs `SAVEPOINT participation_intake`, one `INSERT ... ON CONFLICT (intent_key) DO NOTHING`, and on conflict
one read of the stored payload hash (equal: `duplicate`; different: insert into `participation_intent_conflict`,
`conflict`); then `RELEASE`. Any exception: `ROLLBACK TO` the savepoint, return `deferred`, log the ids. A fault that
fails every write (a full disk) fails the producer's own writes equally; nothing in E22 adds a failure the producer
would not already have.

### 5.3 Projector

One worker task per hub (E01 worker with health check and restart). It fetches at most 256 pending intents per read,
projects one per transaction, and releases the write lock between transactions, so a help write waits at most one
projection (budget in 11). Retries: 5 with backoff 50 ms to 2 s; then `parked`. `Settle` waits on the worker's progress
signal up to the deadline (hub setting `participation.settle_timeout`, per SYSTEM.md); it never projects on the request
thread.

### 5.4 Read fence

`participation/adapters/fence.py` provides `with fenced(conn):`, which installs `Connection.set_authorizer` returning
`SQLITE_DENY` for `SQLITE_READ` or a write on any table not starting with `participation_` (and not `sqlite_`), and
removes it on exit. Every E22 repository statement runs inside it; E01 `AuditLog` and `Outbox` calls run outside it on
the same transaction. The read connection keeps the fence permanently. T-E22-041 records every statement E22 issues.

### 5.5 Bounds

| Bound | Value |
|---|---|
| Intents fetched per read; projected per transaction | 256; 1 |
| Retries per intent | 5, then parked |
| SQLite busy timeout: projection; reconcile activation | 250 ms; 1 s |
| Reconcile attempts | 3, then `RebuildContended` |
| Days per view | 4,096 (3.2) |
| Members in the guard | 32 (asserted against the roster) |
| `crew_goal_window_days`, thresholds, progress bands | loader checks: at most 31, 16, 8 |
| Per view work | `facts` reads `DISTINCT (patient_id, mission_day)` per origin and range, so any number of episode answers costs persons times days, never more |
| Memo (only if T-E22-100 misses its budget) | LRU of 64 views keyed by the pins and `today` |

Overload never drops an accepted intent: a backlog grows on disk, the health check reports `degraded` above 1,000
pending, and reads report unavailable per 4.1.
