VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.2 and 8: the classifier is incomplete, and its configuration test disables a safety invariant.** The table has no outcome for `unknown` or `declined` with a missing choice, or a consistent `present` choice whose `opens` is null. T-E11-070 explicitly expects removing `opens` from `red_faint` to stop help opening. That contradicts INV-E11-05 and the package: “Any yes opens ‘Someone needs help’.” Evidence: [E11:98](docs/tdd/E11.md:98), [E11:529](docs/tdd/E11.md:529), [PRD:198](docs/product/PRD.md:198). **Required:** specify an exhaustive, ordered classifier; reject configurations that remove required red-flag protection; handle missing or ambiguous mappings through an explicit human-review path. Replace T-E11-070 with a safe configuration-change case and test every missing-choice combination. R1-12 and audit finding 17 remain unresolved.

2. **[blocker] Sections 2, 3.2, 4.2 and 14: offline answers can be interpreted under the wrong configuration.** Falling back to the active questionnaire can change an answer’s clinical meaning. The corresponding help-presentation version is not pinned, and the effect does not specify which release E26 must use. Moreover, E04 currently stores the active questionnaire version and rejects removed questions, contradicting E11’s historical-version promise. Evidence: [E11:99](docs/tdd/E11.md:99), [E04:269](docs/tdd/E04.md:269). The package requires “Question code/version” and immutable release contents ([CONTRACTS:25](docs/product/CONTRACTS.md:25), [CONTRACTS:129](docs/product/CONTRACTS.md:129)). **Required:** agree the submitted-answer version contract with E04/E01, retain the complete applicable configuration pins through effect delivery, and define safe handling when that release is unavailable. Test upload after question removal and flow remapping.

3. **[blocker] Sections 3.4 and 4.2: subject-level help deduplication does not establish episode linkage or correct flow selection.** E26 can return an existing session opened from a button or another episode. Its original `entry.ref_id` remains unchanged, so E11’s event handler cannot necessarily link it to the new episode. Conversely, E11 skips opening whenever the cycle has any previous red-flag session, even a closed one, suppressing help for a genuinely new positive answer. Evidence: [E11:157](docs/tdd/E11.md:157), [E26:131](docs/tdd/E26.md:131). The package requires red-flag entry to open “straight on the flow” ([CONTRACTS:891](docs/product/CONTRACTS.md:891)). **Required:** specify an atomic association result from E26, persist the returned session link explicitly, and define handling of a different required flow. Distinguish replayed answers from new symptoms. Add existing-button-session, different-episode, different-flow and closed-session tests. R1-1, R1-2 and R1-6 are only partially resolved.

4. **[blocker] Sections 3.4 and 4.1 to 4.2: delayed derived events can reopen an already dispositioned incident.** A red flag can commit, an officer can disposition that cycle, and its pending help-opening effect can then deliver. `HelpOpened` is a raising signal, so the transition table opens another cycle for the same already-reviewed cause. The disposition concurrency test covers new signals, not delayed consequences of an old signal. Evidence: [E11:150](docs/tdd/E11.md:150), [E11:287](docs/tdd/E11.md:287). The package requires causation identifiers on audit events ([CONTRACTS:40](docs/product/CONTRACTS.md:40)). **Required:** carry originating cycle and signal identity through effects and help associations; define reconciliation after disposition without fabricating a new occurrence. Test disposition before effect execution, before event consumption, and before retry, while proving that a genuinely new symptom still raises urgency.

5. **[blocker] Sections 4.2 and 12: T-E11-026 deliberately accepts duplicate clinical records after an outage.** Its expected result is “a second answer and signal.” After disposition, that duplicate can also reopen urgency. This faithfully exposes an unsafe package assumption: “Keys are kept 24 hours” ([CONTRACTS:210](docs/product/CONTRACTS.md:210)). Audit finding 9 explicitly requires durable logical identities independent of this cache. The newly available deployment document now requires a durable command ledger ([DEPLOYMENT:526](docs/DEPLOYMENT.md:526)). **Required:** use durable logical command and effect identities, preserving the original outcome after cache expiry. Change [T-E11-026](docs/tdd/E11.md:631) to require one logical answer and signal across multiweek outages, completed help sessions, disposition and restart.

6. **[blocker] Sections 3.3 and 14: acting authority is reconstructed differently from E31 and can survive its revocation.** E11 accepts an unreplaced accepted assignment without checking retirement, session closure or an ended acting-authority interval. It also permits plan-run assignments. E31 now provides `ActingMedicalOfficerPort.acting_for`, ends authority when specified conditions change, and explicitly states that plan runs have no acting officer. Evidence: [E11:125](docs/tdd/E11.md:125), [E31:252](docs/tdd/E31.md:252), [E31:429](docs/tdd/E31.md:429). **Required:** consume E31’s authoritative, current authorization through an agreed transaction-safe port. Test retired assignments, closed sessions, an officer returning, and an incapacitated officer who is neither this patient nor on EVA or asleep. Address audit finding 7 by recording the scope of clinical authorization separately from task assignment and practice recency.

7. **[blocker] Sections 6, 7 and 14: the disposition UI cannot obtain its required concurrency fields.** R-E11-1 requires `cycle` and `cycle_revision`, but R-E11-2 remains optional and proposes obtaining them from a stale-version error. The package says `current_state` is “the current object as GET would return it”; the existing Episode has neither field ([error.schema.json:89](docs/product/api/schemas/error.schema.json:89)). Section 7 also promises signal details that neither the existing Episode nor R-E11-2 exposes. **Required:** make the command, readable urgency detail, authorized signal-history projection and E15 UI a single integration prerequisite. Specify complete schemas and an initial successful read-to-disposition flow. File the requests: [section 14](docs/tdd/E11.md:698) says they are still to be filed, and `docs/requests/E11.md` is absent.

8. **[major] Sections 2, 4.3 and 5.2: supplying ports still disagree with E11.** E10 does not provide `get_passage(passage_id)`; it explicitly requests `read_approved(release_id, passage_id, None)`, whose result distinguishes history, missing membership and unavailable releases. E27 provides `KitGatePort.check(uow, *, capability_code, environment_id, condition_ids) -> GateOutcome`, not E11’s two-argument `KitGate.check`. Evidence: [E11:63](docs/tdd/E11.md:63), [E10:1302](docs/tdd/E10.md:1302), [E27:305](docs/tdd/E27.md:305). **Required:** adopt the supplying signatures and result unions, define handling of every result, and use shared contract fixtures. Complete the unspecified DTOs, including `GateResult`, `PathwayEvaluation`, `EpisodeFacts` and `AuthorityFacts`. R1-8 is not fully resolved.

9. **[blocker] Sections 3.6 and 10: pathway approval does not establish applicability to the patient’s setting.** `evaluate` receives no clinical or environmental applicability facts. A reviewed card, reviewed kit row and one approved `patient_instruction` passage suffice to approve the entire card. The tool contract instead says “Read approved applicable pathway” and requires “Mission and clinical applicability” context ([tool-catalog:147](docs/product/tool-catalog.json:147)). Audit finding 4 requires a shared eligibility rule, not separate review badges. **Required:** apply an explicit shared eligibility decision covering exact content version, purpose and relevant clinical/environmental context; distinguish supporting background evidence from authorization for actionable instructions. Define unknown applicability and release-unavailable outcomes. Test an Earth-only instruction in microgravity and mixed eligible/ineligible supporting material. Evidence: [E11:188](docs/tdd/E11.md:188).

10. **[blocker] Section 3.6: instrument-free examinations can bypass the required operator check.** The design uses “its condition’s capability, if any,” but the condition schema has no such mapping. The package explicitly says an empty instrument list can mean “an examination by a trained person”; its anxiety example is a clinical interview and physical examination. Evidence: [E11:199](docs/tdd/E11.md:199), [CONTRACTS:1162](docs/product/CONTRACTS.md:1162), [kit-map example:495](docs/product/api/examples/kit-map.example.json:495). **Required:** request explicit per-test capability, operator and skill requirements; missing requirements must not imply permission. Also replace “every capability those instruments provide” with the capabilities actually required by that test, so unrelated or partially unavailable outputs do not determine executability. Add trained-examination and partial-capability tests.

11. **[major] Sections 3.7 and 4.3: the manual alternative cannot pass the same gate.** For `adapter_down`, the gate refuses the capability and suggests that same capability by `manual_instrument`. Its signature has no method or provider selection, so revalidation returns the same refusal. Furthermore, `methods` can include methods supplied by instruments that are not the available provider. Evidence: [E11:225](docs/tdd/E11.md:225), [E11:336](docs/tdd/E11.md:336). The charter requires manual entry as the device fallback ([BUILD-CHARTER:100](docs/BUILD-CHARTER.md:100)). **Required:** agree method/provider-specific availability with E05/E27 and carry the chosen acquisition path through acceptance and acquisition. Test successful manual acquisition after adapter failure, not merely an alternative label, and reject alternatives whose physical instrument is absent.

12. **[blocker] Sections 3.7, 14 and 15: missing clinical applicability currently means permission.** R-E11-8 correctly identifies the missing contract, but its interim behavior passes everything not explicitly excluded. That allows the exact standing test R07 prohibits while V17 is merely reported failing. Evidence: [E11:737](docs/tdd/E11.md:737). The binding requirement is “A standing orthostatic test is not requested in microgravity” ([PRD:483](docs/product/PRD.md:483)). **Required:** make approved applicability configuration and its mapping an explicit prerequisite for enabling affected requests. Define unknown applicability as unavailable or requiring review, with a visible gap. Include this prerequisite in step 0 and the release gate. R1-9’s request is appropriate, but the operational defect remains.

13. **[blocker] Sections 2 and 3.8: the provenance checks require facts the consumed contract does not contain.** `OnHelpSessionChanged` receives a `HelpSession`, which contains neither mission ID nor origin mode at opening. The Event envelope does not supply those facts either. E11 nevertheless requires both, and no request defines their source. The warning row also omits the explicit mission/origin checks promised by INV-E11-09. Evidence: [E11:248](docs/tdd/E11.md:248), [HelpSession schema](docs/product/api/schemas/help-session.schema.json:7), [Event schema](docs/product/api/schemas/event.schema.json:61). **Required:** define an authoritative historical-facts port or requested internal event payload. Never reconstruct opening provenance from current mission mode. Test delayed consumption after a mode or mission change and same-person references across missions. R1-5 remains partial.

14. **[blocker] Sections 3.5 and 4.3: the stale-output guard is neither identifiable nor atomic.** `UrgencyToken(cycle, cycle_revision)` contains no episode identity, although `still_valid(uow, token)` must locate the episode. A successful boolean check also leaves a race before output publication or effect application. Nonurgent material answers can change the evidence without changing urgency. The package requires pinning `state_snapshot_version` and rejecting stale application when material evidence changes ([CONTRACTS:269](docs/product/CONTRACTS.md:269)). **Required:** define the complete episode-bound token, its no-cycle representation, and E13/E12’s atomic check-and-apply/publication boundary against current state. Specify client invalidation of already queued output. Test a change between validation and publication, normal-answer corrections, and two episodes with identical cycle numbers. Evidence: [E11:177](docs/tdd/E11.md:177). R1-11 remains partial.

15. **[major] Sections 3.4 and 12: V03 is still demonstrated by an invented producer, and emergency warning entry lacks its help effect.** T-E11-007 assumes a concerning measurement raises an emergency person warning from warning-rules. The package has no observation condition, and E24 records this as unresolved R-E24-5 with “Interim: none.” Separately, `PersonWarning(emergency)` only produces cancellation; help opening is restricted to `RedFlagPresent`. Evidence: [E11:157](docs/tdd/E11.md:157), [E11:612](docs/tdd/E11.md:612), [E24:1006](docs/tdd/E24.md:1006). The package describes Emergency as “‘Someone needs help’ opens” ([USE-CASES:55](docs/product/USE-CASES.md:55)). **Required:** track the actual producer/configuration dependency, assign emergency-to-help ownership, and add a complete accepted-measurement-to-response test. A fabricated Warning only proves E11’s consumer behavior.

16. **[major] Sections 4.4, 7 and 10: the design carries forward the audited privacy defect without a request.** Automatically opening help invokes the package’s crew-wide `HelpSession` event, containing the clinical session rather than a minimal broadcast. Checking E11’s link afterward cannot undo that disclosure. E29’s automatic catch-up contribution also lacks an explicit approval/consent boundary. Evidence: [E11:345](docs/tdd/E11.md:345), [CONTRACTS:998](docs/product/CONTRACTS.md:998), [audit finding 5](crew-health-build-2026-11-14/audit/AUDIT-astra.md:29). **Required:** request separate operational broadcasts and authorized clinical projections, and define what E29 may expose before approval. Specify the emergency-access path when an incapacitated patient has not shared their episode. Test unauthorized event subscribers, caches, ground projections and the authorized officer’s minimal access.

17. **[major] Sections 4.2 and 11: bounded batches do not bound the queue or prevent optional cancellation from delaying help.** One worker serializes help opening and cancellation calls; a blocked cancellation delays help. The pending queue has an alarm threshold but no admission bound, and `failed` effects have no defined recovery action. Clock-back behavior also ignores the persisted `next_attempt_at` deadline. Evidence: [E11:295](docs/tdd/E11.md:295), [E11:592](docs/tdd/E11.md:592). The charter requires bounded queues and says urgent paths never wait on optional services ([BUILD-CHARTER:90](docs/BUILD-CHARTER.md:90)). **Required:** isolate or prioritize help delivery, define bounded admission with durable overflow handling, restart/rearm behavior for failed effects, clock-correction-safe scheduling, and explicit memory/query bounds. Test cancellation saturation, backlog overflow, exhausted retries and backward clock jumps. R1-14 and R1-15 remain partial.

18. **[major] Sections 4.1, 4.2 and 12: a permanently failing evaluator can permanently prevent valid record entry.** Urgency evaluation executes inside answer acceptance, but failure handling only covers storage faults. There is no durable outcome for an otherwise valid answer when classification or an in-process subscriber fails repeatedly. Audit finding 9 explicitly identifies this problem and requests durable input capture with evaluation marked unavailable ([audit:61](crew-health-build-2026-11-14/audit/AUDIT-astra.md:61)). **Required:** agree with E01 how valid input, pending evaluation, audit and recovery work commit atomically without accepting an incomplete safety evaluation as normal. Preserve existing urgency and route to the human path. Add a permanently failing evaluator test, not only process-kill and retry tests. Evidence: [E11:276](docs/tdd/E11.md:276).

19. **[major] Sections 2, 4 and 6: transaction and error contracts remain insufficiently specified.** Section 11 says no write transaction spans a port call, while disposition explicitly reads authority through ports inside `BEGIN IMMEDIATE`. Those readers lack an agreed snapshot, failure result and deadline. API errors use the package envelope without addressing the charter’s RFC 9457 requirement. Evidence: [E11:287](docs/tdd/E11.md:287), [E11:595](docs/tdd/E11.md:595), [BUILD-CHARTER:73](docs/BUILD-CHARTER.md:73). **Required:** distinguish transaction-local readers from external calls, specify their complete typed contracts and unavailable outcomes, and ensure authority cannot change between checking and committing disposition. File the shared error-envelope/media-type reconciliation request and give an exhaustive domain-error mapping.

20. **[major] Sections 9 and 14: deployment assumptions are now stale.** `DEPLOYMENT.md` appeared during this review and is binding. It requires independent site hubs, home-node ownership of urgency, explicit handling of divergent clinical versions, and rover stock custody. E11 still defers all multi-site behavior to “one hub per episode,” while its gate uses only the active environment and roster. Evidence: [E11:539](docs/tdd/E11.md:539), [DEPLOYMENT:163](docs/DEPLOYMENT.md:163), [DEPLOYMENT:274](docs/DEPLOYMENT.md:274). **Required:** map T0 through T7, define local versus replicated event handling, prevent imported history from rerunning urgent effects, and specify disconnected care and disposition reconciliation. Gate against the subject’s reachable kit and operators, not environment-wide inventory. Test a disconnected rover and base in the same environment. This addresses audit findings 8 and 16. `SYSTEM.md` remained absent at the final check.
