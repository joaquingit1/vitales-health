VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.3, 3.4 and 3.7: retained assignments can violate eligibility and describe the wrong task.**  
   E31 lines 118 to 119 preserve `changed` assignments “always” and retain accepted assignments unless the person becomes the subject or goes on EVA. Consequently, a changed assignment survives those exclusions, and an accepted “Compressions” assignment can survive switching to `eye_injury`. Package [CONTRACTS.md:1463](CONTRACTS.md:1463) requires roles to “never assign” the subject or an EVA participant to an on-site role, while line 1362 also protects manual changes. **Required change:** reconcile these rules explicitly. Preserve manual history without presenting an ineligible or obsolete assignment as actionable. Request any necessary contract representation, and test changed assignments after EVA, subject changes, flow changes and role removal.

2. **[blocker] Section 3.3: the engine automatically fills skilled roles with unqualified candidates.**  
   E31 lines 130 to 133 fall back to the first eligible person when a required skill has no holder. Package [CONTRACTS.md:1355](CONTRACTS.md:1355) says a skilled role goes to an “eligible holder”; line 1356 requires roles nobody can fill to appear in `unfilled`. **Required change:** remove this automatic relaxation. Leave the role unfilled when no qualifying holder exists, preserve the human help path, and test `never`, `stale` and SIM-only practice in a LIVE mission.

3. **[major] Sections 3.4 and 4.1: proposal idempotency suppresses required recomputation.**  
   Help proposals are deduplicated by session revision, although an overlay or skill change need not change that revision. Plan proposals include a roster/overlay digest but omit practice and configuration changes. Section 3.4 requires skill-triggered recomputation, yet section 4.3 does not subscribe to `skill.practiced`. Package [CONTRACTS.md:1362](CONTRACTS.md:1362) requires proposals when overlays or participants change. **Required change:** distinguish duplicate event delivery from a new proposal input snapshot, define every invalidation input and subscription, and test overlay and practice changes with an unchanged session revision.

4. **[major] Sections 3.2, 3.5, 7 and 11: time-dependent state has no complete refresh or clock-correction policy.**  
   Freshness changes with time, but the only scheduled work is drill abandonment; skills and readiness screens update only on practice events. A holder can become stale while the same proposal and screen remain visible. Abandonment also lacks restart catch-up and clock-jump behavior. Package [CONTRACTS.md:1369](CONTRACTS.md:1369) defines freshness “at the hub clock,” and [CONTRACTS.md:9](CONTRACTS.md:9) requires clock corrections to be recorded. **Required change:** specify expiry invalidation, client refresh and offline presentation, clock-version handling, future-timestamp validation and abandonment recovery. Test forward/backward jumps, restart across midnight and freshness expiry without incoming events.

5. **[blocker] Sections 5 and 9: dependency failures and capacity limits leave old assignments looking current.**  
   E31 lines 334 to 335 return the previous proposal unchanged after 200 assignments; lines 342 to 343 skip recomputation on timeout and wait for another trigger. Neither invalidates existing assignments or makes degradation visible, contrary to section 9’s promised `unfilled` state. An EVA change followed by an overlay timeout can therefore leave an unavailable person assigned. Package [CONTRACTS.md:1463](CONTRACTS.md:1463) makes the exclusion unconditional. **Required change:** define a visible unavailable/stale projection, bounded recovery independent of another user event, restart recovery and queue-overflow handling. Test failures after an existing valid assignment, including saturation.

6. **[major] Sections 4.3 and 8: configuration activation violates plan-run pins.**  
   E31 lines 286 to 287 re-propose open contexts under new role rules, and lines 418 to 420 expect configuration edits to change proposals without distinguishing plan runs. Package [CONTRACTS.md:1269](CONTRACTS.md:1269) says a plan run pins `onboard-plans`, `skills-catalog`, `role-rules`, `kit-map` and `ui-copy` “for its life.” **Required change:** make release selection explicit for every context and carry the necessary pins through the plan query port. Test an existing run against a newly opened run after activation, plus rejection of corrupt configuration while the previous release remains usable.

7. **[blocker] Section 4.1 and request Q5: accepting an assignment is treated as evidence of performing a skill.**  
   E31 lines 221 to 223 grant practice at session closure to everyone with an accepted or changed skilled role. A designated second helper who never performed compressions can thereby become fresh. Package [CONTRACTS.md:1369](CONTRACTS.md:1369) defines event practice as “the person did the skill.” **Required change:** require attributable performance evidence or explicit completion attestation, with a request if the existing contracts cannot express it. Define event time and provenance, and explicitly reject unsuccessful guided-check results. Test unused assignments, reassignment, false alarms, retries and duplicate delivery.

8. **[blocker] Sections 3.5 and 4.1: drill validation can award skills the scenario never practices.**  
   E31 line 225 requires the scenario to belong to only one requested skill, while completion credits every requested skill. A request containing the pulse scenario and both pulse and CPR can therefore award CPR without the CPR scenario or its manikin requirement. Package [CONTRACTS.md:1375](CONTRACTS.md:1375) starts a drill for a catalog scenario and its skills; the catalog nests scenarios under each skill. **Required change:** define and validate the exact scenario-to-skills relationship, including supplies for every credited skill. Also bind a linked routine occurrence to its owner, origin and completing participants. Test unrelated extra skills, incompatible scenarios and another person’s occurrence.

9. **[major] Sections 4.1 and 5: routine completion can be lost after an accepted drill completion.**  
   E31 lines 229 to 231 call E25 after the drill commits, with no durable retry obligation. A crash between those operations permanently separates the completed drill from its routine occurrence. Package [CONTRACTS.md:1108](CONTRACTS.md:1108) requires state, audit and outbox to commit together; the charter additionally requires accepted records to survive crash and retry. **Required change:** specify either a shared transactional port or a durable, idempotent completion obligation with reconciliation. Define refusal behavior without filling genuine misses. Add crash-boundary, disk-full, lost-response and duplicate-completion tests.

10. **[major] Sections 3.6, 7 and request Q3: practice patches have no implementable browser transport.**  
    `PracticePatchRow.vue` cannot call a Python protocol. “Through E22’s view” does not name a wire contract, and the frozen participation views have no practice-patch field. Package [CONTRACTS.md:1018](CONTRACTS.md:1018) requires screens to load through endpoints; [backlog.json:1552](backlog.json:1552) requires the practice-patch feature. **Required change:** resolve Q3 into an approved endpoint or view extension with schema, authorization, pagination and refresh behavior. An in-process port is not a working interim browser implementation.

11. **[major] Sections 3.2, 3.6 and 5: historical patch derivation is underspecified and can use future practice.**  
    `skill_record` chooses the greatest practice timestamp without restricting it to `now`; patch derivation evaluates freshness at an earlier drill completion. Later practice can therefore make an earlier completion appear to have earned `skill_fresh`. The award identity includes mission, but repository signatures and drill storage do not define mission scoping. Section 3.6 also reads practices while T-E31-070 says adding guided checks changes nothing. Package [config-participation-rules.schema.json:74](api/schemas/config-participation-rules.schema.json:74) defines the milestone through practice within its cadence. **Required change:** specify historical cutoffs, eligible sources, completion ordering, mission isolation and configuration-version semantics. Test later practice, partial participants, mission changes and configuration edits.

12. **[major] Sections 4.1, 6 and 10: role actions lack object-level authorization and context guards.**  
    The design says any session in `x-roles` may act, but does not require the supplied assignment to belong to the path’s context, remain current, or still be actionable. Package [CONTRACTS.md:145](CONTRACTS.md:145) states that supplied IDs are not authorization, and line 1361 permits helper reassignment. **Required change:** define helper and station authorization, assignment-to-context binding, replacement checks and transactional revalidation against closure or concurrent proposals. Test a role ID from another context, replaced assignments and two-client races.

13. **[major] Sections 3.4, 4.2 and 6: plan-step role identity is lost across the repository and API.**  
    The application accepts `step_id` and stores `plan_step_id`, but repository methods operate on the whole plan context. The shared `RoleAssignment` contains no step identifier, leaving the UI unable to distinguish two steps needing the same role and skill. Package [CONTRACTS.md:1287](CONTRACTS.md:1287) explicitly provides roles for plan steps. **Required change:** define per-step proposal, replacement and completion behavior, and request the missing shared association or provide an unambiguous contract-compatible mapping. Test two simultaneous skill steps and completion of one without disturbing the other.

14. **[major] Section 3.3 and request Q2: an unapproved preference is already required as hardcoded behavior.**  
    E31 lines 116 to 117 apply opener-last ordering, while Q2 acknowledges that the configuration vocabulary lacks it. The rule also affects roles without skills, although package [CONTRACTS.md:1355](CONTRACTS.md:1355) assigns those to “the first eligible person in roster order.” **Required change:** keep the current contract behavior until the request is resolved, or make the approved preference configurable with precisely limited scope. Test both the CPR tie and unskilled-role roster ordering. Do not implement the requested configuration change invisibly in code.

15. **[major] Sections 4 and 6: API and error behavior is not fully contract-compatible.**  
    `listPlanRunRoles` is described as a list, but [openapi.yaml:6990](api/openapi.yaml:6990) requires `{items, page}` with pagination. Completion validation does not define omission of `participant_ids`, although [requests.schema.json:1701](api/schemas/requests.schema.json:1701) makes it optional for partial completion. E31 also names `INVALID_VALUE` for completion without requesting its missing operation response. Finally, typed domain errors and their mapping are unspecified; the charter’s RFC 9457 requirement conflicts with the frozen `ErrorEnvelope`. **Required change:** specify the exact response envelope, defaults, headers and typed error mapping. File the error-format conflict and missing response declarations as requests rather than inventing wire behavior.

16. **[major] Sections 2 and 4.2: the declared “exact signatures” leave essential integration types and services undefined.**  
    `HelpSessionSnapshot`, `PlanRunSnapshot`, `DrillOccurrence` and `ActiveOverlay` lack complete shapes, while `EnvironmentPort` is named without a protocol. E30 explicitly requires `DrillReader.running_drill` in [E30.md:438](docs/tdd/E30.md:438), but E31 does not provide it. Package [tdd/E31.md:41](tdd/E31.md:41) requires dependencies and integration examples. **Required change:** define owned DTOs, revisions, pins, missing-data semantics and typed failures; provide the drill reader; reconcile Q1 with E30’s ephemeral-check and event behavior. Name the owning files and integration tests.

17. **[major] Sections 5, 8, 11 and 12: resource limits are partly hardcoded and do not bound the expensive reads.**  
    Limits of 10 drills, 200 assignments, 128 queue entries, import sizes and retry rates have no named configuration fields. Meanwhile, practice and completed-drill repositories return unbounded histories, and patch calculation replays them on every read; “10,000 practices” is only a benchmark input. Package [CONTRACTS.md:1113](CONTRACTS.md:1113) requires missing numbers to be added to configuration, and charter lines 90 to 91 require bounded work and timeouts. **Required change:** name validated settings and provenance, bound repository batches and derivation work, define indexes and memory budgets, and specify overflow behavior. Add parser property tests, malformed-configuration tests and sustained-load tests proving help remains responsive.
