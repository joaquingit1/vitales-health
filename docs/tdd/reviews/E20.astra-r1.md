VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.3, 3.4 and 4.1: installation and restore do not exclude concurrent writes or recover interrupted file replacement.** The install sequence takes a backup, migrates, and may restore that backup without first stopping the serving hub. Restore merely checks that `hub.lock` is free. The supervisor can restart the hub while files are being replaced. Accepted writes after the backup could therefore disappear. Evidence: [E20:223](docs/tdd/E20.md:223), [E20:277](docs/tdd/E20.md:277). **Required change:** specify an exclusive maintenance protocol respected by the supervisor and every writer, held through backup, migration, replacement and restart. Persist installation and restore phases durably, define recovery after interruption at each phase, and test concurrent submissions and power loss between every file or pointer change.

2. **[blocker] Sections 3.4 and 5.2: golden restore omits the actual private-data keystore.** E20 requests a shred list from E03 and lists backup and node keys on the golden medium. E02 instead owns the credential verifiers, per-item keys, tombstones and `keystore-latest.enc`. Restoring the listed E20 artifacts on a replacement laptop cannot recover those credentials or decrypt retained private records. Its shred-list interim also does not implement E02’s deletion protection. Evidence: [E20:285](docs/tdd/E20.md:285), [E20:551](docs/tdd/E20.md:551), [E02:545](docs/tdd/E02.md:545). **Required change:** agree the recovery seam with E02, include its latest-only encrypted mirror, and apply its tombstone checks before restoring private access. Test replacement-machine recovery, deleted entries, stale mirrors and unavailable deletion evidence.

3. **[major] Sections 3.4 and 11: two individually valid database backups are not a consistent backup set.** E20 specifies online backups of `hub.sqlite` and `private.sqlite`, but no snapshot ordering or coordination with the two-store journal protocol. A private-store snapshot taken before a journal write and a hub snapshot taken afterward can contain a marker whose ciphertext is absent; both integrity checks still pass. Evidence: [E20:235](docs/tdd/E20.md:235), [E20:864](docs/tdd/E20.md:864), coordinator decision D4. **Required change:** define a coherent backup-set protocol and manifest, including the recovery cutoff, schema compatibility and referenced releases. Test concurrent journal writes at each backup boundary and verify restored cross-store references, patient namespaces and evidence-release consistency, as CONTRACTS section 10 requires.

4. **[blocker] Sections 2, 8, 13 and 14: the design substitutes unapproved shared mechanisms.** SYSTEM assigns backup and restore to E01 platform and operational bounds to the shared settings mechanism. E20 creates another backup/restore implementation and a third settings source, then declares “Interim: as designed here.” Moreover, `docs/requests/E20.md` does not exist: none of its twelve requests is filed through the binding process. Evidence: [E20:1015](docs/tdd/E20.md:1015), [SYSTEM:121](docs/SYSTEM.md:121), [SYSTEM:545](docs/SYSTEM.md:545). **Required change:** file the requests and resolve ownership, settings and composition seams with the coordinator and E01 before treating them as implementation instructions. Until then, consume the existing E01 mechanisms through agreed ports.

5. **[major] Sections 3.3 and 12: the rollback acceptance test contradicts E01’s migration policy.** E20 promises that the previous version reads the migrated database. E01 explicitly refuses startup when the database contains a migration unknown to that version. Thus T-E20-025 cannot pass after an upgrade that introduces a migration. Evidence: [E20:227](docs/tdd/E20.md:227), [E01:587](docs/tdd/E01.md:587). **Required change:** resolve the compatibility policy with E01 and document the resulting rollback protocol. Test an actual new migration, a record accepted by the new version, and rollback retaining that record.

6. **[major] Sections 4.1, 4.4 and 15: first installation has no path through the pre-start verifier.** Every hub start first opens the database read only for verification; failure starts the static server. E20’s `Init` creates directories and keys, but does not initialize the database. E01’s storage initialization consequently cannot run on a pristine installation. Evidence: [E20:335](docs/tdd/E20.md:335), [E20:343](docs/tdd/E20.md:343), [E20:448](docs/tdd/E20.md:448). **Required change:** define a recognized pristine initialization state that invokes E01’s initialization and validation before serving. Distinguish it from an initialized installation whose database has disappeared. Exercise both cases in the clean-install and recovery tests.

7. **[major] Sections 1.2, 4.5 and 7.1: the general durable command queue is missing.** E03 sends answers, submissions and reaction tests through an E20 queue. E20 defines no queue API or implementation and assigns the command journal to E26. E26’s journal is help-specific and stores reference-only help commands; it cannot implement the observation retry shown in E20’s failure diagram. Evidence: [E20:35](docs/tdd/E20.md:35), [E20:475](docs/tdd/E20.md:475), [E03:594](docs/tdd/E03.md:594), [E26:641](docs/tdd/E26.md:641). **Required change:** define the shared queue and its consumer interface, encrypted actor/mission partitions, exclusions for private journal and reports, conflict handling, bounded retention and post-24-hour duplicate acceptance. Test lost responses, restart, account switching, revocation and concurrent clients.

8. **[major] Sections 2, 4.2, 5.4 and 5.7: the model integration disagrees with both providers.** E20 consumes `model/model-release.json` with `gguf_sha256`, `parallel` and `ctx`, and tells E13 to call `WorkerRuntime`. E17 publishes `model/releases/<release_id>.json`, nested runtime settings, `ModelLaunchSpecPort` and a different supervisor interface; E13 calls E17’s `ModelRuntimePort`. E20 also recomputes thread count instead of using the pinned runtime setting. Evidence: [E20:68](docs/tdd/E20.md:68), [E20:578](docs/tdd/E20.md:578), [E17:144](docs/tdd/E17.md:144), [E17:299](docs/tdd/E17.md:299). **Required change:** agree one control interface and consume E17’s validated launch specification and release format. Define the signed model-artifact installation path and test the real provider interfaces, including identity verification and runtime settings.

9. **[major] Sections 1.3 and 4.2: container mode bypasses the resource arbiter.** `ExternalRuntime.acquire` succeeds whenever a service is healthy; it has no described pause, preemption or scheduling protocol. Requiring more RAM does not implement PRD section 10’s requirement to schedule forecasting and embedding work around interactive inference. Evidence: [E20:48](docs/tdd/E20.md:48), [E20:397](docs/tdd/E20.md:397), [PRD:588](docs/product/PRD.md:588). **Required change:** specify how external workers obey the same scheduling decisions, or disable conflicting work explicitly. Run the contention acceptance test against the actual `full` profile.

10. **[major] Sections 5.4, 5.6 and 5.8: container connectivity is unspecified and conflicts with the prescribed bindings.** Workers and the hub bind loopback, while compose places them in separate services. Those loopback listeners are not reachable from another service’s network namespace or through ordinary published ports. Evidence: [E20:574](docs/tdd/E20.md:574), [E20:599](docs/tdd/E20.md:599), [E20:638](docs/tdd/E20.md:638). **Required change:** define the container network namespaces, listener addresses, endpoint discovery and host exposure while preserving the native loopback boundary. Test browser-to-hub and hub-to-worker calls, not just each container’s self-probe.

11. **[major] Sections 5.3 and 9.2: supervisor recovery leaves worker processes unmanaged.** Children survive supervisor failure, but replacement logic only terminates the orphan hub. Existing camera, model and other workers retain their ports and memory while the new supervisor attempts to launch replacements. Evidence: [E20:568](docs/tdd/E20.md:568), [E20:788](docs/tdd/E20.md:788). **Required change:** specify authenticated process ownership and reconciliation for every surviving child, using adoption or termination before replacement. Guard against PID reuse and stale leases. Extend T-E20-022 to start all workers, kill the supervisor, recover, and demonstrate that no duplicate or uncontrolled worker remains.

12. **[major] Sections 6 and 7.1: bootstrap hash verification lacks the original bytes it promises to verify.** The bootstrap contains parsed document JSON, while its pins are hashes of the original file bytes. Parsing and reserializing can change whitespace, ordering and escapes without changing the JSON value, so the promised per-document verification is not defined. Evidence: [E20:663](docs/tdd/E20.md:663), [E20:676](docs/tdd/E20.md:676), [CONTRACTS:518](docs/product/CONTRACTS.md:518). **Required change:** carry exact raw bytes in a defined encoding, or define a separate transport digest without changing the configuration version. Test noncanonical source files and byte corruption. The repository’s help-presentation example already produces different raw and reserialized hashes.

13. **[major] Section 7.1: cache eviction can remove an open session’s pinned release.** `DocumentStore` retains active, last-good and a bounded number of other releases, with no protection for releases referenced by open sessions, plan runs or queued commands. E26 explicitly requires those pins to survive eviction. Evidence: [E20:676](docs/tdd/E20.md:676), [E26:626](docs/tdd/E26.md:626), [CONTRACTS:521](docs/product/CONTRACTS.md:521). **Required change:** add reference registration and release to the shared store, evict only unreferenced versions, and define storage-exhaustion behavior. Test multiple activations beyond the retention limit followed by an offline restart of an older open session.

14. **[major] Sections 2, 7.1 and 14: the static help fallback may contain no help.** The optional `HelpStaticContent` provider is absent from E26’s current design; E20’s interim renders only a release ID. This cannot meet its own “Fixed first screen visible, never empty” fail-safe or T-E20-035 when all usable bundles are unavailable. Evidence: [E20:65](docs/tdd/E20.md:65), [E20:814](docs/tdd/E20.md:814), [E20:1002](docs/tdd/E20.md:1002). **Required change:** make valid static help content a prerequisite for publishing the shell, using an agreed provider or the validated configuration directly. Test corruption of active, last-good and bootstrap bundles together; wiping IndexedDB alone does not exercise this fallback.

15. **[major] Section 5.2: crash filenames are invalid on a supported operating system.** `ProcessSpec.name` includes `adapter:<id>`, and crash filenames interpolate `<process>` directly. A colon is invalid in a normal Windows filename, so an adapter crash can fail while recording its diagnostic report. Evidence: [E20:103](docs/tdd/E20.md:103), [E20:544](docs/tdd/E20.md:544). **Required change:** define a bounded, collision-safe filesystem encoding or use an opaque report ID as the filename, keeping the process name inside the document. Test adapter crash reporting on Windows.

16. **[major] Sections 1, 8, 12 and 15: required traceability and acceptance evidence are incomplete.** There is no normative rule trace, activation-effects section or acceptance matrix. Several scenario labels overclaim their tests: T-E20-039 checks only supervisor status for V69; T-E20-035 omits the active plan required by V97; T-E20-040 omits malformed output and the incomplete assessment required by V27. Restore tests also omit CONTRACTS section 10’s namespace and evidence-consistency checks. Evidence: [E20:899](docs/tdd/E20.md:899), [VALIDATION:89](docs/product/VALIDATION.md:89), [VALIDATION:117](docs/product/VALIDATION.md:117). **Required change:** add the template’s missing sections and map every acceptance clause to a concrete test or an agreed owning epic and test ID. Include property tests for the new parsers and an actual design-lint report. Design-lint completion was not verified during this review: the available invocation produced no check results.
