1. **[blocker] Section 3.7: the coverage gate as written switches off every `latest` limit, including the emergency
   limits.**
   Line 204 says coverage is "absent for `latest`", and lines 211 to 212 say each limit is evaluated "only when coverage
   is at least its `min_coverage`". The package gives every `latest` limit a `min_coverage` of 0.75, including
   `o2_low_emergency`, `noise_peak_emergency` and `dust_mars_peak_emergency` (sensor-limits.example.json:173 to 197).
   Read as written, an absent coverage is never at least 0.75, so none of these limits is evaluated and the status is
   `insufficient_data`. CONTRACTS.md:682 says "`latest` has no coverage" and that the gate applies to coverage. It does
   not say a `latest` limit can never be evaluated. T-E23-031 would lock in the wrong reading.
   **Required change:** state that a limit on a `latest` aggregation skips the coverage gate and is evaluated whenever a
   current accepted reading exists at E, and that `min_coverage` on such a limit is ignored. Add a golden test in which
   `o2_low_emergency` crosses on one reading and returns `beyond_limit` at `emergency`. If you think the package means
   something else, file the question as a request. Until it is decided, the interim must evaluate the limit.

2. **[blocker] Sections 3.1 and 9: a clock regression can show a dead feed as current.**
   Line 119 pauses staleness sweeps during `ClockRegressed`, and says "no channel returns to `current` by the jump". The
   backup at lines 546 to 548, though, recomputes freshness on every read "from the stored reference and the request
   clock". With a regressed clock, `now - reference` shrinks, so a stale channel reads `current`. A feed that dies during
   the regression is never swept and never turns stale. The two sections contradict each other, and neither is safe. The
   charter makes "stale or offline readings never shown as current" a critical path (BUILD-CHARTER section 6). SYSTEM.md
   5.2 (lines 217 to 220) suspends only expiry-based clears; it never pauses staleness.
   **Required change:** compute freshness against `max(now, last committed instant)`, or against the instant
   `ClockRegressed` carries, until a correction is recorded. Keep sweeping, so channels can still go stale and never
   return to `current`. Define `stale_since` under regression. Extend T-E23-053 to cover a feed that dies during the
   regression, and a read of an already stale channel during it.

3. **[blocker] Sections 3.4 and 9: the freshness transition (event and warning) has no backup, and the deadline relies
   on replace semantics SYSTEM.md does not promise.**
   Lines 177 to 179 schedule `sensors.stale.<channel_id>` through `Scheduler.call_at` and say each new reading
   "replac[es] the earlier one". SYSTEM.md:524 defines `call_at` only as "durable, idempotent by key". If a second call
   with the same key is a no-op, the deadline fires at the first reading's due time. The handler finds the channel
   current, and nothing reschedules it. After that, a dying feed never publishes `ChannelFreshnessChanged` or
   `sensor.quiet`. The backup named at lines 546 to 548 covers only HTTP reads. A client already showing the card keeps
   the last value as current, because it refreshes on `sensor.quiet` and `sensor.status_changed` (line 482). E24 never
   raises `sensor_quiet` (E24.md:166), which V70 and UC17 require. Scheduling through `Scheduler.call_at` instead of
   `uow.schedule` also puts the deadline outside the reading's unit of work (SYSTEM.md:395).
   **Required change:** use `uow.schedule` inside the ingest unit of work. Have the handler reschedule at
   `reference + stale_after_seconds` whenever it finds the channel current. Add an independent bounded periodic sweep
   (a hub setting) that publishes missed transitions; this is the dissimilar backup for the event path. Ask E01 to
   state replace semantics in S5.10 if you rely on them. Add a test that deletes the scheduled job, then checks that
   `sensor.quiet` is emitted and `ChannelFreshnessChanged` reaches E24 within the sweep bound.

8. **[major] Section 3.8 step 6: a reused sequence number silently drops real readings.**
   Line 238 counts any stored `(channel_id, adapter_sequence)` as a duplicate and writes nothing. If an adapter loses its

   index with a code, keep the raw JSON in `sensors_batch`, and mark the adapter degraded. Define how duplicates of
   `(channel_id, observed_at)` are handled. Test sequence reset and replay restart.
