1. **[blocker] Section 4.5: gap creation is undefined for valid requests.** The algorithm always creates a CapabilityGap, but does not specify its required `episode_id`, `consequence` or `alternatives`. The package permits an omitted or null episode: [requests.schema.json:650](api/schemas/requests.schema.json:650). Conversely, [capability-gap.schema.json:66](api/schemas/capability-gap.schema.json:66) requires all three fields, with a non-null episode. **Required change:** specify every gap field’s source and resolve the episode-less case through an exact section 14 request. Define behavior for absent condition IDs, multiple conditions and no applicable plan. Test each case without fabricating an episode, condition or alternative.

2. **[blocker] Sections 4.5 and 12: the unavailable-request transaction is not fully durable or idempotent.** [E27.md:379](docs/tdd/E27.md:379) lists request, gap and outbox writes, but omits the audit entry and persisted idempotency result. T27-28 tests only a crash before the gap insert. Package [CONTRACTS.md:1108](CONTRACTS.md:1108) requires “the state change, the audit event and the outbox entry commit together”; line 210 requires the same key and body to return the first result. **Required change:** explicitly include the hash-chained audit and stored 422 result in the transaction. Define disk-full rollback and recovery after commit but before response delivery. Test concurrent identical submissions, changed-body reuse, restart, and retry after the environment or configuration changes. The retry must return the original request and KitCheck without creating another gap.

3. **[blocker] Section 4.5: kit membership is treated as sufficient authorization.** The success branch immediately creates a request when `kit_check.can` is true. It never invokes the remaining capability, operator, context and consent checks. Package [PRD.md:483](PRD.md:483) defines R07 as “Gate requests on capability, operator, context and consent.” The blanket statement that any request about another person fails also leaves authorized care undefined. **Required change:** identify the E05 checks that follow a successful kit check, their order and errors, and the applicable consent and role policy. Distinguish an aboard but disconnected instrument from an absent instrument. Add integration cases for unavailable operators, inapplicable context, missing consent, unauthorized cross-person access and an authorized onboard care path when the subject is incapacitated.

4. **[major] Sections 2 and 15: the assistant integration uses an unsupported tool payload.** The sequence sends `propose_measurement(ecg_rhythm, ICL10)`. Package [tool-catalog.json:446](tool-catalog.json:446) permits only `capability_code`, `reason` and `source_ids`, with `additionalProperties: false`. The separate ModelAction `request_measurement` supports `condition_ids` and `decision_affected` ([model-action.schema.json:54](api/schemas/model-action.schema.json:54)). **Required change:** specify the exact E12/E13 mapping into `MeasurementRequestCreate`, including condition IDs and the required decision text. Request any tool-schema extension explicitly. Test the real validated assistant boundary, rather than calling E05 directly with fields the tool cannot supply.
