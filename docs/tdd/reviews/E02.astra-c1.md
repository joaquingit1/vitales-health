The shared documents changed during this review. The findings below use the updated specification, including D18. No files were modified; implementation tests were not run.

1. **[major] Section 2: the private coordinator seam names a retired interface. Introduced by the revision, now incompatible with the updated shared specification.**

   [E02:95](docs/tdd/E02.md:95) declares `PrivateJournalCoordinator.write(...)` as the shared S5.8.1 interface. Current SYSTEM section 5.8.1 explicitly says, “PrivateJournalCoordinator is retired,” and defines `PrivateRecordCoordinator` for journals and report versions. [E01:144](docs/tdd/E01.md:144) exposes that replacement.

   **Required change:** Update E02’s seam and R-E02-6 to the exact current `PrivateRecordCoordinator`, private value types and reference-writer registration. Specify how E02’s vault participates in the shared backup barrier for journal and report key allocation/deletion. Extend the integration test mapping to cover those callers. This implements D18; it does not require reopening that decision.

2. **[major] Sections 5, 9, 12 and 13: the concrete live-vault adapter is still unspecified. Introduced by the revision’s replacement of the previous keystore design.**

   [E02:314](docs/tdd/E02.md:314) repeats the required cryptographic and revocation properties, but says only that E02 supplies “vault access controls.” Section 13 claims `identity/adapters/vault.py`, while [E01:146](docs/tdd/E01.md:146) assigns the concrete `PrivateKeyVault` provider to E02.

   Neither the adapter section nor its storage table identifies the backing store for wrapping keys, durable deletion intents, replica receipts or the generation that must survive data restoration. There is also no concrete explanation of secure key deletion or exclusion from OS/cloud snapshots, although SYSTEM section 7.4 explicitly requires that documentation. Protocol fakes cannot establish those properties.

   **Required change:** Specify the supported local vault backend and its persistence, startup, deletion and snapshot-exclusion behavior using the existing shared protocol. Identify ownership and bounded processing for registered replicas and recovery intents. Add real-adapter fault tests demonstrating durable revocation, rejection of stale vault state, and preservation of entry B after deleting entry A. Do not introduce another transaction or recovery protocol.

3. **[major] Sections 2, 3.1 and 4: durable consent-expiry latching has no transaction-compatible execution path. Introduced by the revision.**

   [E02:136](docs/tdd/E02.md:136) requires expiry to be checked at every use and “latched durably once reached.” However, section 2 binds consent readers to the caller’s snapshot, and [E02:267](docs/tdd/E02.md:267) authorizes SSE delivery through a fresh snapshot. SYSTEM section 5.7 explicitly states that `ReadSnapshot` rejects mutations.

   The command table provides session/counter sweeps, but does not specify which operation persists terminal grant expiry observed by a read-only caller. A builder must choose between an illegal snapshot mutation, an undeclared second transaction, or an unpersisted expiry observation. The last choice leaves the expiry-versus-clock-correction behavior unresolved.

   **Required change:** Define the shared-UoW or scheduler/clock-handler transition that durably records terminal grant expiry, and define authorization while that transition is pending. Preserve the caller’s snapshot rules. Add a test where a read-only authorization first observes expiry, then the clock regresses before the scheduled sweep or the process restarts; correction must never reactivate that grant.

**Package issues**

- **Local authentication mutations lack a declared replication exemption.** SYSTEM section 5.7 requires a replication declaration for every repository mutation and explicitly exempts journal plaintext. Credentials, sessions and attempt counters must remain local. [R-E02-5](docs/requests/E02.md:66) correctly records this shared-mechanism gap. Resolve it centrally before authentication storage can pass commit accounting.
- **Several required authorization contracts remain unsettled.** General consent/deletion operations, exact identity and consent query interfaces, help-membership facts, and approved-report snapshot integration remain tracked by R-E02-1/4/5/9/10/19. Existing consumer designs still need propagation. E02 correctly treats missing integrations as unavailable and acceptance as incomplete; those interims do not establish integration acceptance.
- **Roster and consent replication need catalogue support.** DEPLOYMENT section 4.4 assigns these records a home writer, while SYSTEM section 5.7.1’s closed projection catalogue does not supply their projection contracts. The coordinator must register the permitted projections and ownership before E02’s replication promises can be implemented.
