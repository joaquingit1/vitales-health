VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.7, 10 and 12: the assistant guard permits unsupported clinical advice.** G4 checks citations only for turns without an action, and a substring containing one kit name can validate an otherwise unsupported narrative. G2 omits fields such as `request_review.note`; G3 recognizes only the loader's small medicine vocabulary. Citations also disappear before rendering because `HelpSession.assistant` carries only `last_text`. Evidence: E26 lines 211 to 226; package `VALIDATION.md:180`: “Every assistant turn cites a step of the pinned flow or a kit item.” Require validated references for every suggestion, check every displayed field, and render clinical instructions from the referenced configuration. Define how citations reach the screen. Add adversarial tests for action-bearing turns, unsupported text appended to valid references, and medicine names outside the loader vocabulary. Include direct domain tests rejecting assistant attempts to open, change or close safety state.

2. **[blocker] Sections 3.7, 8 and 14 Q5: review status and equipment eligibility are not enforced.** A document-wide draft notice does not implement flow review state. The guard reduces plans to step IDs and text, discarding review status, environment restrictions, required operator, skills and available stock. Consequently, verbatim configuration text can still be inappropriate guidance. Evidence: package `backlog.json:1132` requires “flows carry their review state”; `PRD.md:548` permits detailed procedures “only if appropriately sourced and reviewed for the intended setting”; `tool-catalog.json:755` requires a chosen step to “be runnable here.” Resolve Q5 before implementation, define LIVE versus explicitly labeled simulation eligibility, and consume E28's evaluated step availability. Specify the fallback when no approved applicable instruction exists. Test rejected and unreviewed content, missing equipment, exhausted supplies and unavailable skill holders.

3. **[blocker] Sections 3.6 and 4.2: assistant results are not bound to the context that authorized them.** `turn_completed(session_id, turn_id, guard)` can apply a previously accepted result after another helper switches flows, closes the session or changes relevant state. There is no persistent turn ledger, cancellation rule or atomic context recheck. A single stored conversation ID also lacks an ownership rule for multiple helpers. Evidence: E26 lines 202 to 207 and 295 to 340; package `CONTRACTS.md:269` requires stale output handling when material state changes, and line 954 permits one running turn per conversation. Define turn ownership, snapshot revision, configuration pins, cancellation and durable duplicate handling. Revalidate before committing or displaying output. Test flow changes, close, helper departure, two simultaneous asks and callbacks after restart.

4. **[blocker] Sections 3.8, 6, 7 and 14 Q7: delayed ticks can mark the wrong procedure step complete.** A client checks flow A, another helper switches to flow B, and the first client's stale `tick_step(0)` is merged into B. Also, Q7 incorrectly proposes adding `flow_id`: it already exists in `api/schemas/requests.schema.json:1168`; the missing part is its tick-specific semantics. 5. **[blocker] Sections 5.2, 8 and 9: the cache cannot preserve an open session's pinned release.** Documents are stored by name and replaced on activation. An open session can therefore resume offline using different questions, answer indexes or steps. An offline-created session has no specified reconciliation when the hub's active release differs. Evidence: E26 lines 435 to 440; package `CONTRACTS.md:521` says an open help session keeps its pinned versions, and line 522 requires caching documents “by version.” Store immutable documents by name and hash, activate complete validated bundles atomically, and retain versions referenced by sessions and pending commands. Define release-mismatch recovery without reinterpreting old answer indexes. Test interrupted updates, reordered answers and reconnect across activation.

6. **[major] Sections 5.2, 9 and 12: pre-authentication and missing-cache behavior are not buildable.** The cache is filled at sign-in, but no provisioning path supplies the first screen before the first successful authentication. Evidence: package `PRD.md:548`: “The fixed first screens of Someone needs help stay usable before authentication is complete.” Define the E20 bootstrap artifact, validation, last-good storage and behavior when no valid copy survives. Exercise a signed-out cold launch, expired authentication, missing IndexedDB and corrupt configuration with the hub unavailable.

7. **[blocker] Sections 3.2, 5.2 and 7: offline reconciliation can lose or duplicate care history.** Answers are replayed first, then ticks are sent only if their flow matches the final node.
