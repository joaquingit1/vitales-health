VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.7, 4.3 and 10: officer access bypasses episode consent.** The visibility matrix grants officers the entire episode except restricted answers, and the proposed event uses that same rule. This exposes concern text, reviews and tasks without an episode grant. Evidence: [E15:301](docs/tdd/E15.md:301); the package gives officers access to “Explicitly shared clinical records” ([PRD:146](docs/product/PRD.md:146)). SYSTEM section 8.3 additionally requires labeled, audited emergency access. **Required:** check subject, purpose, consent and explicit emergency authority across reads, commands, lists, events and error `current_state`. Apply restrictions to derived assessments, task text and timeline references as well as raw answers. Test revoked grants, event replay, session changes and restricted information copied into derived records. This addresses audit finding 5.

2. **[blocker] Section 3.4: the anomaly resolution rule can close a continuing symptom concern.** It accepts any qualifying observation when no structured answer is `present`. A concern described only in free text, with absent red flags and unknown or declined follow-up answers, passes this test. The observation need not repeat the anomalous quantity or establish that the anomaly was not reproduced. Evidence: [E15:258](docs/tdd/E15.md:258); the package says a normal repeat can resolve an anomaly “while leaving the symptom episode open” ([PRD:212](docs/product/PRD.md:212)). **Required:** distinguish an explicitly identified measurement anomaly from a symptom concern, identify the original and repeat evidence, and specify the applicable reviewed rule. Unknown, declined and unanswered information must not establish absence. Test unrelated readings, superseded readings, free-text symptoms and unknown red flags.

3. **[blocker] Sections 4.1 and 6: a review can discharge work it did not review.** `RecordReview` closes the single review task regardless of its accumulated sources, the assessment actually covered, or E13 refusing to mark a stale assessment reviewed. The interim explicitly closes work current at commit without the reviewer’s expected revision. Evidence: [E15:381](docs/tdd/E15.md:381), [E15:662](docs/tdd/E15.md:662); package CONTRACTS section 5 requires conflicts rather than silently overwriting, and section 6 says not to apply an assessment to evidence it never saw ([CONTRACTS:203](docs/product/CONTRACTS.md:203), [CONTRACTS:269](docs/product/CONTRACTS.md:269)). **Required:** bind review to the displayed episode revision and explicitly covered source revisions. Preserve uncovered work and unresolved decisions. Before the concurrency extension lands, permit attributed append-only reviews without closing pending work. Test two assessments, correction during review, stale assessments and `needs_more` with an empty `unresolved` array.

4. **[blocker] Sections 3.5, 4.6 and 5.3: deferred correction processing can leave an invalid resolution in force.** Only an effect row is written immediately; protective work waits for retries. On E13 failure, the fallback opens a task only when an assessment exists. A resolved measurement anomaly whose evidence is corrected can therefore remain resolved, particularly when it has no assessment. Evidence: [E15:65](docs/tdd/E15.md:65), [E15:273](docs/tdd/E15.md:273), [E15:631](docs/tdd/E15.md:631). **Required:** immediately record a durable invalidation state that blocks resolution and exposes pending review. Reopen resolutions whose directly recorded evidence is superseded without needing E13. Specify atomic, idempotent reconciliation and recovery of failed effects. Test every crash boundary and both correction-versus-resolution interleavings.

5. **[major] Sections 3.5 and 4.4: correction coverage excludes material evidence.** `correct_onset` explicitly never reopens or schedules assessment review. Observation corrections are handled only when the event carries this episode’s ID, although assessments can cite earlier observations and confirmed report findings. Evidence: [E15:367](docs/tdd/E15.md:367), [E15:506](docs/tdd/E15.md:506). The package permits reopening when “important evidence changes” ([CONTRACTS:117](docs/product/CONTRACTS.md:117)). **Required:** define reverse dependency lookup for every evidence type used by an assessment or resolution, including onset and report findings. Assign each producer and consumer explicitly. Replace T-E15-044’s unconditional “never reopens” assertion with material-change cases.

6. **[blocker] Sections 4.4 and 14: the asynchronous link fallback makes resolution guards unreliable.** A producer can commit an open plan or measurement request before E15 receives its event. During that interval, E15’s link-based guards can permit resolution using an unchanged episode revision. The fallback event list also supplies no observation, assessment or standalone gap event. Evidence: [E15:518](docs/tdd/E15.md:518); the public event vocabulary is enumerated in [CONTRACTS:985](docs/product/CONTRACTS.md:985). **Required:** make atomic producer notification an integration prerequisite, or revalidate authoritative producer facts transactionally before resolution. Define a truthful incomplete-projection state and recovery path. Test resolution between producer commit and subscriber delivery, including subscriber outage and restart.

7. **[major] Section 4.4: state values are not valid event identities.** Keys such as `(kind, ref_id, state)` suppress legitimate repeated transitions. A plan can return from `escalated` to `active` and escalate again; the second occurrence is discarded. Evidence: [E15:509](docs/tdd/E15.md:509), [E28:272](docs/tdd/E28.md:272). SYSTEM specifies durable subscriber deduplication by event sequence ([SYSTEM:465](docs/SYSTEM.md:465)). **Required:** use immutable event IDs or producer revision identities, store the last applied revision, and define out-of-order handling. Test repeated states, duplicates and older events arriving after newer ones.

8. **[blocker] Sections 4.4 and 14: link validation cannot enforce the stated identity invariant.** Several proposed events lack patient, mission or `origin_mode`; `AssessmentChanged.origin` means `model` or `reviewer`, not LIVE, REPLAY or SIM. Yet handlers must validate origin without consulting another module. They also lack an explicit patient and mission equality check. Evidence: [E15:501](docs/tdd/E15.md:501), [E15:1037](docs/tdd/E15.md:1037); the package makes provenance dimensions independent ([CONTRACTS:7](docs/product/CONTRACTS.md:7)). **Required:** define a complete trusted event envelope or an authorized transactional lookup, then check episode, patient, mission and origin together. Quarantine invalid associations while preserving valid source records. Test same-origin cross-patient and cross-mission links, not only SIM-to-LIVE links.

9. **[major] Sections 2, 3.6 and 14: authority and owner selection do not use the shared decision.** E15 requests `OfficerAuthority` from E11, while SYSTEM assigns `ClinicalAuthorityQuery` to E31. Automatic task ownership ignores availability and has no outcome when no non-patient officer exists. Evidence: [E15:63](docs/tdd/E15.md:63), [SYSTEM:903](docs/SYSTEM.md:903). The PRD says the second officer takes over when the first is “the patient or away” ([PRD:146](docs/product/PRD.md:146)). **Required:** consume the shared action-specific authority port, preserve assignment attribution, and define unavailable-owner behavior that neither invents authority nor aborts clinical input. Test incapacitation, no eligible officer, location separation, authority revocation and reassignment. Keep practice, assignment and clinical authorization separate, as audit finding 7 requires.

10. **[major] Sections 3.6 and 4.1: assigned follow-up owners cannot use their tasks.** An officer may assign a custom task to any roster person, but `ActOnEpisode` first denies any other crew member access to the episode. There is no task-scoped read or command interface. Evidence: [E15:283](docs/tdd/E15.md:283), [E15:371](docs/tdd/E15.md:371). The package permits an assisting crewmate to see “Only the accepted task and shared information” ([PRD:144](docs/product/PRD.md:144)). **Required:** specify assignment acceptance, minimal task visibility and authorized completion without chart access, or restrict ownership to actors who can actually perform the workflow. Test a non-officer owner and revoked assignment.

11. **[major] Sections 3.6 and 8: pending due times can never be set.** Tasks pin their due policy permanently, and the configuration test explicitly leaves an existing pending task’s due time null. No action sets or revises that task’s deadline. “To be set by clinical review” therefore promises an unavailable operation. Evidence: [E15:288](docs/tdd/E15.md:288), [E15:771](docs/tdd/E15.md:771). **Required:** add an attributed, revision-checked deadline-setting action with policy provenance and retained history. Define overdue behavior after rescheduling. Test a task created under a pending policy subsequently receiving a clinician-selected deadline.

12. **[major] Sections 3.4, 3.6 and 5.3: clock corrections have no defined behavior.** Review validity uses wall-time ordering, overdue status latches permanently after a notice, and task creation uses a different mission-clock interface. A forward jump followed by correction can leave a task falsely overdue; a backward jump can invalidate chronological evidence checks. Evidence: [E15:257](docs/tdd/E15.md:257), [E15:298](docs/tdd/E15.md:298). SYSTEM defines sequence ordering, `ClockCorrected`, `ClockRegressed`, versioned labels and scheduler rescheduling ([SYSTEM:181](docs/SYSTEM.md:181), [SYSTEM:535](docs/SYSTEM.md:535)). **Required:** adopt those mechanisms, use causal revisions for evidence ordering, and distinguish a historical overdue notice from current deadline status. Add forward/backward jump, restart and mission-clock correction tests.

13. **[blocker] Sections 4.1, 5 and 12: command durability is underspecified for retries and evaluator failures.** The action sequence checks mutable revisions without specifying prior idempotency lookup; only the short key store is named. Handler failures are universally described as storage failures that abort the producer. Evidence: [E15:369](docs/tdd/E15.md:369), [E15:501](docs/tdd/E15.md:501). SYSTEM requires lookup before mutable preconditions, a mission-life command ledger, and separate handling for evaluator and storage faults ([SYSTEM:495](docs/SYSTEM.md:495), [SYSTEM:955](docs/SYSTEM.md:955)). **Required:** use `CommandIdentity`, register episode actions as durable commands, and specify transactional result recording. Preserve valid input with pending reconciliation after non-storage processing faults. Test lost responses, retries after weeks, disk full, permanent handler faults and crash after acceptance but before UI acknowledgement. This addresses audit finding 9.

14. **[major] Sections 3, 5 and 14: accepted completion evidence and review corrections have no persistence design.** `complete_followup` accepts `evidence_ref`, but neither the task closure nor its storage records it. R-E15-6 proposes review supersession without defining its storage, current-head selection or effects on tasks and resolutions that relied on the old review. Evidence: [E15:362](docs/tdd/E15.md:362), [E15:594](docs/tdd/E15.md:594), [E15:1015](docs/tdd/E15.md:1015). CONTRACTS requires “completion evidence or cancellation reason” and retained correction lineage ([CONTRACTS:35](docs/product/CONTRACTS.md:35)). **Required:** specify immutable evidence references and review supersession chains, including concurrency and downstream invalidation tests.

15. **[major] Sections 5 and 11: bounded processing is claimed but not achieved.** The aggregate is described as bounded, while derivation accepts whole task/link sequences and the Episode response embeds task history. Proposed acknowledgments, reopenings and onset history are also unpaged. Sources can accumulate indefinitely. Exceeding the answer limit makes the episode unreadable. Evidence: [E15:158](docs/tdd/E15.md:158), [E15:218](docs/tdd/E15.md:218), [E15:779](docs/tdd/E15.md:779), [E15:989](docs/tdd/E15.md:989). **Required:** define bounded summaries and paginated histories, indexed derivation inputs, explicit capacity behavior and bounded reconciliation. Specify how every E13 call receives an enforceable timeout despite the synchronous protocol. Test long-lived episodes and saturation without losing record access.

16. **[major] Sections 2, 4.2 and 13: the port design is internally incompatible and diverges from SYSTEM.** One `EpisodeQueries` class is required to implement conflicting `facts`, `subject_of` and `visible` signatures. The E26 consumer now expects `EpisodeRefPort.visible(session, episode_id) -> bool`. E15 also retains `IdGenerator`, `TimerPort`, `AuditLog.append`, `MissionClock.day_end` and old bus signatures instead of the shared kernel interfaces. Evidence: [E15:394](docs/tdd/E15.md:394), [E15:421](docs/tdd/E15.md:421), [E26:408](docs/tdd/E26.md:408), SYSTEM sections 5.1 to 5.12. **Required:** use separate typed adapters or distinct methods and adopt `EpisodePort`, `SessionContext`, `IdFactory`, `ReadSnapshot`, `UnitOfWork`, `Scheduler` and shared configuration/error interfaces exactly. Add `module.py` registration and reconcile DTO import paths, table names and consumer contracts.

17. **[major] Sections 1, 6 and 13: E15 excludes a view it now owns.** The design delegates Records projection to an unspecified SYSTEM owner, but SYSTEM explicitly assigns `RecordsView` to E15. Evidence: [E15:74](docs/tdd/E15.md:74), [SYSTEM:141](docs/SYSTEM.md:141). **Required:** design `getRecordsView`, its authorized source ports, stable mixed-record pagination, configured title/detail rendering, degraded states, owned files and tests against `records-view.schema.json`. Update section 14 rather than leaving the responsibility unassigned.

18. **[major] Sections 6, 7 and 14: the proposed projections cannot deliver several promised displays.** The timeline stores and returns no attempt failure reason, and no read port supplies it. The gap schema has no claimed form-link field. Unanswered questions are declared as a port but never mapped into the episode screen. Error examples treat `field_errors` as a map, while its schema requires an array of `{field, code, message}`. Evidence: [E15:602](docs/tdd/E15.md:602), [E15:690](docs/tdd/E15.md:690), [E15:998](docs/tdd/E15.md:998); D08 requires the failed attempt to remain visible with its reason ([VALIDATION:163](docs/product/VALIDATION.md:163)). **Required:** provide exact source-to-response mappings and complete schema requests for these displays. Use the shared typed error mapping and schema-valid examples.

19. **[major] Sections 6 and 8: configuration-dependent commands ignore configuration concurrency.** E15 ignores `Config-Release` while `add_followup` applies the active release’s deadline policy. A release change can therefore alter the result of a form the user already reviewed. Evidence: [E15:669](docs/tdd/E15.md:669). The package requires a mismatch response for “a mutating request that depends on configuration under a different active release” ([CONTRACTS:214](docs/product/CONTRACTS.md:214)). **Required:** validate the rendered release for policy-dependent actions and read configuration through the transaction’s pinned handle. Define how the UI obtains the task’s pinned notice and words; those fields are absent from the proposed response. Reconcile the supported duration units, including `d`, and test activation during an open form.

20. **[major] Sections 7 and 9: optional failures can make the whole episode unavailable or silently stale.** An E13 read failure returns a whole-view 500. After adopting SSE, the design specifies stale handling for failed refetches but not stream loss, cursor expiry or authorization loss. Evidence: [E15:696](docs/tdd/E15.md:696), [E15:802](docs/tdd/E15.md:802). The package requires every screen to remain usable with the assistant unavailable ([USE-CASES:213](docs/product/USE-CASES.md:213)); SYSTEM requires clinical views to remain only in authorized reader memory. **Required:** serve durable episode facts with explicit unavailable components, fail closed only on dependent actions, and define reconnect, cursor recovery and cache clearing. Test component failure, silent stream loss and revocation while a view is open.

21. **[major] Sections 9 and 14: deployment assumptions contradict the completed deployment contract.** E15 proposes hub-prefixed IDs, treats merge handling as an open question, and suggests importing ground reviews as `ground` sessions on the crew hub. DEPLOYMENT specifies UUIDv7 IDs, retained divergent clinical versions and ground sessions only on ground nodes in flight deployments ([DEPLOYMENT:180](docs/DEPLOYMENT.md:180), [DEPLOYMENT:222](docs/DEPLOYMENT.md:222), [DEPLOYMENT:274](docs/DEPLOYMENT.md:274)). **Required:** map T0 through T7 explicitly, adopt home-node provenance and the conflict-record workflow, and preserve remote signature time separately from receipt time. Define authenticated review import without granting a flight-hub ground session. Test disconnected replicas, duplicate import and conflicting versions.

22. **[major] Sections 3.7 and 10: the ground-review requirement needs an operational correction.** The design correctly prevents automatic ground control, but provides no explicit path for an onboard person to accept, reject or turn received advice into attributable local work. A generic episode consent also risks exposing later live records beyond the approved snapshot. Evidence: [E15:310](docs/tdd/E15.md:310), [E15:386](docs/tdd/E15.md:386), audit finding 7. NASA explicitly supports routine private medical communication using store-and-forward under delay. [NASA medical operations, V1 6002 and V1 6003](https://www.nasa.gov/reference/6-0-medical-operations/). **Required:** propose a package clarification and a locally authorized advice-adoption workflow, linked to the delivered snapshot and review. Preserve complete offline operation and prohibit automatic clinical changes. Test advice arriving after correction, resolution or consent revocation.

23. **[major] Sections 12 to 15: acceptance evidence and integration gates are incomplete.** V38 concerns imported clinician diagnosis, not generic review attribution; V30 requires correction during inference; V35 requires recovery after acceptance and before UI update. The listed tests do not establish those scenarios. Parser and due-policy property tests, disk-full behavior, incapacitated-patient handling and clock-jump tests are missing. Evidence: [E15:903](docs/tdd/E15.md:903), [VALIDATION:50](docs/product/VALIDATION.md:50). SYSTEM also assigns hub validation to `scripts/validate_hub.py`, contract copies to `contracts/api/`, and interim execution to `uv run --project hub` ([SYSTEM:594](docs/SYSTEM.md:594)). **Required:** supply a complete ownership-and-test trace matrix, add the fault and boundary tests above, update commands and owned evaluation paths, and make coverage, mutation and traceability checks executable gates. File the section 14 proposals in `docs/requests/E15.md` and identify which approvals are prerequisites for each work package’s acceptance.

Questions for the user

- What clinical authorization limits should apply when an acting medical officer records a clinical review or a `clinician_assessed` resolution? SYSTEM explicitly authorizes acting officers for urgency disposition, but does not settle these two actions.
