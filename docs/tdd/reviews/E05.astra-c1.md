VERDICT: GREENLIGHT

1. **[major] Sections 3 to 5: request revision updates are underspecified.** [E05:254](docs/tdd/E05.md:254) explicitly increments revision for submit, accept and decline. The following start, cancel and recordAttempt rows omit that obligation. This matters especially for a quarantined attempt appended to a terminal request: its state remains unchanged, but its public representation changes. Meanwhile, the UI rejects older revisions ([E05:407](docs/tdd/E05.md:407)), and CONTRACTS.md:1111 requires revision increments on every object change.
   
   **Required change:** Specify one revision increment for every committed change to the request representation, including attempt additions without state changes. Exact duplicate replay must not increment it. Add tests for start, cancel, terminal late arrivals, duplicate attempts and concurrent If-Match actions; assert matching GET ETag and event revisions.

2. **[major] Sections 2 and 4: resolved-episode handling does not clearly match E15.** [E05:247](docs/tdd/E05.md:247) prevents new work on a resolved episode without its “explicit reopen path”; R-E05-1:35 requires reopening before new work. However, [E15:1071](docs/tdd/E15.md:1071) explicitly permits producers to create work on resolved episodes and says no producer refuses it. E15:509 reopens through the new measurement-request link. These descriptions leave builders choosing between a prerequisite reopen command and reopening caused by request creation.
   
   **Required change:** State the exact ordering and transaction boundary. Align with E15’s authorized new-link reopening in the producer UOW, while continuing to reject unknown or unauthorized episodes. If a different behavior is intended, describe it explicitly as a proposed change in R-E05-1 rather than attributing it to the existing E15 agreement. Add an integration test starting from a resolved episode.

3. **[major] Section 2: the current E30 acquisition protocol has not been reconciled.** [E05:157](docs/tdd/E05.md:157) says E30 has no current design. It does. E30:416 selects a camera reference window instead of a MeasurementRequest; [E30:448](docs/tdd/E30.md:448) binds that window to a guided check and attempt number. Its manual observation is written through E01. In contrast, R-E05-2:61 requires request ID, acquisition ID and generation for E05’s attestation, while merely saying that E30 supplies its operator and sample at line 78. The relationship between these identities and acceptance lifecycles remains undefined.
   
   **Required change:** Update the seam inventory and R-E05-2 using the existing E30 design. Specify the proposed binding for guided-check acceptance, manual observations and camera reference windows, including cancellation and retained late evidence. Preserve the manual count when the camera is unavailable. Keep incompatible bindings disabled until agreement, without importing E30’s superseded kernel interfaces.

4. **[major] Sections 12 and 12.1: T-E05-14 does not establish the claimed V87 coverage.** [E05:570](docs/tdd/E05.md:570) covers disagreement, retry and prevention of diagnosis, gap closure and skill awards. V87 specifically requires a camera returning no reading, retention of the count, an unchecked label and exclusion from supporting evidence ([VALIDATION:107](docs/product/VALIDATION.md:107)). Those are distinct assertions. E12:177 explicitly owns exclusion of unchecked results from support, but the acceptance row names only E06/E14/E30.
   
   **Required change:** Add the no-reference case explicitly. Assign the unchecked presentation to E30, provenance retention to the recording integration, and support exclusion to E12/E13. Name the counterpart tests and require an integration assertion that the retained count cannot become supporting evidence.

5. **[major] Section 15: the coverage command does not enforce the required branch threshold.** [E05:681](docs/tdd/E05.md:681) applies `--cov-fail-under=95` to the entire measurement package. That threshold measures combined statement and branch coverage, including adapters. It does not establish 95% branch coverage for domain and application code, as required by BUILD-CHARTER.md:136. A read-only calculation using the installed coverage library confirmed that 90 covered statements and only 6 of 10 covered branches produce a passing combined score of 96%.
   
   **Required change:** Add an explicit branch-only check scoped to domain and application code, or bind to a shared gate that demonstrably enforces it. Retain the separate full-condition safety checks. The documentation lint passed with zero findings, but it does not verify this gate’s semantics.
