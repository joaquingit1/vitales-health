VERDICT: CHANGES REQUESTED

1. **[blocker] Section 3.8: evaluating once per channel after the batch can erase an emergency crossing.**

   **Problem:** The safety result depends on how the adapter groups otherwise identical ordered readings into HTTP
   requests. Once R-E23-2 supplies the required plausibility criteria, a batch containing an eligible oxygen reading
   below the emergency limit followed by an eligible normal reading evaluates only the latter. The first reading is
   stored but its emergency is never raised. Likewise, an intermediate reading that interrupts a clearing condition
   can disappear from the evidence delivered to E24. Disabling evaluation pending R-E23-2 does not repair the
   algorithm that is to be enabled afterwards.

   **Evidence:** `docs/tdd/E23.md:365` says, "After the loop, each touched channel is aggregated and evaluated once".
   `docs/tdd/E23.md:281` makes E the latest eligible observation, and `docs/tdd/E23.md:310` explicitly requires the
   `latest` oxygen limit to cross on one reading. `docs/product/api/examples/config/sensor-limits.example.json:173`
   defines `o2_low_emergency` with `aggregation_id=latest` and a clearing dwell. `docs/product/CONTRACTS.md:688`
   requires evaluation after each accepted reading; `docs/product/CONTRACTS.md:706` requires continuous clearing
   evidence. T-E23-063 at `docs/tdd/E23.md:1000` tests only the single-reading case and cannot catch this loss.

   **Required change:** Evaluate after each accepted reading in ingest order, applying the existing time, freshness,
   quality and non-advancement rules. Retain a distinct immutable input revision and historical membership for each
   evaluation through SYSTEM 5.10.2, and deliver every resulting safety input to E24 in order within the producer
   UOW. Do not let a later row replace an earlier input before its evaluation. Keep coalescing limited to the
   contracted presentation event throttle in section 4.3. Add a real HTTP/composition-root/SQLite regression using
   the same ordered stream as one batch and as separate requests: emergency then normal before the clear dwell,
   interrupted clearing, duplicate retry, and computation failure on the intermediate input. Compare warning
   history and pending evidence, not merely the final card. Use the configuration's approved values and shared
   isolation; do not invent a new retry or transaction mechanism.

2. **[blocker] Section 3.8: whole-body model validation rejects good readings when one row is malformed.**

   **Problem:** The preliminary validation prevents the promised per-index handling from running. A JSON-valid batch
   with one valid reading and one reading whose `adapter_sequence` is negative is rejected in full, so the valid
   reading, potentially an emergency input, is neither captured nor evaluated. This directly contradicts the ingest
   contract and the design's own acceptance test.

   **Evidence:** `docs/tdd/E23.md:335` requires any body failing `AdapterReadingBatch` to return HTTP 400 before the
   reading loop. The model validates individual rows, including the nonnegative sequence constraint at
   `docs/product/api/schemas/requests.schema.json:1848`. Both `docs/product/CONTRACTS.md:664` and
   `docs/product/api/openapi.yaml:2425` forbid rejecting the whole batch for one bad reading. T-E23-027 at
   `docs/tdd/E23.md:964` therefore cannot pass for this case. A read-only schema probe confirmed that the unmodified
   `value` in `docs/product/api/examples/requests/adapter-batch.json` has zero validation errors; appending a copy
   with `adapter_sequence=-1` produces an error solely at `readings/1/adapter_sequence` and invalidates the batch.

   **Required change:** Separate bounded JSON/envelope validation from generated per-reading validation. Reserve
   whole-request rejection for invalid JSON, an invalid envelope, authentication failures and whole-request bounds.
   Validate each row against its generated schema, retain the bounded rejected input with its index, and continue
   processing valid rows in order in the same UOW. Specify the existing per-index error codes and all required
   rejection fields, including `message` from `docs/product/api/schemas/ingest-result.schema.json:81`; section 3.8
   currently lists only index and code. Extend T-E23-027 with valid rows before and after an invalid sequence,
   missing required field and invalid enum, plus retry and crash boundaries. Preserve boundary validation rather
   than making the reading model permissive. If E01's generated request binding cannot support per-item admission,
   have the author extend R-E23-12 with that concrete binding requirement before implementation.

3. **[major] Sections 4.2 and 4.3: the E24 payload names do not define a buildable public event boundary.**

   **Problem:** A coder is told to use E24's exact input types but is not told which allowed application port exports
   them, how the bus event wraps them, or how a mission event's reported type differs from its bus discriminator.
   Importing E24's stated type locations directly breaks module independence; copying those classes creates a second
   contract. This is an unresolved ownership and representation choice, not permission to pick either approach.

   **Evidence:** `docs/tdd/E23.md:502` requires the exact `SensorEvaluatedInput`, `FreshnessInput`, `MissionEventInput`
   and `StateFactInput` payloads from E24 4.3. That section places them in `rules/domain/inputs.py`
   (`docs/tdd/E24.md:615`). They are input DTOs, without the `DomainEvent.event_type: ClassVar[str]` required at
   `docs/SYSTEM.md:581`; `MissionEventInput.event_type` is instead an instance field for the reported mission event
   (`docs/tdd/E24.md:645`). SYSTEM 6.4 permits cross-module imports only through application ports
   (`docs/SYSTEM.md:1689`). R-E23-5 at `docs/requests/E23.md:65` requests time and quantity agreement but does not
   specify this event/export binding.

   **Required change:** Agree the event/export boundary with E24 and record it in R-E23-5. Specify the producer-owned
   bus event types and their public application-port exports, the fixed bus discriminators separately from mission
   event payload fields, and E24's mapping into its private domain inputs. State exact field correspondence without
   creating duplicate shared DTOs or importing another module's domain. Extend T-E23-049 to type-check and dispatch
   the actual exported events through the shared bus, including mission-event routing, and run the generated import
   contracts on both sides. Existing clock, snapshot and quantity requests remain necessary.

4. **[major] Section 5.1: local mutation accounting is deferred even though SYSTEM already defines it.**

   **Problem:** The design leaves builders waiting for a shared mechanism that now exists. Mission initialization,
   overlays, notes and operational indexes still need concrete local mutation declarations to satisfy the commit
   invariant. Calling them local does not supply those declarations.

   **Evidence:** `docs/tdd/E23.md:594` delegates the non-exportable declaration to R-E23-20, whose reason still calls
   the mechanism missing (`docs/requests/E23.md:225`). `docs/SYSTEM.md:711` explicitly defines
   `ReplicationChange.export_projection=None`: it records local recovery accounting and advances the scan cursor
   without recipient delivery. The same paragraph prohibits private plaintext in that log. Every repository mutation
   must declare its change or fail commit (`docs/SYSTEM.md:722`).

   **Required change:** Adopt SYSTEM 5.7's existing local-only declaration in section 5.1 and have the author mark
   R-E23-20 answered by that mechanism. Specify the safe reference-only declarations for private/person-linked rows
   and the local audiences required by their events/tasks. Keep the two approved export projections narrow. Extend
   T-E23-089/091 to prove that these local writes commit, produce no recipient delivery or private plaintext in the
   recovery log, and still fail atomically when their required accounting cannot be persisted.

5. **[major] Section 15: Python gates select the engine project instead of E23's member toolchain.**

   **Problem:** The unit, acceptance, hardware and mutation commands do not select the standalone hub environment.
   Their success depends on unrelated root installation and configuration. This is not an executable handoff for
   the workspace that SYSTEM currently specifies.

   **Evidence:** `docs/tdd/E23.md:1230`, `docs/tdd/E23.md:1231`, `docs/tdd/E23.md:1234` and
   `docs/tdd/E23.md:1235` use root `uv run` for E23 Python tests and mutations. SYSTEM 6.2 explicitly requires hub
   gates to use `uv run --project hub` and member-specific configuration (`docs/SYSTEM.md:1666`). The current root

   marker (`pyproject.toml:34`). The all-repository Ruff command at `docs/tdd/E23.md:1227` likewise does not establish
   that E23's member configuration is selected.

   **Required change:** Rewrite each E23 gate to select its declared uv member and that member's tool configuration;
   explicitly select the hub pytest configuration for commands spanning hub, adapter and eval paths. Keep engine
   contract validation separate. Ensure mutation execution and its score checker share the intended environment,
   and lint/type-check the adapter with its own declared member configuration. Have the E01/toolchain owner supply
   any missing registration before the commands become implementation gates. Do not edit root engine configuration
   or weaken marker checks to make these commands run.
