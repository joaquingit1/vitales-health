VERDICT: CHANGES REQUESTED

1. [blocker] Sections 3.1, 3.6 and 10: The privacy guard does not enforce the promised patient-data boundary. Private clinical text without a roster name, known ID, MET stamp or denylisted phrase passes G1 to G5. Conversely, blocked text is retained in `DiscoveryQuery.text` and the shared research archive, readable by editors. [E19:106](docs/tdd/E19.md:106), lines 277 and 549 to 553, specify this behavior. The package says the workspace receives “a generalized research question, not patient identifiers or private clinical text” ([LLM-ARCHITECTURE.md:106](docs/product/LLM-ARCHITECTURE.md:106)). Required change: define a constrained, public-evidence query construction path, validate the entire outbound request, and retain only safe rejection metadata for blocked submissions. Test private narratives and unfamiliar identifiers without preloading their contents into the denylist, including absence from archives and logs.

2. [blocker] Sections 4.1, 4.2 and 5.2: File and URL ingestion bypass the claimed structural isolation. `ImportDiscoveryFile` and `ImportCapture` accept filesystem paths; fetch and link-check adapters accept URLs without a public-destination restriction. An import dependency rule cannot prevent reading a journal export or adjacent benchmark file, and HTTP-only validation does not exclude localhost or private services. See [E19:328](docs/tdd/E19.md:328) and lines 423 to 435. The package requires patient attachments to stay outside the global corpus ([LLM-ARCHITECTURE.md:74](docs/product/LLM-ARCHITECTURE.md:74)) and V33 explicitly tests a hidden target in an adjacent file. Required change: specify approved import roots, path and symlink containment, isolated extraction permissions, and destination validation on every fetch and redirect. Add filesystem-boundary and private-address tests using the actual adapters.

3. [blocker] Sections 3.1 and 5.1: The query state machine cannot be persisted using the specified table. Queries transition from `sent` to `succeeded` or `failed`, adding response hashes and error information, but the single-row `workbench_query` table forbids every update and delete. Evidence: [E19:103](docs/tdd/E19.md:103), lines 404 and 414. Required change: define append-only query transition/attempt records with a current-state projection, or a mutable projection backed by immutable history. Specify restart handling for an interrupted request and an explicit outcome when no response was received. Test successful, failed, cancelled and interrupted requests against the stated constraints.

4. [blocker] Sections 4, 5, 9 and 12: Accepted records have no defined atomic commit or recovery protocol. E19 writes reviews and approvals, invokes E10 transitions, archives blobs and calls E01 audit services, but never specifies which writes commit together. Documentation outputs also lack an atomic publication mechanism despite the promise that the previous release remains published. The package requires: “One command is one transaction: the state change, the audit event and the outbox entry commit together” ([CONTRACTS.md:1108](docs/product/CONTRACTS.md:1108)). Required change: specify transaction ownership across E19/E10/E01, durable blob ordering, idempotency-result persistence, audit chaining, startup reconciliation and atomic documentation activation. Add crash and disk-full tests at each boundary, proving no acknowledged record disappears and no partial release becomes visible.

5. [major] Sections 3.1, 4.2 and 14.1: Concurrency and command identity are inconsistent. Most state-changing use cases omit expected revisions; activation omits the revision required by E10. Promotion deduplication excludes `dry_run` and other build inputs, while capture/extraction use content hashes without defining object scope. Query IDs omit the actor and depend on timestamps, allowing identical simultaneous requests to collide. See [E19:325](docs/tdd/E19.md:325). The package requires optimistic concurrency and says the same idempotency key with a different body returns `409 DUPLICATE_COMMAND` ([CONTRACTS.md:203](docs/product/CONTRACTS.md:203)). Required change: distinguish command identity from content deduplication, specify complete key scopes and payload hashes, and carry expected revisions through API and CLI use cases. Test concurrent approval/withdrawal, dry-run followed by promotion, retries after restart, and clock jumps.

6. [blocker] Sections 3.2, 3.3, 3.5 and 12: Reviews are not bound tightly enough to the content they approve. `ClaimReview` references only a stable `claim_id`; `UseApproval` does not pin the supporting reviews or extraction hash. The design allows claim-file edits and review corrections without defining which verdict remains effective or when dependent approvals become invalid. Publication checks only resolvable references and nonempty limitations, so an unsupported claim can satisfy the documented gate. See [E19:155](docs/tdd/E19.md:155) and tests T-E19-14, 15 and 21. The package states, “Approval belongs to a version and purpose” ([CONTRACTS.md:129](docs/product/CONTRACTS.md:129)). Required change: bind reviews to immutable content revisions, define correction and revocation precedence, and specify admissible publication verdicts and qualifications. Test content edits after approval, superseded passing reviews, and publication of contradicted claims.

7. [major] Sections 3.3 and 3.4: The scalar review workflow does not implement approval by purpose. A document approved for `risk_context` can no longer take the specified `technically_checked → clinically_reviewed` edge to obtain `patient_instruction` approval. The design also does not resolve how superseding one use affects other still-approved uses. Evidence: [E19:194](docs/tdd/E19.md:194). The package explicitly permits branching approval by purpose ([CONTRACTS.md:129](docs/product/CONTRACTS.md:129)). Required change: agree with E10 on independent review facts and per-use approval/supersession state, with a defined aggregate display status. Request the shared change in section 14 and test adding a second use, rejecting one use, and superseding only one use.

8. [major] Section 3.3: Extraction checks the wrong completeness property. It rejects items whose “completeness ceiling” is `catalog_only`, `summary_only` or `inaccessible`. E10 defines that field as the strongest provenance available **without a blob**; a subsequently fetched full document can therefore remain blocked by its original discovery classification. Compare [E19:193](docs/tdd/E19.md:193) with [E10:220](docs/tdd/E10.md:220). The package ingestion sequence requires discovery followed by full capture and extraction ([LLM-ARCHITECTURE.md:78](docs/product/LLM-ARCHITECTURE.md:78)). Required change: distinguish catalog provenance from the captured version’s completeness and define the evidence required to advance it. Test a catalog-only discovery followed by a full capture, while proving that a search summary alone remains ineligible.

9. [major] Sections 2, 3.2 and 4: The E10 integration cannot carry the promised review results. A discrepancy has an unordered `passage_ids` collection, without explicit superseded/current endpoints. E10’s `build` signature accepts approvals but no discrepancies, and E19 provides no review-read port. Withdrawal also lacks a specified conversion into E10’s `ApprovalInput.withdraws` and `reason`. See [E19:155](docs/tdd/E19.md:155), [E10:353](docs/tdd/E10.md:353) and [E10:504](docs/tdd/E10.md:504). V24 requires version/applicability enforcement and a visible discrepancy ([VALIDATION.md:44](docs/product/VALIDATION.md:44)). Required change: specify exact typed mappings and ports for approval evidence, withdrawals and directed discrepancy pairs. Include repository methods instead of `WorkbenchRepository(Protocol): ...`, and test the integration without reading another module’s tables.

10. [major] Sections 4.2, 5.1 and 6: `addResearchSource` has no defined durable home for all contracted fields. E10 catalog registration retains source identity, titles and URLs, but its mutation ports do not accept `date` or `access`; E19’s tables contain no source-registration record. Registry sources can also have null metadata, while the response schema requires nonempty strings. Compare [E19:444](docs/tdd/E19.md:444), [E10:147](docs/tdd/E10.md:147) and [research-source.schema.json:19](docs/product/api/schemas/research-source.schema.json:19). Required change: define the owning store and port for complete source metadata, merge precedence across registry/catalog/releases, and an explicit contract-compatible representation of unknown metadata. Test create, restart and list round-trips without fabricated dates or access descriptions.

11. [major] Sections 1, 3.5, 8 and 15: The documentation release does not cover the package’s required contents or distinguish incomplete verification from publication readiness. Its named outputs cover the annex, sources, conditions and counts; other mandatory documentation has neither a navigation contract nor an assigned owner. Offline link checks still produce a `built` release. [RESEARCH-ANNEX.md:138](docs/product/RESEARCH-ANNEX.md:138) requires architecture diagrams, adapter manuals, schema/migration references, model/data/evaluation cards, deployment/recovery instructions, privacy behavior and a capability manifest, among other items. E19-03 requires “links and licenses checked” ([backlog.json:810](docs/product/backlog.json:810)). Required change: enumerate each required item, its owning epic and versioned input, then define release completeness and verification gates. Offline previews may remain available, but incomplete checks must not satisfy the publication acceptance criterion.

12. [major] Sections 2, 4.1 and 14.6: Coverage and evaluation outputs lack reproducible derivation rules. `latest_results()` and the six count names do not define eligible runs, condition populations, denominators, release compatibility, aggregation or evidence references. A result from an older corpus could consequently be presented beside current coverage without a defined qualification. See [E19:312](docs/tdd/E19.md:312). The package requires separate coverage counts and qualified clinical-review claims ([VALIDATION.md:209](docs/product/VALIDATION.md:209)); V80 requires every number to trace to a result artifact with its denominator. Required change: provide exact schemas and formulas, pin configuration/evidence/run hashes, define environment-specific kit counts, and distinguish zero from unmeasured. Test missing, partial, failed and incompatible runs. Resolve the proposed `KitMapPort` with E27’s actual application interface.

13. [major] Sections 5.2, 9 and 11: Resource bounds do not establish failure containment. `Retry-After` has no maximum, HTTP read timeouts do not define a total operation deadline, imports and extracted output lack byte/item bounds, and archive growth has no quota or exhaustion policy. Background priority alone does not establish that hub safety operations remain responsive. See [E19:421](docs/tdd/E19.md:421). The charter requires bounded work and timeouts ([BUILD-CHARTER.md:90](docs/BUILD-CHARTER.md:90)), and PRD section 11 requires help within 500 ms under load. Required change: define total deadlines, capped retry delays, bounded parsing/output, disk admission limits, cancellation latency and worker recovery. Test slow streaming responses, excessive retry delays, oversized inputs and worker failure while help and record entry operate with optional components unavailable.

14. [major] Section 8: Configuration is neither complete nor safely activated. Queue size, timeout/retry values, rate limits, extraction limits and polling cadence are specified outside the named policy fields. The loader description omits version pinning, atomic activation and retention of the last valid document. `claims.json` and templates also lack explicit schema/validation contracts. Evidence: [E19:497](docs/tdd/E19.md:497). The package requires engines to read numbers and words from configuration ([CONTRACTS.md:439](docs/product/CONTRACTS.md:439)); [AGENTS.md:89](AGENTS.md:89) requires atomic validation and last-good retention. Required change: name every configuration field and provenance source, distinguish build policy from runtime configuration, specify loader ownership and snapshot pinning, and add the missing configuration proposals to section 14. Test corrupt updates and policy changes during running jobs.

15. [major] Sections 6, 14 and 15: The contract requests and build dependencies are incomplete. Request 14.1 omits used errors including `CAPTURE_OFF`, `REVIEW_INCOMPLETE`, `REASON_REQUIRED`, `SUPERSEDE_INVALID` and `EXTRACTION_TIMEOUT`. Request 14.4 adds job kinds but does not address editor cancellation: the existing cancel operation permits only crew, medical officer and operator ([openapi.yaml:5576](docs/product/api/openapi.yaml:5576)). Phase A also requires new UI copy and job behavior despite claiming to need only the existing contract and E10. Required change: supply complete operation IDs, request/response schemas, error mappings, authorization rules and prerequisites. Reconcile the charter’s RFC 9457 requirement with the package’s closed error envelope through an explicit request, preserving the package shape meanwhile. Define safe interim behavior for every pending dependency.

16. [major] Sections 13 and 15: Ownership is not disjoint, and the validation handoff has no owned destination. E19 claims files under `knowledge/policy/` and `knowledge/schemas/` ([E19:625](docs/tdd/E19.md:625)), while E10 claims both directories recursively ([E10:977](docs/tdd/E10.md:977)). E19 also runs an `eval` gate without owning an evaluation path or naming the receiving owner, and that gate does not account for its claimed V22 and V80 contributions. Required change: request exact ownership carve-outs, assign the integration scenarios and shared gate/configuration changes, and name the evidence required from other epics. Preserve the complete E19-01 to E19-03 acceptance mapping across both build phases.
