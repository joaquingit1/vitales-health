VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.4, 3.6 and 14: manual-input provenance and patient routing are incorrect.**  
   E30:315 to 324 derives the felt count's origin from the camera and stores it on the SIM persona when no camera exists. Camera availability does not determine whether a person's wrist is real. Furthermore, routing `patient_id` to the demo operator leaves `episode_id` pointing at the persona's episode. The package states: “LIVE means acquired from a real source” ([CONTRACTS.md:11](docs/product/CONTRACTS.md:11)) and “the beats and the camera reading are the presenter's and go to the demo-operator record” ([CONTRACTS.md:1336](docs/product/CONTRACTS.md:1336)).  
   **Required:** establish manual-input origin and actual subject independently of the reference camera. Route or reject every linked object consistently, including Answers, episodes, camera requests, events and plan references. Replace X16's conflicting interim behavior. Test absent cameras and every LIVE/REPLAY/SIM pairing.

2. **[blocker] Sections 3.2, 3.8, 9 and 12: an interrupted count becomes a fabricated full-window rate.**  
   The finish guard at E30:219 accepts any contiguous prefix containing at least one beat. Thirty accepted beats followed by an outage pass that guard and become 30 beats/minute over the nominal 60 seconds. T30-16 explicitly expects finish to work after a mid-count crash. Sequence gaps cannot detect a lost suffix, and the UI only enables Beat after the start response, although timing starts before the camera call. This violates the charter's “insufficient samples stay insufficient” rule ([BUILD-CHARTER.md:30](docs/BUILD-CHARTER.md:30)).  
   **Required:** define how full-window capture is established. Interrupted or uncertain attempts must remain incomplete and offer a fresh count or explicit manual alternative. Add tests for lost final taps, delayed start responses, disconnects, reloads and hub downtime.

3. **[blocker] Sections 3.2, 4.2 and 6: beats have no attempt identity.**  
   E30 resets sequences on retry but accepts beats using only sequence, session and current window. A delayed request from the previous attempt can enter the new attempt or collide with its legitimate beat. The package request contains only `sequence` and `client_time` ([requests.schema.json:1509](docs/product/api/schemas/requests.schema.json:1509)); this limitation is not requested in section 14.  
   **Required:** request an attempt token returned at count start and required on beats, or specify another provably unambiguous protocol within the contract. Define duplicate handling before expiry and capacity checks. Test delayed previous-attempt packets, reordered delivery, duplicate requests with new command keys, and concurrent taps.

4. **[major] Sections 3.8, 4.1 and 12: a non-decreasing UTC clock does not protect count duration.**  
   E30:367 guarantees only non-decreasing time within one process. It permits a forward jump that ends a count immediately, a backward correction implemented by freezing time, and discontinuity after restart. T30-07 does not inject these faults despite claiming H11 coverage. The package requires clock corrections to be recorded and prohibits silently replacing UTC with monotonic time ([CONTRACTS.md:9](docs/product/CONTRACTS.md:9)).  
   **Required:** specify separate elapsed-time and UTC semantics, clock-generation changes, worker-to-hub timestamp uncertainty, restart handling and mission-clock ownership. Define when uncertainty invalidates an attempt. Add forward/backward jump, suspension, reboot and camera-clock drift tests.

5. **[blocker] Sections 4.1, 4.2 and 10: authorization does not validate the complete clinical context.**  
   The listed guards do not require the requested subject to match the plan's subject, the helper to match the role assignment, or helper and subject to belong to the drill. A crew member can nominate themselves as helper to obtain another person's check; station sessions can read any active check. No consent or task-acceptance mechanism establishes that access. The package says “Client/model-supplied IDs are not authorization” ([CONTRACTS.md:145](docs/product/CONTRACTS.md:145)).  
   **Required:** specify authoritative relationship and permission checks for every supplied ID, including reads, camera acquisition and event delivery. Bound station access to an authorized task and define the incapacitated-subject path. Add adversarial tests using valid IDs from different patients, plans, roles and drills.

6. **[blocker] Sections 3.4, 4.2 and 5.1: drill persistence rules contradict the command procedure.**  
   I30-10 prohibits persistent drill measurements, but the finish procedure at E30:484 to 489 unconditionally writes an attempt, Observation, Answer and event. Selecting an ephemeral GuidedCheck repository does not suppress `RecordsWriter`, audit, outbox or idempotency-response writes. The package explicitly states that drills “never touch health records” ([CONTRACTS.md:1379](docs/product/CONTRACTS.md:1379)).  
   **Required:** define a complete drill execution policy covering every persistence sink and camera call. Specify ephemeral idempotency behavior after expiry and restart, plus races with drill completion. Make T30-10/T30-21 inspect WAL, idempotency, audit, outbox and worker stores as well as teach tables.

7. **[blocker] Section 3.4: the proposed Answer cannot satisfy the shared schema.**  
   E30:286 to 289 invents `skill:<skill_id>:step:<step_no>` as the question code. `Answer.question_id` references `config_id`, whose pattern is `^[a-z][a-z0-9_]{0,63}$`; colons are invalid ([answer.schema.json:11](docs/product/api/schemas/answer.schema.json:11), [common.schema.json:12](docs/product/api/schemas/common.schema.json:12)). The package also records the Answer on `answer`, whereas E30 defers it to finish. Its claimed superseding Answer cannot exist after a disagreement that wrote no Answer.  
   **Required:** define a valid, configuration-backed question identity and exact Answer mapping. File the timing, cancellation and supersession discrepancy in section 14, then make the state machine, transactions and T30-19 consistent with the agreed behavior.

8. **[major] Sections 3.3 and 6: the pending-tolerance path produces an invalid response.**  
   E30:735 copies the catalog tolerance directly. The catalog permits `tolerance.value: null`, but the GuidedCheck response requires a number whenever `tolerance` is an object ([config-skills-catalog.schema.json:448](docs/product/api/schemas/config-skills-catalog.schema.json:448), [guided-check.schema.json:274](docs/product/api/schemas/guided-check.schema.json:274)).  
   **Required:** add an explicit contract request and define a valid interim projection, such as a null tolerance with an appropriate configured explanation. Test all five operations with pending tolerance, including finish after its transaction commits.

9. **[major] Sections 3.3 to 3.5 and 5.2: numerical and unit handling is incomplete.**  
   The agreement function subtracts raw values without checking compatible units. Worker rates cross the port without a unit-bearing quantity. An “exact decimal string” cannot represent every permitted rational rate: one beat in seven seconds is `60/7`. CPR formatting also hardcodes zero decimal places at E30:305. The package permits arbitrary positive integer count durations and requires decimal counts and units to come from configuration ([CONTRACTS.md:439](docs/product/CONTRACTS.md:439)).  
   **Required:** define finite, dimensionally validated quantity types, conversion ownership, reference-unit compatibility, and configured serialization/rounding rules. Add properties for non-terminating ratios, incompatible units, non-finite inputs and extreme values. Name the configuration field controlling CPR display precision.

10. **[blocker] Sections 3.5 and 7: stale CPR feedback can remain displayed as current.**  
    E30 handles worker silence only while the coordinator continues ticking. `CoachingLine` displays the latest stored sample with no expiry rule. Hub failure, SSE loss or job termination can leave “in range” or “push faster” visible indefinitely. Delayed raw samples are also accepted without an age check. This violates “stale or offline readings never shown as current” ([BUILD-CHARTER.md:108](docs/BUILD-CHARTER.md:108)).  
    **Required:** define freshness at ingest and display, configured expiry, disconnect behavior, replay ordering and terminal clearing. Add any missing wire fields through section 14. Test hub death, delayed samples, reconnect replay and expired history while preserving the fixed help steps.

11. **[major] Sections 4.2, 5.1 and 11: coaching job recovery and contention are undefined.**  
    Job IDs depend only on session and check; subsequent starts are no-ops. The design does not explain re-entering the flow, restarting the hub, recovering an unavailable camera, or handling two sessions competing for the single worker job. The 60-minute stop also lacks a continuation or visible terminal behavior. The package requires coaching while the qualifying flow is active ([CONTRACTS.md:1340](docs/product/CONTRACTS.md:1340)).  
    **Required:** specify a job state machine, generation identifiers, restart reconciliation, idempotent start/stop behavior and deterministic resource arbitration. Define bounded continuation and visible refusal when capacity is unavailable. Test each transition and failure.

12. **[major] Sections 5.3 and 8: the compression quality gate is not sufficiently specified to implement.**  
    `CompressionGate` has no exact type, values, schema or validator. Parameters are deferred until the venue protocol. Missing-frame handling, irregular sampling, zero-variance normalization, peak ties, subject tracking and unsupported camera geometry are unspecified. The brief explicitly requires the TDD to settle the quality gate ([package tdd/E30.md:15](docs/product/tdd/E30.md:15)).  
    **Required:** freeze a versioned gate specification with provenance, bounds and refusal behavior. Define the supported geometry and signal-processing details, including range, saturation, stuck-input and rate-change checks required by AGENTS.md. Until validated settings exist, return no measurement. Add fault and property tests beyond clean sinusoids.

13. **[major] Sections 6 to 8: configuration pinning cannot survive a client reload or release change as designed.**  
    The client reads “the pinned catalog step,” but GuidedCheck exposes no catalog version or configuration pins. E30 pins only three documents, although teaching also reads responder flows and landmarks. The client-side template interim contradicts “The hub renders every template that needs hub state” ([CONTRACTS.md:548](docs/product/CONTRACTS.md:548)). Ignoring `Config-Release` on creation also conflicts with the general rule at CONTRACTS.md:214.  
    **Required:** define one atomic configuration snapshot and how every consumer retrieves it. Extend X1 to cover all required rendered content or pin identifiers. Specify coaching pins and runtime loader checks. Resolve the create-header discrepancy explicitly. Test release activation, cold client reload, missing cached versions and corrupt updates preserving the last good release.

14. **[major] Sections 7, 8 and 14: the stated interim implementation omits required R51 behavior.**  
    The bleeding question and eye-rinse timer are removed, and essential controls render “unknown.” The package specifically requires “Is it still soaking through?” and “a timer for the 20 minutes” ([PRD.md:361](docs/product/PRD.md:361)). Recording requests does not make those omissions an acceptable completed implementation. CPR teaching entry is also unclear because creation rejects skills without a count-agreement check, while `TeachOnlyViewer` is described for skills without any check.  
    **Required:** make X2 to X4 and X6 explicit delivery blockers with complete schema proposals and acceptance tests. Specify executable teaching entry paths for all five skills, including CPR drills and the bleeding region.

15. **[major] Sections 7 and 8: the clinical review notice has no rendering contract.**  
    The catalog declares an unreviewed notice, but no component or UI test requires it to appear. The schema says the notice is “Shown on every page that renders this document's clinical content” ([config-skills-catalog.schema.json:15](docs/product/api/schemas/config-skills-catalog.schema.json:15)). An Experimental tag describes a different limitation.  
    **Required:** specify notice and provenance rendering on the guided screen, teach-only viewer, drill view and embedded coaching presentation, including offline mode. Add UI tests for these surfaces.

16. **[major] Section 3.2: cancellation from retry violates the response invariant.**  
    The cancel transition retains the previous outcome unless an unspecified action clears it. Cancelling after disagreement therefore leaves `result: disagree` in `state: cancelled`, contrary to I30-02 and the schema, which requires null result and Observation for cancelled checks ([guided-check.schema.json:418](docs/product/api/schemas/guided-check.schema.json:418)).  
    **Required:** enumerate every field changed by cancel and retry, preserving historical attempts separately. Define camera abandonment and late-result handling. Add a contract test for disagree, cancel, GET, restart and GET again.

17. **[major] Sections 2, 4.3 and 14: the E28 integration contradicts the current neighboring design.**  
    E30 expects E28 to consume `guided_check.checked`. E28 instead provides `PlanRunGuidedCheckPort.complete_step` for a call inside E30's transaction ([E28.md:390](docs/tdd/E28.md:390)) and does not list the event as consumed. Builders following both documents will leave the plan step incomplete. The package requires a checked GuidedCheck to mark its plan step done ([CONTRACTS.md:1282](docs/product/CONTRACTS.md:1282)).  
    **Required:** resolve X11 to one agreed seam before integration. Include actor attribution, duplicate delivery, concurrent plan closure and rejection behavior. Correct the neighboring disagreement-completes-step expectation through its owner. Test against the actual E28 port or consumer.

18. **[major] Sections 4.2, 5 and 12: command durability and external side effects lack a complete failure protocol.**  
    Camera acquisition starts before the transaction commits, but commit failure, disk full and concurrent cancellation have no cleanup rule. Concurrent finish commands can wait on the camera and then race to write records. T30-16 kills a count, not the finish transaction. The package requires “the state change, the audit event and the outbox entry commit together” ([CONTRACTS.md:1108](docs/product/CONTRACTS.md:1108)).  
    **Required:** specify revision revalidation, transaction boundaries, idempotency ordering, durable acknowledgement guarantees and camera-ticket cleanup. Name the E01 durability dependency precisely. Add fault injection at every finish write boundary, disk-full tests, lost-response retries and two-client finish/cancel races.

19. **[major] Sections 4.1, 5 and 11: resource bounds and external-call timeouts are incomplete.**  
    `abandon`, `drain` and `stop` have no timeout contract. Count duration has no validated maximum, so the beat bound is itself unbounded. Attempt counts, active persistent checks, frame buffers, response size and several coordinator queues have no limits or overload behavior. The charter requires “bounded loops and queues, timeouts on every external call and subprocess” ([BUILD-CHARTER.md:90](docs/BUILD-CHARTER.md:90)).  
    **Required:** provide a resource table with configuration keys, validated maxima, overflow behavior and scheduling priority. Separate durable history from bounded working sets. Test maliciously large configuration values, worker hangs and saturation while the emergency path remains responsive.

20. **[major] Sections 3, 4 and 6: typed errors and the RFC 9457 discrepancy remain unresolved.**  
    The design mostly lists wire codes, without defining domain/application exceptions or their mappings. It does not resolve the charter's RFC 9457 requirement against the package's closed `ErrorEnvelope`, which has `additionalProperties: false` ([error.schema.json:136](docs/product/api/schemas/error.schema.json:136)).  
    **Required:** define typed exceptions and a complete mapping table, including storage, configuration, routing, capacity and worker failures. File the envelope conflict in section 14 and state the package-compliant interim wire representation. Test that failures neither leak private content nor cross layers as bare exceptions.

21. **[major] Sections 1, 12 and 15: E30-06 has deliverable filenames but no study design.**  
    T30-30 names statistical outputs, but the document does not define capture columns, pair/window identifiers, exclusions, denominators, first-time completion scoring, metronome conditions, refusal handling, retention or the How we know publishing seam. VALIDATION requires all of these results to be reproducible and says compression feedback “stays Experimental” and “is not shown in the video” ([VALIDATION.md:227](docs/product/VALIDATION.md:227)); E30 instead permits removing the label after a study citation.  
    **Required:** specify the protocol and data schema now, leaving only equipment, recruitment and consent authority unresolved. Define analysis commands, consent-controlled exports, retention/deletion and publication ownership. Resolve the package's labeling/video discrepancy explicitly.

22. **[major] Sections 12 to 15: the proposed gates do not select the declared scenarios and ownership is incomplete.**  
    Tests use `@pytest.mark.scenario("V85")`, but the gate selects `scenario_V85`; these are different marker names. The repository enables strict markers without registering either convention. The plan also lacks parser property tests and explicit tests for I30-17. Runtime validator and import-linter changes require files outside section 13's ownership. The charter requires traceability that fails on an untested requirement ([BUILD-CHARTER.md:82](docs/BUILD-CHARTER.md:82)).  
    **Required:** use one registered scenario convention, fail on zero selected tests, and name the owner of shared gate/configuration changes. Add parser properties, configuration-pin tests and the fault tests requested above. Specify mutation, traceability and CI evidence required before completion.
