VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 3.5 and 4.1: configuration edits can clear an unresolved hazard.**  
   [E24.md:210](docs/tdd/E24.md:210) clears a warning whenever its definition hash changes, including a title or step edit. If its sensor is stale, reevaluation cannot establish that the condition still holds, so the warning can disappear without fresh clearing evidence. The package says “a warning whose definition is gone clears” on activation ([CONTRACTS.md:521](docs/product/CONTRACTS.md:521)), and “Stale data never clears a warning” ([CONTRACTS.md:706](docs/product/CONTRACTS.md:706)).  
   **Required change:** distinguish definition removal, content edits and rule changes. Preserve unresolved warnings across content edits; specify how rule changes interact with pinned evidence, dwell and routine overrides. Request approval for any additional clearing semantics. Test content and threshold changes while a warning is acknowledged, stale or awaiting sufficient coverage.

2. **[blocker] Sections 3.5 and 5.3: dwell does not establish continuous evidence.**  
   [E24.md:216](docs/tdd/E24.md:216) clears when two qualifying evaluations are separated by the dwell duration, unless an intervening failure event resets the marker. Two `latest` readings separated by an unobserved interval can satisfy this, particularly during fast replay or after downtime. The package states that `latest` has no coverage and requires the clear condition to hold “continuously” ([CONTRACTS.md:682](docs/product/CONTRACTS.md:682), [706](docs/product/CONTRACTS.md:706)).  
   **Required change:** define continuity evidence, permitted sample gaps, timestamp ordering and startup reconciliation with E23. Persist the necessary evaluation state and reset dwell when continuity cannot be proved. Test sparse `latest` readings, replay gaps, out-of-order readings and power loss during dwell.

3. **[blocker] Section 3.6: one warning per sensor/channel suppresses distinct hazards.**  
   [E24.md:224](docs/tdd/E24.md:224) permits only one active sensor-limit warning per group and chooses one crossed limit. The package instead raises “once per definition and channel” and supersedes only lower levels ([CONTRACTS.md:704](docs/product/CONTRACTS.md:704)). Its oxygen limits include low oxygen using a one-hour average and high oxygen using `latest`, both at `act`; both can hold simultaneously ([sensor-limits.example.json:132](docs/product/api/examples/config/sensor-limits.example.json:132), [215](docs/product/api/examples/config/sensor-limits.example.json:215)).  
   **Required change:** implement per-definition uniqueness and the contracted escalation behavior. If mutually exclusive escalation families are needed, request an explicit configuration shape. Define equal-level behavior and test simultaneous low-average/high-current oxygen conditions.

4. **[blocker] Sections 3.5 and 4.1: delayed events can clear newer occurrences, and replay can resurrect completed ones.**  
   The mission-event rule clears on a matching event type and scope key, without comparing causality or occurrence time ([E24.md:203](docs/tdd/E24.md:203)). An old all-clear arriving after a newer storm alert therefore clears the newer warning. UC-R1's active-row uniqueness also stops deduplicating once that row becomes final. The package distinguishes observed and received times and says “a new occurrence” creates a new warning ([CONTRACTS.md:9](docs/product/CONTRACTS.md:9), [776](docs/product/CONTRACTS.md:776)).  
   **Required change:** define durable occurrence identity, input deduplication and causal matching for clear events. Specify reconstruction during release/environment reevaluation so resolved answers and dismissed insights do not reappear from the same evidence. Request missing correlation fields. Test delayed all-clears, repeated inputs after finalization and reevaluation after dismissal.

5. **[blocker] Sections 2, 7, 9 and 12: the storm warning path does not deliver V58.**  
   `EmergencyInterrupt` handles only `emergency`, while the package's `radiation_storm_shelter` definition is `act` ([E24.md:704](docs/tdd/E24.md:704); [warning-rules.example.json:592](docs/product/api/examples/config/warning-rules.example.json:592)). T-E24-075 checks database raise/clear behavior, not shelter steps on every screen. V58 requires those steps “on every crew screen at once,” and UC05 requires the onboard monitor to start the flow with the ground link down ([VALIDATION.md:78](docs/product/VALIDATION.md:78); [USE-CASES.md:148](docs/product/USE-CASES.md:148)). The configured event currently permits only `ground` and `operator`.  
   **Required change:** specify the onboard trigger and presentation path, without inventing a radiation threshold or silently changing the configured level. Assign shelter attendance and post-storm behavior to explicit owners. Add a multi-screen V58 test with the model stopped and link down.

6. **[major] Sections 4.4 and 7: historical SSE events are treated as current emergencies.**  
   The component displays every received `warning.raised` emergency immediately, without reconciling current state ([E24.md:491](docs/tdd/E24.md:491), [704](docs/tdd/E24.md:704)). After reconnect, an unseen historical raise may already have been cleared. Conversely, the design gives no equivalent interruption path for an active emergency loaded by GET. The package explicitly supports resumable, at-least-once historical delivery ([CONTRACTS.md:981](docs/product/CONTRACTS.md:981)).  
   **Required change:** define snapshot/cursor reconciliation, revision ordering and interruption behavior for initial load, reconnect and cursor expiry. Render origin and evidence time on the interruption itself. Test raise-and-clear during disconnection, duplicate delivery and an emergency active before sign-in.

7. **[major] Sections 3.10 and 14: the proposed hold policy still permits behavior forbidden by V74.**  
   R-E24-1 permits additional interrupting levels and does not require both sleep and EVA. The implementation also excludes warnings raised before the overlay began, and specifies no retained deferred notification for a warning that clears during the overlay ([E24.md:302](docs/tdd/E24.md:302), [917](docs/tdd/E24.md:917)). V74 says “nothing below Emergency interrupts” and held warnings show afterwards with their original time ([VALIDATION.md:94](docs/product/VALIDATION.md:94)).  
   **Required change:** constrain the policy to that requirement and define notification lifecycle separately from warning lifecycle, including overlapping overlays, preexisting warnings, acknowledgements and clearing while held. Make approval of the required contract extension an implementation prerequisite; the explicitly red interim is not acceptance coverage.

8. **[major] Sections 3.12, 4.2 and 14: the vehicle-alarm proposal has incompatible authorization and visibility.**  
   R-E24-9 allows an `adapter` to record vehicle events, but `recordMissionEvent` lists only `crew`, `crew_medical_officer`, `operator` and `ground` ([openapi.yaml:1744](docs/product/api/openapi.yaml:1744)). It creates a `crew` warning, while E24 offers E26 only `active_habitat_at_or_above`. The help design expects both habitat and crew warnings ([E26.md:491](docs/tdd/E26.md:491)).  
   **Required change:** include the authorized adapter ingestion mechanism in the request and agree one air-safety query contract with E26. Test a vehicle alarm arriving through that mechanism and appearing before the help questions, with no vehicle acknowledge/silence capability.

9. **[major] Section 4.1: command replay is not ordered before revision checks.**  
   The prescribed check order tests `If-Match` against the current revision without specifying prior idempotency-result lookup ([E24.md:388](docs/tdd/E24.md:388)). After commit followed by response loss, the identical retry carries the old revision and can return `STALE_VERSION`. The package requires “the same key with the same body returns the first result” ([CONTRACTS.md:210](docs/product/CONTRACTS.md:210)).  
   **Required change:** specify authenticated replay lookup before mutable precondition evaluation, atomic storage of the original outcome, and transaction serialization for competing actions. Test crash after commit before response, same-key concurrent retries and two clients acting on the same revision. T-E24-070 currently tests only failure before commit.

10. **[major] Sections 2 and 4: shared input interfaces are neither agreed nor sufficiently defined.**  
    E24 expects `SupplyCoverChanged`, but E32 supplies `SupplyCoverFacts.rows` and specifies reevaluation on supply use, configuration and environment changes ([E24.md:478](docs/tdd/E24.md:478); [E32.md:80](docs/tdd/E32.md:80)). `RuleInput`, decision variants, `InsightDraft`, `RecordFacts` and several producer payloads lack complete typed definitions. The sensor payload has no explicit release/freshness identity; supply quantities lack units. Both SYSTEM.md and DEPLOYMENT.md are absent.  
    **Required change:** record exact shared interfaces and owner agreements as requests, including transaction ownership, dispatch ordering, nullable fields, units and release identity. Define state-query ports needed for reevaluation. Add producer/consumer contract tests. Internal events need not become SSE events, but parallel builders need one agreed shape.

11. **[major] Sections 3.5 and 4.3: supply rules do not handle unknown cover or activation without a supply use.**  
    The evaluator compares `cover_uses` directly and requires a `supply_use` as evidence ([E24.md:208](docs/tdd/E24.md:208)). The package defines cover as `null` for unknown or unavailable quantities and computes it from both stock and applicable plans ([CONTRACTS.md:1391](docs/product/CONTRACTS.md:1391)). Low cover can therefore arise on activation without any use record.  
    **Required change:** define unknown-cover behavior without manufacturing zero or treating unknown as recovery. Specify evidence and reevaluation for stock, plan, release and environment changes, requesting an evidence shape where necessary. Test known-low to unknown, unknown to known, initial low stock and two simultaneously low supplies.

12. **[major] Sections 3.9, 5.2 and 8: rendering inputs and provenance are incomplete.**  
    The renderer needs sensor names, decimals, unit display, aggregation labels, channel source labels, source titles and evidence summaries, but the declared reader does not supply all of them ([E24.md:647](docs/tdd/E24.md:647)). `{insight_fragment}` has no source field in `Insight`; R-E24-8 requests only steps. Ground-silence warnings explicitly use empty evidence. The package requires warning templates and evidence to be rendered from configuration/state ([CONTRACTS.md:565](docs/product/CONTRACTS.md:565), [765](docs/product/CONTRACTS.md:765)).  
    **Required change:** provide a field-by-field rendering table naming each source document/field or typed query. Request missing summary, fragment and ground-evidence shapes. Define citation provenance when sourced content and team-default timing coexist. Ensure REPLAY evidence includes its original date and exposure disclaimer, not only HH:MM.

13. **[major] Sections 5.4, 9 and 11: resource bounds and storage-failure behavior are not implementable.**  
    `len(definitions)` is not a fixed bound because definitions, notes, evidence, active warnings and deadline rows have no stated maximum. Startup loads every deadline, and the cache has a target size without an eviction policy. “No external calls” also leaves SQLite lock/I/O waits and cross-module calls without deadlines ([E24.md:655](docs/tdd/E24.md:655)). This conflicts with the charter's bounded-work and timeout rules ([BUILD-CHARTER.md:90](docs/BUILD-CHARTER.md:90)).  
    **Required change:** name configuration fields, provenance, enforcement and overflow behavior for each bound. Define typed disk-full, locked-database and failed-commit handling with E01, including a visible fail-safe path that does not require another successful database write. Add saturation and storage-fault tests.

14. **[major] Sections 3.5 and 5.3: injected time is not a clock-correction policy.**  
    Deadlines fire immediately when their UTC due time is past, but there is no behavior for forward/backward corrections, mission-clock version changes or contradictory evidence timestamps ([E24.md:655](docs/tdd/E24.md:655)). A forward correction can expire an answer warning without the intended elapsed duration. The package requires clock corrections to be recorded and distinguishes UTC, mission time and observed time ([CONTRACTS.md:9](docs/product/CONTRACTS.md:9), [583](docs/product/CONTRACTS.md:583)).  
    **Required change:** specify time bases and correction handling for expiry, ground-silence deadlines, event-relative answer windows and displayed labels. Define restart reconciliation and uncertainty behavior. Add forward/backward jump and mission-clock correction tests.

15. **[major] Sections 6 and 14: API conflicts are resolved silently.**  
    The charter requires RFC 9457 errors, while the package defines a closed `ErrorEnvelope`; E24 adopts the latter without requesting resolution. It also changes `listWarnings` ordering before R-E24-6 approval and maps invalid action bodies to `MALFORMED_REQUEST`, although the package distinguishes malformed JSON/headers from field validation ([E24.md:679](docs/tdd/E24.md:679); [CONTRACTS.md:224](docs/product/CONTRACTS.md:224), [242](docs/product/CONTRACTS.md:242)).  
    **Required change:** file the exact envelope and response-code conflicts, including the operation's missing 422 and configuration-mismatch response. Specify a complete typed-error mapping and a contract-conforming interim. Do not implement the requested ordering change before approval.

16. **[major] Sections 12, 14 and 15: acceptance coverage and the proposed verification are incomplete.**  
    Required help-event warnings are removed pending R-E24-12, required UI wording is blocked on R-E24-2, V57 has only an import restriction test, and V69 has no named whole-day scenario. Parser property tests are absent. T-E24-044 also demands equality with examples that contradict the renderer: `assistant-sleep.json` contains literal `"why": "{insight_why}"`, and the fixed example IDs cannot match the specified hash-derived IDs ([E24.md:851](docs/tdd/E24.md:851); [assistant-sleep.json:23](docs/product/api/examples/warnings/assistant-sleep.json:23)). The backlog still requires help-event raisers and the complete warning UI ([backlog.json:1034](docs/product/backlog.json:1034), [1062](docs/product/backlog.json:1062)).  
    **Required change:** add an acceptance-to-test matrix with explicit owners for every split scenario and approval prerequisites for blocked work. Request correction of all conflicting examples and define comparison rules for generated identifiers. Add parser properties, V57/V69 integration scenarios, the fault tests above and explicit mutation, coverage, UI lint and traceability gate commands.
