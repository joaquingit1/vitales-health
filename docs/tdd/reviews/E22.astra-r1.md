VERDICT: CHANGES REQUESTED

1. **[blocker] Sections 4.1, 9 and 14: participation failures can block clinical record entry and warnings.** `RecordCompletion` derives views inside the producer transaction, while the declared fallback is failed submission and retry. A permanent derivation fault will fail every retry. X-E22-6 protects Today only after an unapproved schema change. The claim that infrastructure faults “fail every module equally” does not establish isolation. Evidence: [E22:230](docs/tdd/E22.md:230), lines 48 and 454; package `CONTRACTS.md:1099` requires Help to work “with every later module absent”; audit finding 9 identifies this rollback hazard. **Required change:** commit valid clinical input and a minimal durable completion intent independently of participation projection success. Specify projection retry, unavailable presentation and recovery. Coordinate the necessary Today and submit-response contract changes. Test a permanently failing projector while recording concerns, urgent events and checks, with existing warnings still accessible.

2. **[blocker] Sections 1.3 and 14: resetting SIM destroys accepted LIVE records.** Q-E22-2 explicitly acknowledges that restoring the whole database clears LIVE guest completions and nevertheless selects “yes” as the interim. Evidence: [E22:589](docs/tdd/E22.md:589); package `UX-DESIGN.md:690` says the demo resets “the Sim scenario”; charter lines 32 to 33 require accepted records to survive restart and retry. **Required change:** isolate the resettable SIM database or scenario from LIVE storage, audit and command identities. Coordinate the reset with E21. Test that a LIVE check survives repeated SIM resets and a crash during reset. Demo operation is not authorization to discard real records.

3. **[major] Sections 2, 3.3 and 4.3: concern completion wiring disagrees with its producer.** E22 expects E04 to call `CompletionRecorder`, but E04’s `StartConcern` commits without that call. E04 instead says E22 reacts to `AnswerAccepted`; E22 subscribes only to clock correction and configuration activation. Evidence: [E22:65](docs/tdd/E22.md:65), `docs/tdd/E04.md:257-279`; package `CONTRACTS.md:383-384` requires concern starts and qualifying open-episode updates to count. **Required change:** agree one producer or event adapter for each basis, including urgent events for an incapacitated subject. Specify how the producer proves acceptance, original actor, patient, episode eligibility and occurrence time without exposing answer content. Add end-to-end tests through actual concern and help commands, including closed episodes and failed commands, rather than testing only direct recorder calls.

4. **[major] Sections 4.2 and 5: the declared reader cannot guarantee visibility of the producer’s uncommitted completion.** Recording must compute views “on the same connection,” but repository read signatures take no transaction and the fenced reader opens its own connection. A separate SQLite reader cannot see the producer’s uncommitted insert. Evidence: [E22:230](docs/tdd/E22.md:230), lines 268 to 276 and 361 to 364; package `CONTRACTS.md:1108` requires state, audit and outbox to commit together. **Required change:** specify transaction-bound repositories or explicit read-context parameters, with separate committed-read behavior. Preserve the participation read restriction without denying legitimate audit/outbox writes. Test response and event contents against the newly inserted completion, followed by rollback and concurrent submission.

5. **[major] Section 3.3: idempotency keys collide for valid IDs and silently accept changed payloads.** The keys concatenate colon-containing IDs. `(basis_ref="a:b", patient_id="c")` and `(basis_ref="a", patient_id="b:c")` both produce `cc:daily_check:a:b:c`. Evidence: [E22:182](docs/tdd/E22.md:182); package `common.schema.json:10` permits `:` in IDs. The duplicate rule also returns the old completion without checking payload equality, contrary to `CONTRACTS.md:210`: “with a different body, `409 DUPLICATE_COMMAND`.” **Required change:** use unambiguous structured identities and compare immutable payloads on duplicates. Specify durable logical identity independently of the 24-hour HTTP cache, addressing audit finding 9. Test valid separator-containing IDs, changed payloads, concurrent duplicates and retries after a multiweek outage.

6. **[major] Sections 3.3, 4.1 and 5: identity correction cannot support correction reversal safely.** After A is reassigned to B, correcting B back to A encounters A’s original, permanently voided idempotency key. The recorder returns that row instead of creating a valid replacement. The reassign port also lacks an expected correction revision, and storage omits explicit replacement lineage and update-cause fields. Evidence: [E22:182](docs/tdd/E22.md:182), lines 250 to 252 and 354; package `CONTRACTS.md:400` requires immutable originals and later identity-correction voids. **Required change:** specify a versioned correction chain with distinct replacement identities, preserved occurrence provenance, authorization and conflict handling. Define retries of the same correction separately from competing corrections. Test A to B to A, repeated corrections, two clients correcting simultaneously and crash recovery.

7. **[major] Section 3.2: patch attribution is not deterministic from the contracted events.** Patches use local insertion `seq`, which is absent from CheckCompletion. With the configured threshold of seven, inserting identical day-1-to-day-7 events in ascending order attributes the award to day 7; inserting them in reverse attributes it to day 1. Shuffling already assigned `CompletionFact` objects does not test this. Evidence: [E22:155](docs/tdd/E22.md:155); package `CONTRACTS.md:396` requires “identical serialization apart from `as_of`.” The local sequence-based `event_cursor` also undermines that guarantee. **Required change:** define canonical ordering from immutable contracted fields, including ties, and specify a deterministic, person-scoped cursor. Test rebuilding separate databases from different arrival orders and interleavings with other people’s records.

8. **[major] Sections 4.1 and 11: batched rebuilds expose partially corrected history.** Rebuild updates active day assignments, but section 11 commits one unit of work per batch. Readers can therefore observe mixed clock assignments; a crash leaves a partially applied correction. Concurrent records or configuration activation can also make the result hash describe no single snapshot. Evidence: [E22:236](docs/tdd/E22.md:236), lines 488 to 489; package `CONTRACTS.md:1108` says “One command is one transaction.” **Required change:** specify either a bounded atomic rebuild or staged generations with an atomic activation transaction. Pin time, event boundary, clock history, roster and configuration. Publish audits and events consistently with activation. Test crash and disk-full failures between batches, concurrent inserts and simultaneous clock/configuration changes.

9. **[major] Sections 3.4, 4.3 and 8: award-removal semantics contradict the package, and activation loses the before-state needed for audit.** The design removes awards after clock corrections and immediately recalculates under changed thresholds. The package says: “A rebuild after a void … removes that award … Nothing else removes one.” Evidence: [E22:302](docs/tdd/E22.md:302), lines 344 and 432; package `CONTRACTS.md:402`. With no stored prior projection or pinned prior inputs, a later rebuild cannot reliably discover awards already removed by activation. **Required change:** request an explicit resolution of the package contradiction for threshold changes and clock corrections. Define old/new configuration and clock pins, the atomic transition and exactly when removal audits occur. Specify the source of `completion_rule_version`. Test valid activation, rejected configuration retaining the last good version, clock-induced day merging and audit replay.

10. **[major] Sections 4.2, 5, 9 and 14: multi-hub reconciliation transports completions but not their corrections.** `import_synced` accepts only CheckCompletion. There is no transport contract for voids, correction lineage or clock history, and its signature cannot supply the `source_hub` that storage expects. A corrected completion can remain counted indefinitely on another hub. Evidence: [E22:252](docs/tdd/E22.md:252), lines 354 to 359 and 445; package `CONTRACTS.md:388` requires accepted, **non-voided** events. Audit findings 8, 9 and 16 require disconnected reconciliation and agreed shared interfaces. **Required change:** agree a trusted synchronization envelope and owner covering completions, voids, replacement lineage and required clock/roster versions. Specify collisions, contradictory copies and void-before-completion delivery. Test convergence after prolonged disconnection with reordered and duplicated deliveries.

11. **[major] Section 9: incomplete replica data can be presented as current participation history.** A disconnected rover recomputes views with a fresh `as_of`, although remote completions are missing. Neither view schema carries replication completeness, so E03 cannot infer the promised stale state from the response. Missing remote completions can also appear as missed days. Evidence: [E22:445](docs/tdd/E22.md:445); `crew-goal-view.schema.json:34-43` contains computation time and versions, not synchronization status. **Required change:** request explicit completeness and synchronization metadata, distinguish computation time from data currency, and define how incomplete day histories are rendered without asserting a confirmed miss. Test a healthy local hub isolated from another hub while both continue recording.

12. **[major] Sections 1.3, 4.2, 6 and 14: the proposed REPLAY crew-goal response violates its schema.** The design promises an empty REPLAY CrewGoalView, but the schema allows only `"LIVE"` and `"SIM"`. Evidence: [E22:47](docs/tdd/E22.md:47), line 262; package `crew-goal-view.schema.json:11-15`. X-E22-7 changes only `reached`, so it does not resolve the origin mismatch. **Required change:** request and settle the response semantics for a station in REPLAY mission mode, including Today and events. Until approved, do not construct a schema-invalid view or relabel REPLAY as another origin. Add contract tests for this deployment mode.

13. **[major] Sections 3.1 and 5: unknown original offsets cannot be preserved.** `CompletionBasis.original_offset` is mandatory `str`, and its database column is `NOT NULL`. The contracted offset explicitly permits `null` when unknown. Evidence: [E22:93](docs/tdd/E22.md:93), line 353; package `common.schema.json:28-37` says “Original UTC offset where known” and permits null. **Required change:** preserve the nullable contracted offset through local recording, synchronization and storage. Do not manufacture `+00:00` merely because `occurred_at` was normalized to UTC. Test unknown offsets and malformed boundary input through the generated schema.

14. **[major] Sections 3.2 and 7: empty histories and supported mission-time boundaries are undefined or inconsistent.** A guest before their first completion has neither a roster start nor a first accepted completion, but StreakView requires `first_mission_day`. Clipping the crew window to day 1 creates an inverted window on day 0. The day-row rule also assumes a known planned mission length. Evidence: [E22:159](docs/tdd/E22.md:159), lines 163 and 396; package `common.schema.json:47` explicitly permits zero and negative preflight days, and `mission-context.schema.json:21-30` permits a null planned length. **Required change:** define first-read guest behavior, preflight participation, future roster starts, unknown or exceeded mission length, and forward/backward clock jumps. Apply the same eligible-day filtering to streak totals and patch awards. Add boundary tests for each case.

15. **[major] Sections 4.3 and 10: the privacy promise is stronger than the product can deliver.** Exact rolling totals in a small crew permit inference by subtraction and successive observation. E22 additionally emits a crew event for every accepted episode update even when the aggregate is unchanged, exposing activity timing. Evidence: [E22:296](docs/tdd/E22.md:296); package `PRD.md:226` mandates the shared total while `CONTRACTS.md:408` promises individual participation privacy. Audit finding 5 explicitly identifies this contradiction; finding 13 calls for optional gamification. **Required change:** submit a product-policy request defining honest visibility, voluntary participation and publication rules. Remove no-change crew broadcasts and cross-person cursor leakage. Test inference with a two-person crew and repeated polling/SSE observation. Delaying publication alone must not be described as anonymity.

16. **[major] Sections 5 and 11: resource estimates are not enforced bounds.** Three events per person per day is a sizing assumption, not a limit; every episode answer can create another event. Full-history queries, day-range loops, configurable window lengths and the proposed LRU have no fixed maxima. SQLite waits and rebuild cancellation are unspecified. Evidence: [E22:366](docs/tdd/E22.md:366), lines 477 to 489; charter lines 87 to 90 require bounded work and timeouts. **Required change:** specify validated resource limits, paged iteration, transaction deadlines, cache capacity and overload behavior that never silently drops accepted history. Bound configuration sizes at activation. Test oversized valid histories, huge clock jumps, lock contention and rebuilds under simultaneous help/record traffic. This also addresses audit finding 10.

17. **[major] Sections 6 and 14: the error wire contract remains unresolved.** “Errors are RFC 9457” does not match the frozen API, whose operations return `application/json` ErrorEnvelope and whose schema rejects extra fields. Evidence: [E22:382](docs/tdd/E22.md:382); package `CONTRACTS.md:220`, `error.schema.json:127-136` and `openapi.yaml:10714-10745`. Charter section 3 requires RFC 9457, so this is a shared conflict requiring a request. **Required change:** agree the E01 mapping and wire representation before implementation. List mappings for storage, isolation, malformed configuration, cursor and correction errors, including retryability and safe metadata. Add non-success response contract tests; do not let each epic invent its own envelope.

18. **[major] Sections 7, 9 and 12: the UI rules contradict station operation and miss specified states.** Every component renders only on `everyday`, while station sessions must show the crew goal and E03 declares a separate `station` surface. No station slot is specified. `StreakCard` always shows a big number, including the large zero prohibited after a miss. Evidence: [E22:389](docs/tdd/E22.md:389), lines 395 and 443; package `CONTRACTS.md:1086` permits station crew-goal access and `UX-DESIGN.md:681` prohibits “a large zero.” **Required change:** coordinate a station-only aggregate slot without personal queries, define the missed-day card state, and explicitly cover warning and routine routes in D27 tests. Test sign-out/idle-lock transitions from personal cards to station mode, including late responses and events.

19. **[major] Sections 2 and 14: the practice-patch integration has incompatible proposals.** X-E22-2 merges practice awards into PatchAward and adds `skill_id`. E31 instead requests a separate `/v1/me/practice-patches` resource and tests that PatchAward contains no skill/readiness field. Evidence: [E22:610](docs/tdd/E22.md:610), `docs/tdd/E31.md:517` and `556-561`; package `CONTRACTS.md:1371` says skill data is “never in participation views.” **Required change:** settle one shared representation and endpoint with E31 before either builder implements it. Keep mission and practice derivations separate, define whether rebuild hashes include practice awards, and make the Practice row’s delivery dependency explicit. Test a completed drill updating the Practice row while mission streak, mission patches and crew goal remain unchanged.

20. **[major] Sections 12 and 15: the acceptance gates do not execute all claimed evidence.** Browser scenarios and mutation testing are named, but the gate list contains no explicit browser or mutation command and no explicit branch-coverage failure threshold. Parser property tests are also absent, despite new configuration and cursor parsing. The isolated 21,600-row benchmarks do not establish operation under combined load. Evidence: [E22:556](docs/tdd/E22.md:556), lines 644 to 653; charter lines 82 to 90. Audit findings 10, 14 and 15 require integrated, reproducible evidence. **Required change:** provide executable gates for browser scenarios, parser properties, critical-path mutation testing and the 95% branch threshold. Include the fault and concurrency cases above, and bind results to document, implementation, configuration and fixture hashes. Keep all results explicitly planned until executed.
