### 3.2 Freshness (`freshness.py`)

`period_seconds(f, calendar)`: `daily` 86 400; `weekly` `calendar.week_days` x 86 400; `monthly` `calendar.month_days`
x 86 400; `every_n_days` `f.n` x 86 400. Any other cadence word is a configuration error (section 8, check R-L3).

`skill_record(person, skill, practices, f, calendar, now, label_at) -> SkillRecord` with practices filtered to one
`origin_mode`:

* no practice: `freshness` `never`, every time field `null`, `source` `null`;
* `last` = the practice with the greatest `practiced_at` (ties: `drill` before `event` before `preflight`, then
  `source_ref_id`); `last_practiced_at`, `source`, `source_ref_id` from it; `trained_at` = greatest `preflight` time
  or `null`;
* `due_at` = `last_practiced_at` + `due_after_periods` x period; `stale_at` = `last_practiced_at` +
  `stale_after_periods` x period;
* `freshness` = `fresh` when `now < due_at`, `due` when `due_at <= now < stale_at`, `stale` when `now >= stale_at`;
* `last_practiced_label` = `label_at(last_practiced_at)` (the inline day label under the profile active then: "day 12"
  for the station practice, read on the Moon base); `freshness_text` = ui-copy `freshness_words[freshness]`;
  `freshness_basis` and `freshness_to_be_set_by` from the catalog.

Check against the fixture: practice on 2026-11-06T15:20:00Z, `monthly`, `month_days` 30, periods 1 and 2 give
`due_at` 2026-12-06T15:20:00Z and `stale_at` 2027-01-05T15:20:00Z (`api/examples/events/page-drill-day12.json`).

A holder of a skill (CONTRACTS section 22) is a person whose record is `fresh` or `due`.

Origin rule (decision): role proposals, readiness and freshness read only practices whose `origin_mode` equals the
mission's practice mode: `LIVE` when the mission mode is `LIVE`, otherwise `SIM`. REPLAY never creates a practice.
SIM practice never makes anyone a holder in a LIVE mission (CONTRACTS section 9: no simulated result enters LIVE).

### 3.3 Role engine (`role_engine.py`)

`propose(ctx, rules, candidates, records, kept, now) -> Proposal(assignments, unfilled)`. Deterministic: same inputs,
same output (IDs are assigned outside the domain). Steps, CONTRACTS section 24:

1. Eligible for a role: on the roster; not `ctx.subject_person_id` (`never_subject`); not `on_eva` when the role is
   `on_site` (`not_on_eva_for_on_site`). These two are hard exclusions and apply to every proposal and every reassign.
2. Preference order for a set of eligible people (`order_key`): awake before asleep (`awake_first`), then the role's
   own key, then not the opener before the opener (request Q2), then `roster_index`.
3. `kept`: assignments in state `changed` stay as they are, always. Assignments in state `accepted` stay unless the
   person became ineligible (subject, or `eva` for an on-site role). Their people count as holding a role.
4. `medical_officer` (when the needs list it and it is not kept): walk `rules.cascade` in order. `officer_rank` r: the
   roster person with `medical_officer_rank == r`; if that person is ineligible, add a context reason
   (`officer_is_subject` or `officer_on_eva`) and continue; if asleep while a later cascade step yields an awake eligible
   person, add `officer_asleep` and continue; otherwise assign with the step's `reason_code`.
   `freshest_skill_holder`: the needed skill is the `medical_officer` need's `skill_id`, else the first non-null
   `skill_id` among the needs in order; assign the eligible holder with the greatest `last_practiced_at` (key from
   step 2, freshness first); with no needed skill or no holder, the role is `unfilled`. If every cascade step passed
   over only asleep officers, assign the first asleep eligible officer with its step's `reason_code`.
5. Required needs in order, then optional needs in order. `one_role_each`: a required need takes people without a role
   first and falls back to people who already hold one only when none is free; an optional need takes only people
   without a role. A need with `skill_id`: the eligible holder with the latest practice (`freshest_skill`, phrase
   `{skill_short} practiced {day_label}`); with no holder, a required need falls back to the first eligible person
   (`free_to_help`) and an optional need is `unfilled`. A need without `skill_id`: the first eligible person
   (`free_to_help`).
6. `reason_text` = `reason_phrases[reason_code]` rendered with `{officer_name}`, `{eva_word}` (profile walk word),
   `{time}` (the overlay's planned end, mission time HH:MM), `{skill_short}`, `{day_label}`, `{person_name}`; a missing
   value renders `designed_states.unknown` (CONTRACTS section 11). `context_reasons[].text` uses the same phrases.
   `label` from `roles[role_id].label`; `task_text` from the need.

Plan step proposal: `propose_plan_step(ctx, skill_id, ...)` proposes `rules.plan_step_role` for the freshest eligible
holder of `skill_id` (not the subject; not on `eva` when that role is on-site) with `context_reasons` for each medical
officer who is unavailable (subject, on a walk, asleep). With no holder: `unfilled` (the step shows
`needs_skill_holder` in E28's PlanView).

### 3.4 RoleAssignment state

`proposed → accepted`; `proposed` or `accepted` → `changed` (reassign); `changed → changed` (reassign again). A
re-proposal never edits an assignment: it creates a new one and sets `replaced_by_id` on the replaced `proposed` or
ineligible `accepted` one. The current assignments of a context are those with `replaced_by_id` null. `allowed_actions`:
`accept` only in `proposed`; `reassign` in every state; empty when the help session is closed or the plan run closed.

Re-proposal triggers: the context first needs roles (session reached a flow; plan run step needs a skill holder); the
flow changes (`switch_flow`, `start_over` then a new flow); `overlay.changed` for anyone on the roster; helpers join or
leave; a `skill.practiced` that changes holders. A trigger re-runs `propose` with `kept`; unchanged results write
nothing (no event churn).

### 3.5 Drill state

`running → completed` (`POST /v1/drills/{id}/complete`), `running → abandoned` (automatic at the end of the mission day
it started on, section 14 Q4). `stores_measurements` is the constant `false`. Completion writes, in one transaction, one
`skill_practice` row per completing participant and drill skill (`source` `drill`, `practiced_at` the hub time of
completion), and emits `drill.changed` and one `skill.practiced` per row.

### 3.6 Practice patches (`practice.py`)

Computed on read from completed drills and practices of one person and one origin mode; never stored, so a rebuild is
not needed. With `participation-rules.practice`: `first_drill` is earned at the person's first completed drill;
`drill_count` with threshold n at the nth; `skill_fresh` at the first completed drill after which every
`core_skill_ids` skill is `fresh` for that person at the completion instant. Award ID = `ppa_` + first 16 hex of SHA-256
of `person|mission|origin|kind|threshold`. Inputs are completions only: no drill duration, no camera value, no guided
check result (`drill_measurements_count` is the constant `false`).

Event practice rules (decision, section 14 Q5): a checked guided check with no `drill_id` gives the helper a practice of
its skill; a help session that closes with a disposition other than `false_alarm` gives a practice of the need's skill
to each person whose role in it, with a non-null `skill_id`, was `accepted` or `changed` at close.

Validation in `StartDrill`: `scenario_id` is a `drill_scenarios[].scenario_id` of one of `skill_ids`; each skill exists;
each participant is on the roster; `origin_mode` equals the mission's practice mode (`ORIGIN_MISMATCH`); every
`needs_supplies` entry is aboard in the active environment (`CONTEXT_INAPPLICABLE`); `routine_occurrence_id`, when set,
is a `due` or `later` occurrence of an item whose `skill_ids` include every requested skill (`INVALID_VALUE`).
`CompleteDrill`: `participant_ids` a non-empty subset of the participants (`INVALID_VALUE`); after commit, the linked
occurrence is completed through E25 (a refusal, for example an occurrence already `missed`, is logged and never forces
the occurrence: misses are never filled in).

## 10. Safety, security and privacy

| Hazard | Cause | Mitigation | Test |
|---|---|---|---|
| H1 The patient or a walker is assigned a hands-on role | Engine bug or reassign | Hard exclusions in proposal and reassign; property test over random rosters and overlays | T-E31-030 to T-E31-032 |
| H2 Help delayed waiting for roles | Coupling | Event-driven after commit; E26 never calls E31 synchronously except the 100 ms broadcast source | T-E31-036 |

Authorization: section 6 roles; identity only from the session. Readiness only for `crew_medical_officer`; my skills only
for the session person. Skill data is operational: no health values, never in participation views, never in a model
prompt except `get_crew_readiness` for medical officer sessions (E12). The assistant cannot propose, accept or reassign
a role: no tool reaches `actOnHelpRole`; `propose_guided_check` names a step, and the role engine names the helper.

Observability: logs carry context IDs, proposal sequence, reason codes and latency; never names in debug output beyond
IDs.

Unresolved clinical and equipment assumptions: freshness cadences (monthly, due after 1, stale after 2) are team
defaults until the flight surgeon sets them; the role needs of each flow are the team's reading of RESPONDER-FLOWS.md;
the manikin (`cpr_manikin`) is a supply that may not be aboard (drill then returns `CONTEXT_INAPPLICABLE`); the CPR rate
check is experimental.
