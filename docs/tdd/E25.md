## 3. Domain model

All code in `crew_health/routine/domain/` is pure. Types are frozen dataclasses with slots or `StrEnum`.

### 3.1 Vocabulary

Enums mirror the schemas: `CadenceWord` (nine words), `OccurrenceState` (`not_due, due, later, done, skipped, missed`;
`OPEN = {due, later}`, `FINAL = {done, skipped, missed}`), `CauseKind`, `SkipReason`, `OccurrenceAction`, `Audience`,
`StartedBy`, `SourceKind`, `EndsKind`, `EndReason` from `routine-occurrence`, `routine-override` and `requests`
schemas. Internal: `DueKind` (`specific`, `all_day`), `QuestionInstanceState` (`open`, `answered`,
`partially_answered`, `unanswered`), `OriginMode` (`LIVE`, `REPLAY`, `SIM`).

### 3.2 RoutineRelease

Built once per release by the reader (5.2), immutable: `items` (file order), `sources`, `notice`, `calendar`,
`suppressed_overlays`, `display_groups` (labels from ui-copy), `item_policies`, `misses`, `bindings` (tagged unions),
`question_sets` (IDs and question IDs), `words` (ui-copy keys of section 8), `event_type_labels`, `release_id` and
document versions, and `item_content_sha256[item_id]` (RFC 8785 canonical JSON of the item's guidance parts: `plain`,
`why`, `instrument`, `minutes`, `steps`, `body_region`). `RoutineItem.cadence_for(environment_id)` returns
`by_environment[environment_id]`.

`daily_check_item_id` is the single item that `add_questions` bindings target (loader check R-E25-10: exactly one) until
R-E25-1 gives items a `kind`. No item ID appears in code.

### 3.3 Identity

```python
occurrence_id = ids.derived("ro", person_id, item_id, str(mission_day), cause_key)
override_id   = ids.derived("rov", binding_id, source_kind, source_ref, audience_key)      # bound
manual_ovr_id = ids.derived("rov", "manual", actor_ref, idempotency_key)                   # manual (4.1)
instance_id   = ids.derived("rq", override_id, person_id, question_set_id, slot)
```

`cause_key`: `cadence`; `override:<ovr>` (a day under a replaced periodic cadence); `override:<ovr>:at_trigger`, `:t<i>`,
`:every:<k>`, `:at_clear`, `:q:<slot>`; `per_eva:<overlay>:before|after`; `cadence_event:<binding>:<source>:<slot>`;
`assistant:<insight>`; `walk_summary` (projection only). `slot` is `initial` or `repeat:<i>`. `audience_key` is the
person ID for `person`, else the audience word. Derived IDs are what let a restart, a rerun or another hub reproduce the
same objects (INV-E25-08).

### 3.4 Cadence and generation

| Word | Period | Occurrences |
|---|---|---|
| `continuous` | 1 | One per day; completed by an accepted observation of the item's codes after R-E25-1, by the person until then |
| `daily` | 1 | One per day |
| `every_n_days`, `weekly`, `monthly` | `n`, `calendar.week_days`, `calendar.month_days` | One on the next periodic day |
| `per_eva` | none | From the person's walks per `item_policies[item].per_eva` (`before_start`, `after_end`, `both`); no policy: manual (loader warning) |
| `after_event`, `mission_phase` | none | Only from a `cadence_event` binding; else manual |
| `as_needed` | none | Only from triggers, bindings, the assistant or (after R-E25-8) the person |

**Periodic history** of an item for a person is the set of its occurrences with cause key `cadence` or `override:<ovr>`
(a periodic day). Occurrences added by triggers, walks, cadence events, the assistant or the person are never in it, so
they never move the next periodic day (PRD 4.9 "never removes, loosens or postpones a task"; INV-E25-14).

Next periodic day (CONTRACTS 15): `candidate = last_ended_day + period`, where `last_ended_day` is the mission day of the
latest final occurrence in periodic history on or after the anchor day; with none, the anchor day. The occurrence day
is `max(candidate, first_unshown_day)` (today when today has no stored periodic occurrence of the item, else tomorrow),
so a slot on a day the hub never showed moves to today and is never a miss (DE25-7).

### 3.5 Effective cadence (DE25-5, INV-E25-04)

`effective_cadence(item, environment_id, active_overrides, activations, calendar) -> EffectiveCadence(cadence,
governing_override_id | None, governing_basis, governing_source_ids)`:

1. `base = item.cadence_for(environment_id)`.
2. Candidates: active `replace_cadence` overrides and cadence activations applying to the person.
3. A periodic candidate replaces the base only when the base is not periodic or `period(candidate) <= period(base)`;
   smallest period wins; ties by latest `started_at`, then larger ID.
4. A `per_eva` candidate is additive (walk occurrences added, base continues).
5. An event word candidate, or a periodic candidate looser than the base, adds one occurrence at its start
   (`:at_trigger`) and stays listed with its words; it never replaces the base.

### 3.6 Occurrence and state machine

```python
@dataclass(frozen=True, slots=True)

    occurrence_id: str; revision: int; person_id: str; item_id: str; environment_id: str
    mission_day: int; cause: Cause; cause_key: str; question_instance_ids: tuple[str, ...]
    state: OccurrenceState; due_from: datetime | None; base_due_until: datetime | None
    due_until: datetime | None; due_kind: DueKind; suppressed_by_overlay: str | None
    completed_at: datetime | None; outcome: Outcome | None; skip: Skip | None
    miss_counted: bool; config_release_id: str; origin_mode: OriginMode; clock_version: int
```

| From | Input | To | Actor | Guard |
|---|---|---|---|---|
| (new) | Event-created occurrence for a future day | `not_due` | scheduler | Cadence occurrences of future days are only projected |
| (new), `not_due` | Day start or creation on today | `later` if `now < due_from` or held, else `due` | scheduler | `now < due_until`; otherwise not created, audit `routine.occurrence_not_created` |
| `later` | Clock reaches `due_from` and not held | `due` | scheduler | |
| `due` | `later` with `later_until` | `later` | the person | `now < later_until <= due_until` |
| `due`, `later` | Hold recomputed (3.6.1) | `later` held, or `due` when released | scheduler | Not a `before_start` occurrence of that same walk |
| `due`, `later` | `complete` | `done` | the person, an auto-complete over that person's accepted evidence (R-E25-1), E03 `ReactionTestRecorded` or `DailyCheckSubmitted` for that person, E31 for a drill | `completed_at <= now`, inside `[day start, due_until]`; admissible origin (3.8.1) |
| `due`, `later` | `skip` with a reason | `skipped` | the person | No linked records |
| `due`, `later`, not held | Clock reaches `due_until` | `missed`; `miss_counted` per 3.11 | scheduler | Clock trusted (3.13) |
| `due`, `later` (cadence cause) | Its successor in periodic history becomes `due` | `missed`, `miss_counted = false`, reason `superseded_by_next_slot` | scheduler | Keeps one open periodic occurrence per item (3.7) |
| `later` (`before_start`) | Its walk starts | `missed` | scheduler | |
| final | any local input | rejected `INVALID_TRANSITION` | | INV-E25-01; only replication reconciles (5.1.1) |

`allowed_actions` per session: the occurrence's person sees `complete, skip, later` in `due` and in `later` when not
held, `complete, skip` while held, nothing otherwise; other sessions see nothing. Every transition increments
`revision`, appends one `routine_occurrence_transition` row and emits `routine.occurrence_changed`.

#### 3.6.1 Hold (DE25-4, INV-E25-03)

Input: the base window `[f, u)` and `S`, the merged union of the person's intervals of overlays in
`suppressed_overlays` (from `OverlayPort.intervals`, an active overlay has end `None`, meaning unbounded).

```python
def held_window(f: datetime, u: datetime, s: Sequence[Interval]) -> tuple[datetime | None, str | None]:
    end = u                                   # None when an unbounded interval holds the window
    for a, b in s:                            # merged, sorted by start, bounded by settings
        if a >= end: break
        start = max(a, f)
        if b is None: return None, kind_of(a, b)
        if b > start: end = end + (b - start)  # held time inside the window extends it
    return end, None
```

The extension is nonnegative by construction, overlapping overlays count once (merged union), an overlay that ended
before `f` adds nothing (13:00 to 15:00 task, sleep ending 08:00: window unchanged), and the result is a function of
the interval set, so delivery order does not matter. At instant `t` the occurrence is held when some interval of `S`
contains `t` and `t >= f`; `suppressed_by_overlay` names the kind of that interval (the earliest started, ties by
kind order of `suppressed_overlays`). Held occurrences have no miss deadline; on every overlay change the hold, `due_until`
and deadlines are recomputed in the overlay's transaction. A `before_start` occurrence ignores its own walk.

### 3.7 Due windows

| Case | `due_from` | `base_due_until` | Kind |
|---|---|---|---|
| Policy `preferred_time` | that mission time on the day | `due_from + window_minutes`, or day end when `null` | specific |
| Created at trigger instant `t` | `t` | `t + window_minutes` with a policy window, else end of `t`'s day | specific |
| `times[]` entry | mission time on trigger day + offset | as above | specific |
| `every_minutes` slot `k` | `t + k * every_minutes` | next slot's `due_from` | specific |
| `per_eva` `after_end` | walk end | `due_from + window_minutes`, or day end | specific |
| `per_eva` `before_start` | `planned_start - window_minutes`, or start of the walk's day | walk `started_at`, else `planned_start` | specific |
| Question instance slot | 3.9.1 | 3.9.1 | specific |
| Otherwise | day start | day end | all_day |

`t` is the input's source time (`occurred_at` for mission events, `raised_at` for warnings, `observed_at` or
`answered_at` for records), never the receipt time (3.13). The occurrence's `mission_day` is the day of `due_from`;
`due_until` may fall on a later day (a 1,440 minute pre-walk window starts the day before; holds extend windows past
midnight). An open occurrence stays open and listed until it is final, whatever its day (3.10). The only interaction
with the next cadence occurrence is the successor rule of 3.6, which applies to periodic history only: an added
occurrence never closes or is closed by a cadence occurrence.

#### 3.8.1 Inputs and admissibility (DE25-16, DE25-12)

`TriggerInput` variants all carry `mission_id`, `origin_mode`, `source_at`, `received_at` and the subject person IDs:

|---|---|---|
| Mission | `inp.mission_id == mission.mission_id` | `routine.foreign_mission` |

|---|---|
| `person` | The input's subject |

#### 3.8.3 Matching, effects and ends

`match_bindings(release, inp, environment_id) -> tuple[Firing, ...]` (pure) fires per CONTRACTS 15 `on` table, with an
`observation` binding firing only for `quality_status == accepted` and the binding's exact unit (else audit
`routine.binding_unit_mismatch`). A `cadence_event` binding fires only when its `environment_id` is null or active.

| Binds and effect | Result |
|---|---|
| `trigger` + any | One override (derived ID; a replay finds it). `started_by`: `sensor_limit` when the warning's `raised_by` is `sensor_limit`, else `rule`. Source kind per the input; `environment_activated` has no contract source kind, so the loader rejects `trigger` bindings on it until R-E25-20 (no example binding uses it) |
| `trigger` + `replace_cadence` | Effective cadence per 3.5 from the next materialization; recompute for members at once |
| `trigger` + `add_occurrences` | Occurrences per `at_trigger`, `times`, `every_minutes`, `at_clear`, coalesced per 3.9 |
| `trigger` + `add_questions` | Question instances per 3.9.1 |
| `cadence_event` + `replace_cadence` | A cadence activation (no override) for its `until` |
| `cadence_event` + `add_occurrences` | Occurrences, cause `cadence_event` |

A warning source also calls `WarningCommands.attach_routine_overrides` in the same transaction.

Ends (each in the transaction of the input that ends it):

| `until` | Ends when | `end_reason` |
|---|---|---|
| `warning_cleared` | `WarningCleared` for the last warning of `source_chain` with a clear reason other than `superseded` and `config_changed`. `superseded` re-points to the new warning (revision + 1). `config_changed` (CONTRACTS 11: "a warning whose definition is gone clears") sets `awaiting_disposition`: the override stays active and listed, and a crew medical officer may `end` it (R-E25-25) | `warning_cleared`, or `environment_changed` for that clear reason |

Releases never end an override: it keeps its pinned effect when its binding is edited or removed. On end the base
cadence returns with no action by anyone (INV-E25-13); occurrences it created keep their windows.

Texts, rendered at start:

- `reason_text`: `trigger_text` without its trailing `(sensor_limit)` or `(rule)` marker, trimmed.
- `cadence_text`: ui-copy `cadence_words[word]` rendered (`{n}`, `{eva_word}`, `{event}`, `{phase}`) and capitalised,
  followed by `", " + note` when a note exists ("Daily, while CO2 stays above the limit"; "Weekly, live"). The comma is a

  `RoutineTask.cadence_text`.
- `ends.text`: ui-copy `routine_words.ends[kind]` after R-E25-2. Interim: `designed_states.unknown`, logged; E25-02 is
  not done until R-E25-2 is approved (12.2).

### 3.9 Coalescing (DE25-5)

Before creating an added occurrence for person P and item I with window `[f, u)`: when P has an open occurrence of I
whose window covers `f` and `u`, and neither occurrence carries question instances, nothing is created; the new
override is still created and listed and reaches `effect_complete` when that occurrence ends (D20: the walkers'
dust check at 11:40 absorbs the 11:55 alert). An all day occurrence never absorbs a question instance or a repeat.

#### 3.9.1 Question instances (DE25-13)

Each `add_questions` firing creates, per member, one instance per slot: `initial`, and `repeat:<i>` for each
`repeat_after_minutes[i]`. Instances are rows (5.1) with `question_ids` (the set's), `due_from`, `due_until`, carrier
and state.

| Slot | `due_from` | `due_until` | Carrier |
|---|---|---|---|
| `initial`, `attach_to: next_occurrence`, today's daily check not yet started | `source_at` | end of that mission day | Today's daily check: `added_questions` returns the IDs |
| `initial`, today's check started or submitted | `source_at` | `due_from` plus the daily check item's policy window, else end of day | An occurrence of `daily_check_item_id`, cause `override`, key `:q:initial` |
| `repeat:<i>` | `source_at + repeat_after_minutes[i]` (D16: "now and 2 hours later") | as above | An occurrence of `daily_check_item_id`, key `:q:repeat:<i>` |
| `each_occurrence` | each daily check while active | end of that day | That day's daily check |

All slots are created in the trigger's transaction, so a restart or an unanswered first slot never loses a repeat;
repeats crossing midnight belong to the day of their `due_from`. Answers arrive as `AnswerAccepted` (question ID,
person, `daily_check_id`, `answered_at`); an answer counts for the earliest open instance of that person containing that
question whose window contains `answered_at`. An instance is `answered` when every question has an answer of any
presence (including `declined`); at `due_until` an open instance becomes `partially_answered` or `unanswered`. Submitting
or abandoning the carrying check changes nothing about an instance; its carrier occurrence becomes `done` only when its
instance is `answered`, and `missed` with its instance otherwise. Answering added questions after submission is the
E03 rule "question in `repeat_question_ids` and not yet answered"; questions added after the check started need
R-E25-16(b).

### 3.10 Schedule projection

`project_schedule(ctx, range_) -> RoutineScheduleView` (pure):

1. **Rows (DE25-9).** Every open occurrence of the person, of any day; every stored occurrence of today; for periodic
   items with neither, the latest periodic occurrence when its day is in the current period (blocks of `period_days`
   from the anchor), else the next projection (`not_due`); `per_eva` items with no occurrence today, a walk summary row.
   Event and `as_needed` items without an occurrence have no row.
2. **Group.** `today` for an open occurrence or a stored occurrence of today not `not_due`; else the display group of
   the effective cadence word.
3. **Order.** State rank (`due`, `later`, `done`, `skipped`, `missed`, `not_due`), `due_from` (nulls last), file
   position, `occurrence_id`.
4. **Counts.** Over group `today`: `due`, `later`, `done` (today's), `open_today = due + later`.
5. **`days[]`.** Seven mission days ending today; distinct items with at least one stored non `not_due` occurrence;
   distinct items with a `done`; `label` the day's short label.
6. **Range `week`.** Same fields, `groups: []` (matches `examples/routine/week-station.json`).
7. **`active_overrides`.** Active overrides applying to the person, by `started_at`, then ID.
8. **`misses`.** 3.11.

`end_text` follows the CONTRACTS 15 first match table from ui-copy `occurrence_end_text`, with `{time}` the hours and
minutes of `MissionClock.met(at)` and `{day_label}` the profile's inline label; a held occurrence uses `suppressed`.

### 3.11 Misses and the barrier question (DE25-7)

- A miss counts when the occurrence is `missed` with `miss_counted` true and its day lies after the latest barrier ask
  covering the item. `miss_counted` is false for misses ended during an outage, a clock jump or regression (3.13), by
  the successor rule, or on a held window.
- Window per item: the counted misses of item I qualify when `day(last) - day(first) <= w(I)`, where `w(I) =
  max(misses.window_days, (misses.ask_barrier_after_misses - 1) * period_days(I))` for periodic items and
  `misses.window_days` otherwise. With the example policy (2 within 7), weekly misses on days 14 and 21 qualify (span 7),
  monthly misses 30 days apart qualify, daily misses must fall within 7 days. Basis: team default (the example's own
  basis), recorded in R-E25-5(f); R-E25-10 adds a loader warning showing `w(I)` for every periodic item so the reviewer
  sees the effective window.
- When due, the question is offered on the person's next daily check: E25 records `routine_barrier_ask(person,
  item_ids, offered_day)` in the day job or the miss transaction, and `added_questions` returns `misses.question_id` with
  cause `miss` for that day.
- Outcome: `answered` on an `AnswerAccepted` of `misses.question_id` (stored with item IDs for E29); `shown_unanswered`
  when that day's check was submitted without it (the person had it in the check they completed; consumed);
  `not_shown` when the check was abandoned or never started (not consumed: offered again on the next check). The app
  therefore asks once.
- Nothing here reads or writes participation (INV-E25-06).

#### 3.12.3 Versions and activation (DE25-8)

At `ConfigReleaseActivated`, in the activation transaction (UC-T14), for every open occurrence: an item still present is
re-pinned to the new release (revision + 1, transition reason `release_repinned`); a `later` occurrence whose window
came from a policy that changed gets the new window, never ending earlier than its current `due_until`; deadlines move
in the same transaction. An item absent from the new release keeps its occurrence open until its window ends, served
from its pinned release (E01 keeps old releases) and labeled with that release ID. Overrides keep their pinned effect.

Completion records `guidance_release_id`: the `Config-Release` request header when present, else the occurrence's
release. When the header names a release whose `item_content_sha256` differs from the occurrence's release, the action
returns `409 CONFIG_VERSION_MISMATCH` with `current_state` (CONTRACTS 5: "a mutating request that depends on
configuration under a different active release"); the client refetches the steps.

Guidance loader checks G1 to G8 (errors G1 to G6): one sentence `plain`; at least one non-empty step; `instrument`,
`minutes`; `body_region` in the fixed set or null; no amount pattern; every source resolves; every environment has a
cadence; team default cadences listed in `validation.warnings`.

### 3.13 Time

- Source time drives everything (3.7); `received_at` is stored for audit. A late input whose window has passed still
  creates its override (visible under Changed for now) but no occurrence (audit `routine.late_input`).
- Each occurrence and deadline stores the `clock_version` of its creation. Recorded labels never change after a
  correction (SYSTEM 5.3).
- `ClockRegressed` sets `clock_suspect_since`: until `ClockCorrected` arrives, misses are recorded with `miss_counted =
  false` and `days` ends wait (a tightening is never ended by a suspect clock). States never move backward: a `due`
  occurrence whose `due_from` is again in the future stays `due`; the materialization watermark never decreases, so a
  backward correction across midnight never materializes a day twice.
- A forward jump larger than `clock.regression_tolerance_ms` (the same setting, applied forward) recorded by
  `HubLifecyclePort.clock_discontinuities` makes misses inside the jump uncounted.
- Restart: holds and deadlines are recomputed from stored occurrences and overlay intervals in startup phase
  `STATE_SWEEP` (SYSTEM 5.12).

#### 4.3.1 Fault isolation (DE25-14, SYSTEM 8.6 item 2)

Every subscription is registered as a wrapped evaluator. Domain rejections (3.8.1) are normal outcomes. Any other
exception inside E25 rolls back to E25's savepoint; the producer's input and its own effects commit; the platform
records a durable job `routine.reapply` with the event's stored reference; `HealthState.mark_degraded("routine",
"EVALUATION_UNAVAILABLE", since)`. `ReapplyInput` retries with backoff up to `routine.reapply_max_attempts`; the last
failure parks the job (visible in health) and startup retries a parked job once. Existing overrides, occurrences and
warnings are never ended or cleared by a failed evaluation. Storage faults (`StorageUnavailable`) are not evaluator
faults: nothing commits (SYSTEM 8.6 item 3).

migrations are additive only within a mission (DEPLOYMENT 7.4); `crew-health rollback-software` switches the software

#### 5.1.1 Reconciliation across hubs (DE25-17, DEPLOYMENT 4.4)

Each local transition row is a replicated append entry (`origin_node_id`, `origin_seq`, `hlc`); occurrences are not
replicated, since every node derives the same IDs. Timers run only on the person's home hub (DEPLOYMENT 9). Applying a
remote transition (UC-T18): admissibility (3.8.1) and the actor rule of INV-E25-01 first (else quarantine with reason);
a duplicate `(origin_node_id, origin_seq)` is a no-op; then:

| Local state | Remote | Result |
|---|---|---|
| open | any person action | applied as if local |
| `missed` by a timer | `complete` by the person with `completed_at` inside the window | `done`; the miss row stays as history (DEPLOYMENT 4.4 routine special case) |
| `done` or `skipped` by the person | the other person action | later HLC wins; the loser stays as a row with `applied = 0` |
| `done` or `skipped` | a timer miss | never applied; kept as history |
| final | `later` | kept as history only |

The occurrence update carries `reconcile_entry_id`, which the trigger requires (5.1). Interim: one hub (SYSTEM 11);
the reconcile path is built and tested against two databases (T-E25-090).

### 5.2 Configuration reader

`routine/adapters/config_reader.py` builds `RoutineRelease` once per release at activation and keeps the active and
pinned releases (bounded by open occurrences). It reads `routine-schedule`, `routine-rules`, `questionnaires`, `ui-copy`
and `environment-profiles` (`mission_event_types[].label`) only.

### 5.3 Deadlines and the day job

On start and on every timed decision the adapter upserts `routine_deadline` and calls `Scheduler.call_at`. Kinds: `day`
(one transaction per person), `due`, `until`, `ovr_days`, `every` (next slot only), `qi` (question instance end). Each
handler writes `routine_heartbeat` at most every `routine.heartbeat_seconds`. A stale key is a no-op.
