**Decisions this design settles** (brief, "Decisions the TDD must settle"):

| # | Decision | Selected | Alternatives rejected and why |
|---|---|---|---|
| DE25-1 | Cadence vocabulary | Frozen to the nine `cadence_word` keys of `common.schema.json`; each word has exactly one generation rule (section 3.4). Frequencies come only from `routine-schedule.json` (ROUTINE.md) or carry `basis: team default` and the "frequency to be set by the flight surgeon" line | Free cadence strings (untestable); numeric periods in code (breaks rule 1) |
| DE25-2 | Materialization and restart | Occurrences on today or earlier, and every occurrence created by an event, are stored. Future cadence occurrences are projected on read and never stored. IDs are deterministic (section 3.3), so a rerun, a restart or another hub computing the same inputs reproduces them | Precomputing N days ahead (stale after every override, release or environment change; many writes); computing everything on read (person actions need durable revisions) |
| DE25-3 | Due windows | `preferred_time` and `window_minutes` from `item_policies`; trigger instant; walk end; walk start for `before_start`; otherwise all day (00:00 to 24:00 mission time). An occurrence on today whose `due_from` is still ahead is `later`, which is what the CONTRACTS 20 count vectors require (section 3.6, request R-E25-5) | `not_due` for today (fails the station vector 2, 3, 1) |
| DE25-4 | Sleep and walk overlays | While an overlay in `suppressed_overlays` is active, an open occurrence of that person is held as `later` with `suppressed_by_overlay`; when the overlay ends it is due again and `due_until` moves by the held time. A `before_start` walk occurrence is never held by its own walk and ends `missed` when that walk starts (section 3.7) | Moving windows ahead of a planned overlay (a plan is not a fact); dropping the occurrence (silently loses a prompt) |
| DE25-5 | Two triggers on one task | Every binding firing except a cadence event creates its own RoutineOverride, so both stay listed under Changed for now. Cadence: the tightest active periodic override wins, ties by the most recent; an override never makes an item less frequent than its base (non-loosening). Added occurrences: a new one is coalesced into an open occurrence of the same item and person whose window covers it (section 3.9, request R-E25-5) | "Most recent wins" alone (a newer, looser trigger would loosen an active tightening); two copies of the same check (alarm fatigue) |
| DE25-6 | Trigger end | Each override ends on its own by its `until` (warning cleared, effect complete, days, a mission event); `person_stops` only by the named role. A warning superseded by a higher level of the same chain keeps the override (it is re-pointed), so a worsening hazard never ends a tightening | Ending on `superseded` (loosens while the hazard worsens) |
| DE25-7 | Misses | A miss is recorded only for an occurrence the hub showed and whose window passed while the hub was running. Misses caused by an outage or clock jump are recorded but not counted. After `misses.ask_barrier_after_misses` counted misses of one item within `misses.window_days` (team default 2 within 7), the next daily check adds `misses.question_id` once; the association with the items is stored by E25 for the ground log | Counting outage misses (punishes a hub fault); asking every day (nagging) |
| DE25-8 | Guidance format and versioning | `routine-schedule.json` is a configuration document in the release; `GET /v1/routine/tasks/{item_id}` serves the parts from the active release; the client renders them and refetches on `config.release_activated` (section 3.12) | Steps bundled in the client (breaks R43) |
| DE25-9 | Which occurrence represents an item | Today's occurrences; else the item's latest ended occurrence when it lies in the current calendar period of its cadence (anchored at `calendar.anchor`); else the next projected occurrence; walk items without an occurrence today show a walk summary row (section 3.10) | Always the next one (drops "done day 17" of the station example) |
| DE25-10 | Audience | `person`: the person the input names. `all_crew`: the roster of the mission day. `everyone_in_location`: roster members not in an `eva` overlay at the trigger instant, frozen on the override (single site; multi-site per DEPLOYMENT.md) | Recomputing membership later (a person who walks in later would gain a past exposure check) |
| DE25-11 | Deployment calendar anchor | `config/routine-rules.json` uses `anchor: mission_start` so weekly and monthly items keep their stagger across an environment change; the example keeps `environment_start` and both are tested | `environment_start` in flight (every weekly and monthly task falls due on landing day, the busiest day) |
| DE25-12 | What the assistant may change | One occurrence of an existing item, for the insight's person, due today, cause `assistant` with the insight ID, through `AssistantRoutinePort.add_recheck`. ## 3. Domain model

All code in `crew_health/routine/domain/` is pure: no I/O, no clock reads, no framework imports. Types are frozen
dataclasses with slots or `enum.StrEnum`; generated Pydantic models from the contracts appear only at the API edge.

### 3.4 Cadence and generation rules

`Cadence(word, n, event, phase, note)` is `common.schema.json#/$defs/cadence`. Period in days, from configuration only:

| Word | `period_days(calendar)` | Occurrences |
|---|---|---|
| `continuous` | 1 | One per day; completed automatically by an accepted observation of the item's codes (after R-E25-1; interim: completed by the person) |
| `daily` | 1 | One per day |
| `every_n_days` | `n` | One on the next periodic day (below) |
| `weekly` | `calendar.week_days` | One on the next periodic day |
| `monthly` | `calendar.month_days` | One on the next periodic day |
| `per_eva` | `None` | From the person's walks, per `item_policies[item].per_eva`: `before_start`, `after_end` or `both`. An item whose effective cadence is `per_eva` with no `per_eva` policy stays manual (loader warning, R-E25-10) |
| `after_event` | `None` | Only from a `cadence_event` binding of the item; none otherwise (manual) |
| `mission_phase` | `None` | Only from a `cadence_event` binding of the item; none otherwise (manual) |
| `as_needed` | `None` | Never scheduled; only from triggers, bindings, the assistant or (after R-E25-8) the person |

Next periodic day (CONTRACTS 15): `candidate = last_ended_day + period` where `last_ended_day` is the mission day of the
person's latest `done`, `skipped` or `missed` occurrence of the item on or after the anchor day; with none,
`candidate = anchor_day` (environment day 1 or mission day 1 per `calendar.anchor`). The occurrence day is
`max(candidate, first_unshown_day)`, where `first_unshown_day` is today when today has no stored occurrence of the item,
else today plus one. A slot that fell on a day the hub never showed therefore moves to today, never to a miss (DE25-7).

### 3.5 Effective cadence and non-loosening (DE25-5, INV-E25-04)

```python
def effective_cadence(item: RoutineItem, environment_id: str, active: Sequence[OverrideView],
                      calendar: Calendar) -> EffectiveCadence:
    """Returns (cadence, governing_override_id | None, additive: tuple[OverrideView, ...])."""
```

1. `base = item.cadence_for(environment_id)`.
2. Candidates: active `replace_cadence` overrides (bound or manual) that apply to the person.
3. A candidate with a periodic word replaces the base only when `base` is not periodic or `period(candidate) <=
   period(base)`. Among replacing candidates the smallest period wins; ties go to the latest `started_at`, then the
   larger `override_id`. The winner is `governing_override_id`.
4. A candidate whose word is `per_eva` is additive: walk occurrences are added and the base continues.
5. A candidate whose word is `after_event`, `mission_phase` or `as_needed` (event words), or a periodic candidate looser
   than the base, never replaces the base: at its start it adds one occurrence due at once (`:at_trigger`), and it stays
   listed under Changed for now with its words. This is how a manual "measure now" trigger works without stopping the
   weekly cadence.

CONTRACTS 15 says "the most recent active override"; rule 3 refines it so that a newer, looser trigger never loosens an
older, tighter one (request R-E25-5).

### 3.6 Occurrence entity and state machine

```python
@dataclass(frozen=True, slots=True)
class Occurrence:
    occurrence_id: str; revision: int; person_id: str; item_id: str; environment_id: str
    mission_day: int; cause: Cause; cause_key: str; question_set_ids: tuple[str, ...]
    state: OccurrenceState; due_from: datetime | None; due_until: datetime | None; due_kind: DueKind
    suppressed_by_overlay: str | None; suppressed_since: datetime | None
    completed_at: datetime | None; outcome: Outcome | None; skip: Skip | None
    miss_counted: bool; config_release_id: str; origin_mode: str   # internal: mission namespace at creation
```

| From | Input | To | Actor | Guard |
|---|---|---|---|---|
| (new) | Materialize for a future day | `not_due` | scheduler | Stored only when created by an event (walk, binding); cadence occurrences of future days are projected, never stored |
| (new) or `not_due` | Day of the occurrence starts, or creation on today | `later` if `now < due_from`, else `due` | scheduler | `now < due_until`; otherwise it is not created (an occurrence whose window already passed is never created, audit `routine.occurrence_not_created`) |
| `later` | Clock reaches `due_from`, not suppressed | `due` | scheduler | |
| `due` | `later` with `later_until` | `later` (`due_from = later_until`, `due_kind = specific`) | the person | `now < later_until <= due_until` |
| `due`, `later` | A suppressing overlay of the person is active | `later` with `suppressed_by_overlay`, `suppressed_since = max(due_from, overlay start)` | scheduler | Not a `before_start` occurrence of that same walk |
| `later` (held) | That overlay ends at `e` | `due` if `e >= due_from`, else `later`; `due_until += e - suppressed_since`; `due_from = max(due_from, e)` | scheduler | |
| `due`, `later` | `complete` | `done` with `completed_at`, `outcome` | the person, or an auto-complete rule linking that person's accepted evidence (R-E25-1), or E31 for a drill | `completed_at <= now` and within the occurrence's mission day or window |
| `due`, `later` | `skip` with a reason | `skipped` with `skip`, `outcome = null` | the person | No `observation_ids` or `answer_ids` in the body |
| `due`, `later` (not held) | Clock reaches `due_until` | `missed`, `miss_counted` true when the hub was running at `due_until` | scheduler | |
| `later` (`before_start`) | Its walk starts | `missed` | scheduler | |
| `done`, `skipped`, `missed` | anything | rejected `INVALID_TRANSITION` | | Final (INV-E25-01) |

`allowed_actions` (computed per session, never inferred by the client): the occurrence's own person sees
`complete, skip, later` in `due`; `complete, skip, later` in `later` when not held; `complete, skip` while held; nothing
in `not_due` and in final states; any other session sees nothing (and cannot see the occurrence at all, section 3.13).

Every transition increments `revision`, appends one `routine_occurrence_transition` row and one outbox event
`routine.occurrence_changed`.

### 3.7 Due windows (DE25-3, DE25-4)

`window(item, policy, day_bounds, trigger_at, walk) -> (due_from, due_until, due_kind)`:

| Case | `due_from` | `due_until` | Kind |
|---|---|---|---|
| Policy with `preferred_time` | that mission time on the day | `due_from + window_minutes`, or the end of the day when `null` | specific |
| Created at a trigger instant `t` | `t` | `t + window_minutes` when the item has a policy window, else the end of `t`'s mission day | specific |
| `times[]` entry `(day_offset, local_time)` | that mission time on trigger day + offset | as above | specific |
| `every_minutes` slot `k` | `t + k * every_minutes` | the next slot's `due_from` | specific |
| `per_eva` `after_end` | the walk's end | `due_from + window_minutes`, or the end of that day | specific |
| `per_eva` `before_start` | `planned_start - window_minutes`, or the start of the walk's day when `null` | the walk's `started_at` when it started, else `planned_start` | specific |
| `repeat_after_minutes` value `m` | first answer time of the set + `m` | as for a trigger | specific |
| Otherwise | start of the day | end of the day | all_day |

The occurrence's `mission_day` is the day that contains `due_from`. `due_until` can cross midnight only through a
suppression shift. All times are mission-clock instants in UTC; `HH:MM` strings come only from configuration.

### 3.8 Overrides and bindings

```python
@dataclass(frozen=True, slots=True)
class Override:
    override_id: str; revision: int; item_id: str; person_id: str | None; audience: Audience
    member_ids: tuple[str, ...]              # frozen at start; internal (DE25-10)
    binding_id: str | None; trigger_index: int; trigger_text: str; started_by: StartedBy
    source: SourceRef; source_chain: tuple[str, ...]   # warning IDs in a supersede chain
    effect: BindingEffect                    # pinned copy of the binding effect, or replace_cadence for manual
    new_cadence: Cadence; cadence_text: str; reason_text: str
    state: Literal["active", "ended"]; started_at: datetime; ends: Ends
    ended_at: datetime | None; end_reason: EndReason | None
    basis: str; source_ids: tuple[str, ...]; config_release_id: str
```

Binding evaluation is a pure function:

```python
def match_bindings(release: RoutineRelease, inp: TriggerInput, environment_id: str) -> tuple[Firing, ...]
```

`TriggerInput` is one of `WarningRaisedInput(definition_id, warning_id, scope, person_id, location, origin_mode, at)`,
`MissionEventInput(event_type, event_id, person_ids, at)`, `OverlayInput(kind, change: ended|planned, overlay_id,
person_id, at)`, `AnswerInput(question_id, presence, answer_id, person_id, at)`, `ObservationInput(code, value, unit,
observation_id, person_id, quality_status, at)`, `EnvironmentActivatedInput(environment_id, profile_id, at)`.

| `on` kind | Fires when |
|---|---|
| `warning_raised` | `definition_id in definition_ids` |
| `mission_event` | `event_type in event_types` |
| `overlay_ended`, `overlay_planned` | the overlay kind matches and the change matches |
| `answer` | `question_id` equal and `presence in presence` |
| `observation` | `code` equal, `quality_status == accepted`, `unit` equal to the binding `unit` (a different unit never fires: audit `routine.binding_unit_mismatch`), comparator holds |
| `environment_activated` | `environment_id in environments` |

A `cadence_event` binding fires only when its `environment_id` is `null` or equals the active environment.

For each firing, in the same transaction:

| Binds and effect | Result |
|---|---|
| `trigger` + any effect | One RoutineOverride with ID `override_id(binding_id, source kind, source ref, audience_key)`; a replay of the same input finds it and does nothing. `new_cadence`: the trigger's `new_cadence` (`replace_cadence` requires `effect.cadence` to equal it, R-E25-10). `trigger_index`, `trigger_text`, `source_ids`, `basis` from the trigger. `started_by`: `sensor_limit` for a warning whose `raised_by` is `sensor_limit`, `rule` otherwise |
| `trigger` + `replace_cadence` | Effective cadence per section 3.5 from the next materialization; a recompute runs for the members at once |
| `trigger` + `add_occurrences` | Occurrences per `at_trigger`, `times`, `every_minutes`, `at_clear` with cause `override`, coalesced per 3.9 |
| `trigger` + `add_questions` | A question attachment to the bound item's next open or next materialized occurrence (`next_occurrence`) or to every occurrence while active (`each_occurrence`); repeats per DE25-13 |
| `cadence_event` + `replace_cadence` | No override: a cadence activation `(binding_id, person, source_ref, started_at, until)` makes the item's cadence `effect.cadence` for its `until`; occurrences carry cause `cadence_event` with `binding_id` |
| `cadence_event` + `add_occurrences` | Occurrences with cause `cadence_event` and `binding_id`, coalesced per 3.9 |

When the source is a warning, E25 calls `WarningCommands.attach_routine_overrides(uow, warning_id, override_ids)` in the
same transaction (E24 UC-R7).

Override texts, rendered when the override starts:

- `reason_text`: `trigger_text` with a trailing marker `(sensor_limit)` or `(rule)` removed (the markers are defined in
  `config-routine-schedule.schema.json`) and white space trimmed: "Habitat dust monitor alert".
- `cadence_text`: the cadence's `note` with its first letter capitalised when `note` is present; otherwise ui-copy
  `cadence_words[word]` rendered with `{n}`, `{eva_word}`, `{event}`, `{phase}` and capitalised ("Weekly", "Per
  surface walk"). The same rule renders `RoutineTask.cadence_text`.
- `ends.text`: ui-copy `routine_words.ends[kind]` with `{n}` (days), `{role}` (role word), `{event}` (mission event
  label) after request R-E25-2. Interim: `designed_states.unknown`, logged (CONTRACTS 11 missing value rule).
- `ends.at`: `started_at + days * day_length_seconds` for `days` (the active profile's `day_label.day_length_seconds`,
  so "3 days" means three sols on a Mars profile set to sols); `null` for the other kinds.

Ending (each in the transaction of the input that ends it, `end_reason` from the schema enum):

| `until` | Ends when | `end_reason` |
|---|---|---|
| `warning_cleared` | `WarningCleared` for the last warning of `source_chain` with a clear reason other than `superseded`; a `superseded` clear re-points the override to the new warning (`previous_warning_id` link), revision + 1 (DE25-6) | `warning_cleared`, or `environment_changed` when the clear reason is `environment_changed` |
| `effect_complete` | Every occurrence and question attachment the override added is final (done, skipped, missed; an attachment is final when the daily check carrying it is submitted or abandoned) | `effect_complete` |
| `days` | Clock reaches `ends.at` (deadline) | `days_elapsed` |
| `person_stops` | `end` by a session holding `until.role` (manual overrides: crew medical officer or ground) | `stopped_by_person` |
| `mission_event` | An event of `event_types` is recorded | `mission_event` |

On end, the next materialization uses the base cadence again (no manual reset, INV-E25-13). Occurrences the override
already created stay as they are: an open one keeps its window and can still be done; it is never deleted or rewritten.

### 3.9 Coalescing (DE25-5)

Before creating an added occurrence for person P and item I with window `[f, u)`: if P has an open occurrence of I whose
window covers `f`, nothing is created; the existing occurrence keeps its cause, the new override is still created and
listed, and both overrides reach `effect_complete` when that occurrence ends. Example (D20): the walkers' dust check
created by `dust_exposure_check.after_surface_walk` at 11:40 absorbs the 11:55 dust alert, while Mara and Tomas get a new
one. Question sets attached to one occurrence are a set union.

### 3.10 Schedule projection

```python
def project_schedule(ctx: ScheduleContext, range_: Literal["today", "week"]) -> RoutineScheduleView
```

`ScheduleContext` holds the person, now, today's `DayLabels`, the release, stored occurrences of the person (today and
the 7-day window, and each item's latest ended occurrence), active overrides applying to the person, cadence
activations, the person's planned walks and `walks_since_activation`.

1. **Representative rows per item (DE25-9).** Every stored occurrence on today. Else, for periodic cadences, the
   latest ended occurrence when its day lies in the current calendar period (blocks of `period_days` counted from the
   anchor day); else the next projected occurrence (`not_due`, `due_from` and `due_until` null). For `per_eva` items
   with no occurrence today, a walk summary row (cause `per_eva`, cause key `walk_summary`, today's day, `not_due`,
   `allowed_actions` empty). Items with an event or `as_needed` word and no stored occurrence have no row (they are in
   `GET /v1/routine/tasks`). With the station fixture this reproduces "done day 17" for the weekly wellbeing check (day
   17 is in block 15 to 21) and "day 21" for body mass (done day 14 is in the previous block).
2. **Group.** `today` when the occurrence is on today's mission day and not `not_due`; otherwise the display group
   whose `cadence_words` contain the effective cadence word (first match; R-E25-10 makes it unique).
3. **Order within a group.** State rank (`due`, `later`, `done`, `skipped`, `missed`, `not_due`), then `due_from`
   (nulls last), then the item's position in `routine-schedule.json`, then `occurrence_id`.
4. **Counts.** Over today's group: `due` and `later` count occurrences in that state; `done` counts today's done;
   `open_today = due + later`. Skipped and missed are not counted.
5. **`days[]`.** The seven mission days ending today; for each day, `due` is the number of distinct items with at least
   one stored occurrence that day in any state but `not_due`, `done` the number of distinct items with at least one
   `done` occurrence that day; `label` is the day's `short_label`.
6. **Range `week`.** Same `day`, `counts`, `days`, `active_overrides` and `misses`; `groups` is empty, matching
   `examples/routine/week-station.json`. The week's occurrences are listed by `listOccurrences?range=week`.
7. **`active_overrides`.** Active overrides that apply to the person, ordered by `started_at` then `override_id`: this
   is Changed for now.
8. **`misses`.** Section 3.11.

`end_text`, first match (CONTRACTS 15), rendered from ui-copy `occurrence_end_text`:

| Case | Key and placeholder values |
|---|---|
| `done`, completed on today | `done_today`, `{time}` = mission time of `completed_at` |
| `done`, earlier day | `done_earlier`, `{day_label}` = inline label of the occurrence's day |
| `skipped` | `skipped`, `{reason}` = ui-copy `skip_reasons[skip.reason]` |
| `missed` | `missed` |
| Held by an overlay | `suppressed`, `{overlay}` = ui-copy `overlay_words[overlay]` |
| `later` | `later`, `{time}` = mission time of `due_from` |
| `due`, `due_kind` specific | `due_now` |
| `due`, all day | `due_today` |
| Walk summary, no walk planned for the person | `no_walk_planned` |
| Walk summary, a walk planned; `walks_since_activation == 0` | `first_walk`, `{day_label}` of the planned walk's day |
| Walk summary, a walk planned; walks already happened here | `next_walk`, `{day_label}` of the planned walk's day |
| Any other `not_due` | `not_due`, `{day_label}` of its day |

### 3.11 Misses and the barrier question (DE25-7)

`misses.evaluate(person, item_history, policy, asks, now) -> MissesView`:

- A miss counts when the occurrence is `missed`, `miss_counted` is true, it ended within the last
  `policy.window_days` mission days, and it ended after the latest barrier ask covering that item.
- `barrier_question_due` is true when any item has at least `policy.ask_barrier_after_misses` counted misses and no
  ask is pending for it. `count` is the largest counted-miss count over the person's items; `window_days` is copied.
- When due, `DailyCheckAdditionsPort` adds `policy.question_id` to the person's next daily check and records a
  pending ask `(person, item_ids, daily_check_id)`. The ask is consumed when that daily check is submitted or abandoned,
  answered or not: the app asks once. An answer to the question (`AnswerAccepted`) is stored with the item IDs and
  exposed to E29 through `RoutineCatchUpPort` so it goes into the next log for the ground (UC13).
- Nothing here reads or writes participation: the streak, patches and crew goal are untouched (INV-E25-06).

Versioning: `routine-schedule.json` is one of the documents a ConfigRelease pins (its version is the SHA-256 of its
bytes). Editing a step, a cadence or a source in the document and activating a release changes `GET
/v1/routine/tasks/{item_id}` at once; clients refetch after `config.release_activated`. Occurrences keep the
`config_release_id` they were computed under; the steps a person reads are always the active release's (the brief's
"an edited step reaches the screen"). Rollback is activating the previous release.

Guidance checks registered with the loader (E25-03 evidence; errors reject the release, warnings are listed): G1 every
item has `plain` of exactly one sentence (CONTRACTS 13 sentence rule); G2 at least one step, every step non-empty; G3
`instrument` and `minutes` present; G4 `body_region` in the fixed set or `null`; G5 no amount pattern in any step
(loader check 3's pattern); G6 every source ID resolves (loader check 2); G7 every environment has a cadence (schema);
G8 a cadence with `basis: team default` is reported in `validation.warnings` as "frequency to be set by the flight
surgeon" so the list of pending frequencies is visible to the reviewer. G1 to G6 are errors.

### 5.2 Configuration reader

`routine/adapters/config_reader.py` builds `RoutineRelease` (section 3.2) once per `config_release_id`, cached; rebuilt
on `ConfigReleaseActivated`. It reads `routine-schedule`, `routine-rules`, `questionnaires` (`question_sets`, question
IDs), `ui-copy` (keys in section 8), `environment-profiles` (`mission_event_types[].label`) and nothing else. Parsing
cost is paid at activation, never on the request path (AGENTS code rule 3).

### 5.3 Deadlines and the day job

On start (UC-T15) and on every decision that sets a time, the adapter upserts `routine_deadline` and calls
`Scheduler.call_at(key, due_at, handler)`. Kinds: `day` (next mission day start: UC-T10 for every roster person, one
transaction per person so the writer lock is short), `due` (`later` to `due`), `until` (to `missed`), `ovr_days`
(override end), `every` (next `every_minutes` slot, created one at a time). A deadline whose target already moved is a
no-op. Clock source: the injected clock; tests drive it.

### 5.4 Bounds and external calls

E25 makes no network, device, model or subprocess call. Per input: at most `len(bindings)` binding checks; per person
and day at most `len(items) + added occurrences`, capped by the hub setting `routine.max_occurrences_per_person_day`
(E01 settings, default 500: a safety bound far above any configured content, logged and audited when hit); `every`
slots are created one at a time; `repeat_after_minutes` is bounded by the list length in configuration; recompute
loops are bounded by roster size times item count; no recursion. Domain event handlers run synchronously; the E01 bus
rejects reentrancy deeper than 4.

## 9. Deployment and fallbacks

This assumes the charter's model until DEPLOYMENT.md lands: one hub process on one laptop; clients are browsers on that
laptop or on crew tablets on the habitat network; the ground link is delayed store and forward. The deployment research
(vehicle-computing.md 3.1 and 3.5; surface-mobility-comms.md 7) adds that the minimum setup is also the realistic flight
configuration (the ISS Medical Equipment Computer, an Orion crew tablet), that each place a crew sleeps or works for
hours may run its own hub, that hubs restart after faults every few weeks, and that NASA's own self-scheduling tool
(Playbook, CAST) syncs flat files with "crew changes win". E25 is shaped by those facts in four ways: deterministic IDs
(two hubs converge), no miss for an unseen window (restarts are routine), nothing reads the link, and a printable task
card from the same configuration (the ISS checklist fallback when the medical computer is down).

| Tier | What the routine does |
|---|---|
| Minimum: one laptop and its webcam, no devices, no sensors, no model, link down | Full scheduler in the hub. Each crew member signs in on the laptop as themselves; a `station` session shows no personal routine. Pulse and breathing tasks record from the webcam (E06) or by hand; cuff, oximeter, thermometer and scale tasks record by manual entry or Not available with its reason. Sleep and walks are recorded as mission events by the crew (`sleep_started`, `eva_started` in environment-profiles), so suppression works with no band. Sensor bindings never fire (no channel); answer, mission event, overlay and environment bindings work |
| One device only (an Orion class crew tablet running the hub and the browser) | Same as minimum (vehicle-computing 3.1 item 3) |
| Laptop plus crew tablets | Each tablet signed in as its owner shows that person's To do and Routine; events arrive by SSE; a tablet that loses the hub keeps its last schedule dimmed with `as_of` and prints task cards from its cached configuration |
| Wrist band | Its adapter records `sleep_started` and `sleep_ended` (`who_may_record` includes `adapter`), so tasks hold during sleep automatically; the sleep observation feeds the short-sleep binding (after R-E24-5) |
| Habitat sensors | Sensor warnings start bindings (CO2, dust, radiation storm); REPLAY channels start overrides only for the mission's roster namespace (section 10, H10) |
| Several hubs (habitat, pressurized rover, a second module) | Per DEPLOYMENT.md: a person's routine runs timers on their current home hub only; other hubs hold replicas. Deterministic occurrence and override IDs make replicas converge; a person's action replicated from another hub with `completed_at` inside the window takes precedence over a timer miss on a hub that did not see it (housekeeping last writer wins by hybrid logical clock, the losing write kept in `routine_occurrence_transition`). Request R-E25-17 |
| Ground | Reads routine facts only through the catch-up log (E29). A ground manual override arrives as a new record when the link carries it and applies on arrival (it only tightens); nothing on board waits for it (CONTRACTS 9). Whether the ground's `createOverride` is a live call or a bundle record is per DEPLOYMENT.md |
| Mars | Day labels come from the profile (sols). `until: days` uses the profile's `day_length_seconds`; occurrences are keyed by mission day per CONTRACTS 15; a sol based routine day is request R-E25-13 |

## 10. Safety, security and privacy

| ID | Hazard (what could harm or mislead) | Cause | Mitigation | Test |
|---|---|---|---|---|
| H1 | A task that was not done shows as done | A default, a retry, a sync, an import | Final states final in domain and SQLite; `done` needs an actor of 3.14 INV-E25-01; no sentinel values; idempotency | T-E25-001, 002, 018 |

| H6 | Shame or pressure to fake completion | Miss counters on screen; streak coupling | No miss counts on screens; one question; participation never reads routine (import-linter) | T-E25-011, 012, 067 |

Authorization: session identity and roles only (E02); client or model supplied IDs are never authority. Private data:
skip notes, completion notes and manual override notes are visible only to those who can see the object; they never
reach audit, prompts, retrieval or the event stream of others; `RecordFactsPort` facts for an occurrence (used by E24
insight evidence) exclude notes. The journal is never read. What the assistant may do in this epic: add one recheck
occurrence of an existing item for the insight's person, due today. It may not: skip, complete, postpone, end,
re-cadence, start an override or read another person's routine.
