## 1. Scope

**What E13 is.** The workflow controller of LLM-ARCHITECTURE section 2: it owns conversations, turns, the bounded
evidence-seeking loop, the assessment job and its verification, insights, the runtime state the hub reports, and the
inference scheduler. The model only proposes; E13 validates every proposal with deterministic code (through E12, E24
and E26) before anything is stored, shown or applied. Nothing in the safety core calls E13: with the model stopped,
E13 answers `MODEL_UNAVAILABLE` and every other flow is unchanged (charter section 5).

## 3. Domain model

Pure code in `hub/src/crew_health/assistant/domain/`: frozen dataclasses with slots, `StrEnum` states, no I/O, an
injected clock and ID factory.

### 3.1 Conversation and context

`Conversation` mirrors `conversation.schema.json`: `conversation_id`, `revision` (starts at 1, plus 1 on every message
appended and every state change), `person_id` (always the session person; never from the request body), `context
{kind, ref_id}`, `state` (`open`, `closed`), `model_release_id` and `config_release_id` (pinned at open), `created_at`,
`active_turn_id`, `allowed_actions` (computed by the hub).

At most one open conversation exists per `(person_id, context.kind, context.ref_id)`; opening again returns it
(section 6). The context decides the subject, the phase set, the snapshot source and what the assistant may say:

| `context.kind` | `ref_id` | Who may open (besides role crew or crew_medical_officer) | Subject (`ToolScope.subject_person_id`) | Phases (E12 3.3) | Assistant message form | Snapshot source (3.4) |
|---|---|---|---|---|---|---|
| `episode` | episode ID, required | E15 `visible_to(actor)` and (actor is the patient, or holds `crew_medical_officer`) | the episode's `patient_id` | `intake` in the conversation; `assessment` then `disposition` in the assessment job | Actions only: `ask` from configured questions, `request_measurement`, `request_review`, `stop_incomplete`, `assessment`; never free text (INV-E13-13) | Episode `revision` and E11 urgency token |
| `help_session` | help session ID, required | E26 snapshot: session open and actor is the opener, a helper or the subject | the snapshot's `subject_person_id` | `help` | Text (guarded by E26 G0 to G5) or `request_measurement` | Help session node and state (3.4) |
| `general` | null | any | the session person | `general` | Text | Conversation revision |
| `reading` | observation ID owned by the session person | owner check through E12 `ObservationFactsPort.owner_of` | the session person | `general` | Text | Conversation revision |
| `warning` | warning ID | E24 `WarningQueries.visible(session, warning_id)` | the session person | `general` | Text; never a level or a warning action (E24 guard) | Conversation revision |
| `insight` | insight ID owned by the session person | own table | the session person | `general` | Text ("Why is this?") | Conversation revision |

A crew medical officer opening an episode conversation for a crewmate works on that crewmate's facts with the
officer's session; E15 visibility and E02 consent decide it, never the model.

### 3.2 Turns, segments and their states

A **turn** is one run of the controller loop for one trigger. A **step** is one inference call inside a turn (it yields
tool calls or a final output). The step budget of a turn is the **segment** of LLM-ARCHITECTURE section 5: it ends when
the turn needs a human (an answer or a measurement) and resumes in a new turn when the result arrives.

| Turn kind | Trigger | Phase | Ends with |
|---|---|---|---|
| `conversation` | `person_message`, `reply`, `answer`, `measurement_result` | `intake` (episode) or `general` | One assistant message (text or action), or a notice |
| `assessment` | `assessment_request` (startAssessment or a `ready` output) | `assessment` then `disposition` | An Assessment, a job state and, in an open episode conversation, an `assessment` action message |
| `help` | `help_request` (E26) | `help` | One assistant message and one sink call |
| `insight` | `daily_check` | `insight` | Zero or one Insight |
| `benchmark` | E18 evaluation composition only | `benchmark_readonly` tool profile | A `BenchmarkAnswer`; nothing stored in product tables |

Turn state machine (`TurnState`):

| From | Event | To |
|---|---|---|
| `queued` | the worker takes it | `running` |
| `queued` | cancel; E11 cancel; evicted by a help turn; runtime lost; hub restart | `cancelled` (the first two), `failed` (the others) |
| `running` | output passed 3.6 (and 3.7 or 3.8) | `committing` |
| `running` | preempted by a help turn, `preemptions < max_preemptions` | `queued` (`preemptions + 1`) |
| `running` | preempted with `preemptions = max_preemptions` | `failed` (`MODEL_UNAVAILABLE`) |
| `running` | snapshot changed (3.4) | `stale` |
| `running` | a deadline of 3.5 passed | `timed_out` |
| `running` | policy, scope, form or schema failure (3.6) | `rejected` |
| `running` | cancel; E11 cancel | `cancelled` |
| `running` | runtime lost; port failure; hub restart | `failed` |
| `committing` | commit transaction succeeded | `completed` |
| `committing` | authoritative snapshot check failed | `stale` |
| `committing` | storage error; hub restart | `failed` |

Every pair not in the table raises `InvalidTurnTransition`. Terminal states are `completed`,
`cancelled`, `timed_out`, `rejected`, `failed` and `stale`. The commit point is the transaction of 4.2 step 9; a cancel
that arrives after it is answered with the completed result (409 `INVALID_TRANSITION` on `cancelTurn`, section 6).

Message mapping. `turn.started` carries a `message_id` (stream schema), so the assistant message row is written at
start with `status: streaming`, `text: null`, `action: null`; the terminal state fills it:

| Turn state | That message | Extra `notice` message (ui-copy words, request R-E13-4) |
|---|---|---|
| `completed` | `complete`, text or action, `evidence`, `limitations` | none |
| `cancelled` | `cancelled`, no text, no action | `assistant_words.notice_cancelled` |
| `stale` | `cancelled`, `error_code: STALE_VERSION` | `assistant_words.notice_stale` |
| `timed_out` | `timed_out`, `error_code: MODEL_TIMEOUT` | `assistant_words.notice_timed_out` |
| `rejected` | `rejected`, `error_code: MODEL_OUTPUT_REJECTED` or `MALFORMED_MODEL_OUTPUT` | `assistant_words.notice_rejected` |
| `failed` | `failed`, `error_code: MODEL_UNAVAILABLE` or `INTERNAL_ERROR` | `assistant_words.notice_unavailable` with the help alternative |

A rejected, cancelled, timed out or stale turn leaves only these two messages: no request, gap, review, handoff draft,
guided check, assessment or insight (INV-E13-05, through E12 INV-E12-13).

### 3.3 Model step and the turn output

Each step sends E17's `PromptBundle` (messages, the phase's tools, the output schema) and receives a `StepResult`
(E17 4.2): parsed tool calls, or a parsed final output that validates against E17's
`model/schemas/turn-output.schema.json`. Raw text and thinking never reach E13 (E17 discards thinking and returns only
token counts).

```python
class OutputKind(StrEnum):
    TEXT = "text"        # contexts general, reading, warning, insight, help_session
    READY = "ready"      # episode intake only: enough information to assess
    STOP = "stop"        # any context: the model cannot make progress; missing items as codes

@dataclass(frozen=True, slots=True)
class FinalOutput:
    kind: OutputKind
    text: str | None                       # TEXT only, at most 2000 characters (E26 G5 bound)
    evidence_refs: tuple[EvidenceRefIn, ...]   # TEXT only: IDs the text relies on
    reason: str                            # always; checked by the output policy
    missing_codes: tuple[str, ...]         # STOP only: capability codes or question IDs, rendered by the hub
```

**Terminal tools.** In episode and help contexts the model acts through proposal tools (E12 4.3). A proposal tool call
whose result is accepted ends the model loop for this turn; the controller builds the ModelAction from the tool's
validated arguments and hub data:

| Terminal tool (result) | Context | ModelAction stored on the assistant message |
|---|---|---|
| `propose_question` (`ok`) | episode, intake | `ask`: `question` and `choices` are the configured text and choice labels of `questionnaires.json` for the proposed `question_id`, verbatim; `reason`, `decision_affected` from the call |
| `propose_measurement` (`ok`, would create) | episode intake, help | `request_measurement`: `capability_code`, `body_region`, `condition_ids`, `reason`, `decision_affected`, after `EffectApplier` created the request at commit |
| `propose_review` (`ok`) | episode, disposition | `request_review`: `to: crew_medical_officer`, `note` (policy checked), `also_tell_ground` omitted (3.6) |
| `draft_assessment` (`ok`) | assessment job | none at once; the verified Assessment, then an `assessment` action message (3.7) |
| final output `STOP` | any | `stop_incomplete`: `missing` rendered by the hub from `missing_codes` (capability words, question text, gap text); `reason` from the output |
| final output `READY` | episode, intake | no assistant action; a `notice` (`assistant_words.assessment_started`) and an assessment job (3.2) |

A `propose_measurement` whose kit check is false (`status: not_aboard`) is not terminal: the turn continues, the next
step sees the result with `kit_check.text` as a limitation, and the pending effect records the `unavailable` request
and its gap at commit (E27 4.5, CONTRACTS 17 step 3). This is E13-01's "unavailable result changes next step".

The model never writes `state_snapshot_version`: the controller fills it from the turn's pinned snapshot (3.4). The
ModelAction `retrieve_evidence` is never stored on a message; it is a tool call (E12 alias of `search_evidence`).

### 3.4 Snapshot version and staleness

`state_snapshot_version` of a turn is pinned at `queued → running`:

| Context | `state_snapshot_version` | Material fingerprint pinned with it | Stale when, at the checks below |
|---|---|---|---|
| `episode` | E15 Episode `revision` | `ContextSnapshot.snapshot_sha256` of the turn's first context build (E12 3.9) and the E11 `UrgencyToken` | A rebuilt context hash differs, or `still_valid(token)` is false |
| `help_session` | `HelpSessionSnapshot.revision` | the snapshot's `state` and `node` | The session is not open, or its node (flow) differs |
| other | Conversation `revision` | the conversation revision itself | Another message was appended (only possible after a cancel) |

The Episode revision moves on every Episode change, including the link E15 writes for this turn's own assessment (E15
4.4), so a raw revision comparison would mark every result stale. The fingerprint therefore compares what the model
could see: the context hash covers the allowlisted sections (concern, red flags, answers, accepted observations,
attempts, capabilities, open gaps, environment, plan, allergies) and nothing E13 itself writes.

Checks: (a) before every step, cheaply (revision unchanged means no rebuild), to stop a doomed turn early; (b) inside
the commit transaction, authoritatively, before effects are applied. A failed check makes the turn `stale`; nothing is
applied (CONTRACTS 6, V30). An assessment already stored becomes `stale` when E15 calls `mark_stale` (a cited record
was corrected, E15 DE15-8) or when E11 opens a new urgency cycle on its episode (E13 subscribes to `UrgencyChanged`).
`startAssessment` compares its body's `state_snapshot_version` with the current Episode revision and answers 409
`STALE_VERSION` when they differ (the client must have seen the current episode).

### 3.5 Loop budgets and stop conditions

| Bound | Source | Initial value | On reaching it |
|---|---|---|---|
| Steps per turn (the segment) | assistant-policy `max_iterations` | 8 | `stop_incomplete` with the hub's missing list (conversation) or the incomplete assessment (job) |
| Tool calls per turn | the same `max_iterations`, enforced by E12 | 8 | E12 `BudgetExhausted`; same as above |
| Schema repairs per turn | assistant-policy `max_schema_repairs` | 1 | `rejected`, `MALFORMED_MODEL_OUTPUT` |
| Wall time per turn, from `running` | assistant-policy `turn_timeout_seconds` | 90 s (team default) | `timed_out`, `MODEL_TIMEOUT`; the job leaves the incomplete assessment |
| First token per step (thinking included) | assistant-policy `first_token_timeout_seconds` | 20 s | Same as wall time |
| Tool call | assistant-policy `tool_timeout_seconds`, by E12 | 10 s | Result `unavailable`, limitation `tool_timeout` |
| Output and thinking tokens per step | E17 release `decoding` | measured by E17 (P6) | E17 returns `finish_reason: length`; treated as malformed |
| Queued turns, all classes | E17 release `runtime.max_queued_turns` | 8 (team default) | 503 `MODEL_UNAVAILABLE` at send (3.10) |
| Preemptions per turn | E17 release `runtime.max_preemptions` | 2 (team default) | `failed`, `MODEL_UNAVAILABLE` |
| Conversation turns per episode | `controller.max_turns_per_episode` (request R-E13-5; interim E17 release `controller` block) | 12 (team default) | Intake outputs other than `READY` and `STOP` are refused; the turn ends `stop_incomplete` |
| Retrievals adding no new passage, in a row | `controller.max_retrievals_without_new_support` (same) | 2 (team default) | The turn ends `stop_incomplete` with "no supported passage" in `missing` |

Other stops, all deterministic: a second proposal for the same `capability_code` and `body_region` in the same
episode while an earlier one is not terminal, or that already produced an accepted result in the last segment, is
refused (E12 `handler_rejected`, reason `repeat_request`, V03 wording owned here); every capability in `missing_codes`
already unavailable or declined allows `STOP` at once (V28); an urgency interrupt cancels the turn (E11 `cancel_episode_turns`).
These are loop protections, not clinical stop rules (LLM-ARCHITECTURE 5).

### 3.6 Action validation

Every candidate passes, in order; the first failure decides:

1. Turn output schema (E17), with at most one repair step that receives the parse error code (never the raw text).
2. Context form (3.1): free text in episode context, or an action kind outside the context's set, is rejected
   `MODEL_OUTPUT_REJECTED` reason `form_not_allowed`.
3. E12 gateway results already applied scope, schema, phase, question allowlist, kit check and E24's warning guard to
   tool calls; any terminal denial (E12 3.4) ends the turn `rejected`.
4. Body regions are members of the fixed set (CONTRACTS 7); capability codes and condition IDs resolve in the active
   configuration (E05 registry and `condition-assessments-119` through E12).
5. `reason` is non-empty for every action, and `decision_affected` is non-empty for `request_measurement` (D06).
6. Output policy (E12 `OutputPolicyPort.check`) over every string the model wrote: `reason`, `decision_affected`,
   `note`, `text`, draft texts. Any rule hit rejects the whole output (V63, D25).
7. Help context only: E26 `HelpTurnGuardPort.check(help_session_id, candidate)`; `accepted: false` rejects with the
   guard's rule IDs (D25).
8. `request_review.also_tell_ground` from the model is never acted on: the hub stores the action without it, and the
   review card offers the person's own "also tell the ground" control through the handoff (E16). Nothing leaves the
   hub because the model asked (R28 "silently contact anyone"; request R-E13-14).

Every rejection appends audit `assistant.output_rejected {turn_id, rule_ids, field_paths}` with hashes only.

### 3.7 Assessment verification (E13-02)

The assessment job ends its `assessment` phase with `draft_assessment`, whose finalized input schema (E17 catalog)
is:

```
{ summary, findings[{text, body_region, evidence_refs[]}],
  hypotheses[{text, body_region, evidence_refs[], condition_ids[]}],
  contradictions[{text, evidence_refs[]}],
  missing_evidence[{text, body_region, capability_code | null, question_id | null}],
  next_step: {kind: "question" | "measurement" | "plan_step", ref_id} | null,
  urgency_review_requested }
evidence_refs[]: {kind: observation | answer | passage | daily_check, ref_id}
```

Deterministic checks, per claim (finding, hypothesis, contradiction):

| ID | Check | Source of truth | On failure |
|---|---|---|---|
| VR1 | Every ref resolves | E12 `ObservationFactsPort.owner_of`, E01 answers, E10 `read_approved(evidence_release_id, passage_id, use)` | The ref is dropped and counted |
| VR2 | The ref was seen in this job's tool results or context (`SeenSet`) | the turn's `assistant_tool_call` rows and `ContextSnapshot.included_ids` | Dropped: the model cannot cite what it did not read (V23) |
| VR3 | `usable_as_support` is true | E12 support labels (3.5 of E12): failed, rejected, declined, stale, REPLAY exposure, unconfirmed extraction are false | Dropped (D11, R16) |
| VR4 | Owner of every person record is the subject | E12 owner check | The whole output is rejected (V25) |
| VR5 | A `crewmate_palpation` observation supports findings only, never a hypothesis or the closure of a gap | E12 `finding_only` label (EI8) | Dropped from the hypothesis |
| VR6 | An answer with presence `unknown` or `declined` never supports anything | the answer record | Dropped |
| VR7 | A finding keeps at least one usable observation or answer; a hypothesis keeps at least one usable ref; a contradiction keeps at least two | after VR1 to VR6 | The claim is withheld (removed, counted, audited by hash) |
| VR8 | Text passes the output policy | E12 3.7 | The whole output is rejected |
| VR9 | `body_region` in the fixed set; `condition_ids` valid | CONTRACTS 7, configuration | The whole output is rejected |

Unsupported claims are withheld, never decorated with a citation (LLM-ARCHITECTURE 5 "remove or qualify"; the schema
has no qualification field, so removal is the fail safe).

The hub then adds what the model may have omitted, each line rendered from configuration:

- **Missing evidence**: every open CapabilityGap of the episode (E05 `GapFacts`) with its capability words and kit text,
  every pending measurement request, and every allowed question not yet answered (E04). Model items stay when their text
  passes the policy.
- **Contradictions**: every `conflicting` result seen in the job (E14 comparison, E12 retrieval `conflicting`, E11 pathway
  discrepancies) rendered from ui-copy with both IDs, so a material contradiction is never lost because the model left
  it out (LLM-ARCHITECTURE 5 step 6).
- **Next step**: `next_step` text is always rendered by the hub: a plan step's text from E28 (`active_step` must return
  it, so a step outside the active plan gives `null` plus limitation `step_not_in_plan`), a configured question's text
  (allowed set), or a measurement's capability words with the kit check. The model's own words never fill `next_step`.

An optional claim-support pass (E17 release flag `verifier.claim_support_pass`, experiment 4 of LLM-ARCHITECTURE 8)
runs the same loaded model with a distinct prompt over each surviving claim and the text of its cited passages, and
returns `{claim_index, supported: bool}`. It can only remove claims; it never adds or rewrites one.

Storage: `assessment` holds the contract fields; `assessment_claim_ref` holds every surviving ref per claim, including
passage refs that `evidence_ref` cannot carry yet (request R-E12-1), so D10 can be checked from the record.

**Incomplete assessment (E13-03).** When the job times out, exhausts its budget, or the model stops, the job still
stores an Assessment from deterministic content only: the verified draft when one exists, otherwise `findings` and
`hypotheses` empty, `missing_evidence` as above with a first line from ui-copy
`assistant_words.assessment_incomplete` (evidence empty), `contradictions` as above, and `next_step` the active plan's
first step text when E28 attaches a plan, else `null`. The job ends `failed` with `MODEL_TIMEOUT` (or `succeeded` for a
model `STOP`) and `result_ref` pointing to it. The internal columns `completeness` and `stop_reason` are served once
request R-E13-2 lands (V27, V28).

### 3.8 Insights

Trigger: `DailyCheckSubmitted` for a person, while the runtime is `running`; otherwise nothing runs and audit
`insight.skipped {reason: model_stopped}` is written (V69: no insight appears). One `insight` turn per topic of
assistant-policy `insight_topics`, priority 2 (3.10).

1. Context: E12 `ContextBuilderPort.build` with phase `insight`, restricted to the topic's `evidence_codes`, the
   person's own records, over `controller.insight_lookback_days` (request R-E13-5; interim E17 release `controller`).
2. Model steps with the `insight` exposure set; the final output follows E17's `insight-draft` schema `{none: true}` or
   `{topic_id, level, title, text, why, evidence_refs[], habitat_reading_ids[]}` (interim for R-E12-8).
3. Deterministic checks in the commit transaction: topic exists; `level` in assistant-policy `allowed_warning_levels`;
   output policy on `title`, `text`, `why` (including `replay_as_exposure`); then E24
   `InsightWarningPort.validate_and_raise(uow, draft)`, which applies the insight bounds of E24 3.13 (kinds, owner,
   REPLAY, accepted state) and raises the topic's warning at `info` or `watch` when `warning_definition_id` is set.
   `InsightRejected(codes)`: nothing is stored, audit `insight.rejected` with codes only (E24).
4. Hub-rendered parts: `habitat_facts[].text` from ui-copy `designed_states.replay_note` for a REPLAY reading and
   `designed_states.habitat_fact` otherwise (the model names only `reading_id`); `citation.text` from the topic's
   `source_ids` and E10 source titles.
5. One active insight per `(person_id, topic_id)`: a new one sets the previous one `expired` and calls E24
   `on_insight_expired` in the same transaction.
6. Routine: no recheck is added until assistant-policy names the allowed item per topic (request R-E13-5); D17 expects
   no task from the insight.
7. `insight.changed` (person scope) through the outbox.

Dismiss (`actOnInsight`): state `dismissed`, E24 `on_insight_dismissed` dismisses its warning (CONTRACTS 17), audit,
`insight.changed`. Rule and sensor warnings are untouchable from here (R40, V65): E24 has no assistant clear port.

### 3.9 Runtime state machine

`AssistantStatus.state` is derived by E13 from the operator's desired state, E20's process state for the model worker
and E17's identity probe:

| From | Event | To |
|---|---|---|
| `stopped` | operator `start` | `loading` |
| `loading` | E17 probe healthy and `/props` identity equals the release (model path hash, context size) | `running` |
| `loading` | E17 `load_timeout_seconds` passed, identity mismatch, or the worker exited | `unavailable` |
| `running` | `assistant.health_fail_threshold` failed probes in a row, or the worker exited | `unavailable` |
| `unavailable` | E20 restarted the worker within its policy, or operator `start` | `loading` |
| any | operator `stop` | `stopped` |

- The desired state (`running` or `stopped`) persists. The safe state at hub start is `stopped` unless the operator's
  last command was `start`, in which case the hub starts in `loading` (AGENTS 7 "known safe state at start").
- Leaving `running` fails every queued and running turn with `MODEL_UNAVAILABLE` and fails the running assessment job
  with an incomplete assessment (3.7).
- `mode` (`stub` or `live`) comes from the active model release (E17). A `stub` release binds E17's pinned responder and
  is accepted only when the deployment `profile` is `demo` or `eval` (DEPLOYMENT 6.2); in `flight` it is refused at
  start (`unavailable`, `last_error` `CONFIG_INVALID`).
- Every transition writes `assistant_runtime_state`, audit `assistant.runtime_changed` and the event
  `assistant.status_changed`.

### 3.10 Scheduling and preemption

One inference slot (E17 runs `llama-server` with one slot). A bounded priority queue holds turns:

| Class | Priority | Turns | Preempts |
|---|---|---|---|
| Help | 0 | `help` | a running turn of class 1 or 2 |
| Episode | 1 | `conversation` turns in episode context, then `assessment` jobs, FIFO within | a running turn of class 2 |
| Other | 2 | `conversation` turns of other contexts, `insight` | none |

Admission: when the queue holds `max_queued_turns`, a new class 1 or 2 turn is refused at send (503
`MODEL_UNAVAILABLE`, nothing stored); a new help turn evicts the newest queued class 2 turn, then class 1, which fails
with `MODEL_UNAVAILABLE`, so help is never refused for lack of room. Preemption closes the running step's HTTP stream
(E17 `CancelToken`), discards its partial results (no effect was written, E12 INV-E12-13), and puts it back in the queue
with `preemptions + 1`. Someone needs help itself never enters this queue: E26 renders its fixed steps with no call to
E13, and `start_help_turn` only enqueues (INV-E13-10).

### 4.2 The turn loop (`RunTurn`)

Each numbered step is bounded; reads use short read-only units of work, and only step 9 writes.

1. Dequeue the highest priority turn; set `running`, `started_at`, pin the model, config and evidence releases.
2. Episode context: E11 `before_turn`. `Refused`, `Interrupted` or `RedFlagsPending` ends the turn `failed` with a
   notice from ui-copy that names what to do (the help button, or the red flag questions, D05). `Proceed(token)` pins
   the urgency token.
3. Pin the snapshot (3.4) and build the context: E12 `ContextBuilderPort.build(uow, scope, phase, budget)`, where
   `scope` is the `ToolScope` built from the session, the conversation and E02 consent purposes, never from model output.
4. Prompt: E17 `PromptPort.build(release_id, phase, context, transcript)`. The transcript holds previous verified
   messages of the conversation (bounded by the release's `context_settings`) and this turn's tool exchanges.
5. Step: E17 `InferencePort.run_step(request, deadline, cancel, progress)`. `progress` reports first token and token
   counts for the timeouts; nothing of the content.
6. Tool calls: each through E12 `ToolGateway.execute(uow, scope, call)` in call order. A terminal denial ends the turn
   `rejected`; `ScopeViolation` also. Each result is recorded in memory and appended to the transcript; a `tool` stream
   chunk (`started`, then `succeeded` or `failed`) carries only the tool name.
7. Final output or terminal tool: validate (3.6); for the assessment job, verify (3.7) and run the `disposition`
   phase steps within the same budget.
8. Check the snapshot cheaply; loop to step 4 while the budget allows; otherwise stop as in 3.5.
9. Commit, one `BEGIN IMMEDIATE` transaction: authoritative snapshot check (3.4) and E11 `still_valid`; E12
   `EffectApplier.apply(uow, scope, effects, turn_id)`; the assistant message (and notice); the tool call rows; the
   assessment or insight with E24's call; the turn row `completed`; `AssessmentChanged`; outbox events; audit
   `assistant.turn_completed {turn_id, kind, steps, tool_names, duration_ms, prompt_sha256}`. Any failure rolls back
   everything and ends the turn `failed` (`INTERNAL_ERROR`) or `stale`.
10. After commit: stream the verified text as `token` chunks (sentence sized), then `message.completed`; help turns
    call `HelpAssistantSink.turn_completed`; a `request_measurement` sets the conversation to wait for the outcome.

A continuation turn (`measurement_result`, `answer`) is enqueued by `ContinueAfterOutcome` when the request or answer
belongs to the latest action message of an open episode conversation and the runtime is `running`; when it is not, the
conversation shows the stopped state and the person continues later with a new message.

### 4.4 Events

`message.completed`, `turn.failed` (`error` envelope with the turn's code).

## 6. API

All operations exist in `api/openapi.yaml`. Errors use the CONTRACTS 5 envelope (`error.schema.json`) with the codes
listed for each operation; client words come from ui-copy `error_messages`. `Idempotency-Key` is required on every
POST (E01 store, 24 hours plus the command ledger). Role checks are those of `x-roles`; object checks follow.

| operationId | Behavior | Errors |
|---|---|---|
| `getAssistantStatus` | AssistantStatus from `assistant_runtime_state`, the active release and `queue_depth` | standard |
| `setAssistantRuntime` (operator) | `start`: `stopped` or `unavailable` → `loading`; when `running` or `loading` it is a no-op returning the current status. `stop`: any → `stopped`, fails queued and running turns. 200 AssistantStatus | 409 `INVALID_TRANSITION` when no model release is installed (`field_errors.model_release`); 409 `DUPLICATE_COMMAND` for a reused key with another body |
| `openConversation` (crew, crew_medical_officer) | Context checks of 3.1; returns the open conversation when one exists for the same person and context (201 with it; request R-E13-9 proposes 200) | 403 `UNAUTHORIZED_SCOPE`; 404 when `ref_id` is not visible (as `getEpisode` does); 503 `MODEL_UNAVAILABLE` when the runtime is not `running` or `loading`, with `supported_alternative` `open_help` |
| `getConversation` | Owner only; `ETag` is the revision | 404 for another person's |
| `sendMessage` | `text`: appended, turn queued, 202 with the person's message. `reply_to_action`: the message must be the latest `ask` of this conversation and `choice` one of its labels; E13 maps the label to the configured choice ID and calls E04 `EpisodeAnswerPort.answer` with the session (the person answers; the model never does), then queues the continuation. ## 10. Safety, security and privacy

| Hazard | Cause | Mitigation | Test |
|---|---|---|---|
| H1 A failed reading supports a conclusion | Model cites it | VR3, VR7; hub-rendered missing evidence | T-E13-041 (D11) |
| H2 Fabricated citation | Model invents an ID or cites one it never read | VR1, VR2 | T-E13-040, 042 (V23) |
| H3 Assessment applied to changed facts | Correction during inference | 3.4 checks; E11 and E15 backups | T-E13-030 to 033 (V30) |
| H4 Model text shown as a question or a step | Free text in episode context | Form rule (3.6 step 2); configured rendering | T-E13-014, 015 |
| H5 Dose or unreviewed treatment in help | Model text | E12 policy, E26 guard, nothing shown before commit | T-E13-012 (V63, D25) |
| H6 Assistant raises Act now or clears CO2 | Model proposal | E12 and E24 guards; no clear port | T-E13-070, 071 (V65, D17) |
| H7 Help delayed by inference | Shared slot | Help never enters the queue for its fixed steps; help turns preempt | T-E13-061, 062 (V01, R15) |
| H8 Fictitious result | Model writes a value | No tool accepts a value from the model; results come only from E05 after acquisition; `STOP` lists the gap | T-E13-018 (V34) |
| H9 Silent contact | `also_tell_ground` | Never acted on (3.6 step 8) | T-E13-019 (R28) |
| H10 Cross-patient leak | Model names an ID | E12 scope; VR4; owner checks on every endpoint | T-E13-043 (V25) |
| H11 Private content in logs | Prompts or text logged | Logs and audit carry IDs, codes, hashes, counts; prompts are hashed, never stored | T-E13-053 (V26) |

Authorization: every endpoint checks the role, then the object (conversation owner, E15 visibility, E24 visibility,
insight owner). The scope given to E12 is built only from the session and the conversation. Private data: the context
excludes the journal and private reports (E12); conversations are clinical records stored in `hub.sqlite` under E02's
at-rest protection (per DEPLOYMENT.md 5.4); thinking is discarded by E17 and never stored.

What the assistant may do in this epic: propose a configured question, a measurement (kit gate and person consent
follow), an on-board review, a gap, a plan step, a guided check or a handoff draft; draft an assessment and an insight
that the hub verifies; explain in text where the context allows. It may not: answer for the person, create a result,
raise a level above watch, touch a rule or sensor warning, contact the ground, close an episode or urgency, accept its
own output, or act after its facts changed.
